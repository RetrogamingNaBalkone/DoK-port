# Правила проекта DoK-port

- Направления разработки независимы: полноценные GBA- и Nintendo DS-порты
  «Подземелий Кремля» и общий SDL2 Source Port Old Gold/PKR/PKE для Windows/Linux и PortMaster.
  SDL2 не является условием начала GBA-разработки; завершение GBA не является
  условием SDL2-разработки.
- Работа по отдельным задачам и чатам: для GBA читать `docs/gba/plan.md`,
  `docs/gba/handoff.md` и паспорта в `docs/gba/tasks/`; для SDL2 использовать отдельную
  линию `docs/source-port/`. Не считать предыдущий чат доступным.
- Корни реализаций: `ports/gba/`, `ports/nds/`, `ports/sdl2/`.
  Общие сведения об оригиналах — `docs/originals/`, данные — `analysis/originals/`.
  Платформенные тесты и инструменты принадлежат своему порту. Корневой `scripts/`
  обслуживает репозиторий; Ghidra-инструменты — `tools/ghidra/`, анализаторы —
  `tools/originals/`, сводки — `tools/reports/`. Выходы сборки — `build/<порт>/`.
- Для Nintendo DS перед каждой задачей читать [план](docs/nds/plan.md),
  [handoff](docs/nds/handoff.md) и соответствующий паспорт `docs/nds/tasks/Nxx.md`.
  NDS-порт восстанавливается с нуля по декомпиляциям PKR/PKE, ASM и проверкам
  оригиналов. GBA-код не является архитектурной основой; исследования GBA —
  референсы, отдельно принят только профиль баланса монстров из NDS-плана.
  Завершение GBA или SDL2 не является зависимостью NDS, и наоборот.
  После каждой NDS-задачи обновлять её паспорт, реестр NDS-плана и NDS-handoff:
  команды, проверки, ограничения, доказательства и следующий ID. Не менять
  статусы и handoff других направлений по факту NDS-работы; изменения общего
  кода требуют отдельного обоснования и проверки затронутых направлений.
  Все NDS-паспорта самодостаточны для нового чата. Игровых сохранений в NDS
  не добавлять; на microSD записываются только настройки.
- Перед задачами общего SDL2-порта Old Gold/PKR/PKE обязательно читать
  [актуальный план](docs/source-port/plan.md),
  [передачу контекста](docs/source-port/handoff.md) и соответствующий паспорт
  в `docs/source-port/tasks/`. Если паспорта ещё нет, оформить его по протоколу
  плана до реализации. Основой восстановления служат декомпиляции трёх оригиналов,
  ASM и проверки оригинального поведения. Не использовать GBA-порт как
  архитектурную основу и не ставить SDL2-разработку в зависимость от завершения
  GBA. WASDify — источник исследований, ECWolf — ориентир для современного
  порта; они не заменяют проверку оригиналов. После задачи обновлять паспорт,
  Source Port handoff и статусы плана. Не менять статусы и передачу GBA
  по факту SDL2-работы. Для GBA после задачи обновлять её паспорт, план и handoff.
- Существенные выводы, структуры, форматы, различия версий, ограничения
  и решения фиксировать в Markdown в `docs/`. Указывать образец, адресную
  систему, доказательства; явно отделять гипотезы от проверенных фактов.
- Компиляторы устанавливать и использовать из общего каталога инструментов
  пользователя. Не добавлять отдельную копию toolchain в каждый проект.
  Текущая общая установка Zig и настройки VS Code описаны в `docs/building.md`.
- Оригиналы в `originals/` не изменять. `originals/`, `mqa/`, `build/`
  и полный экспорт `decompiled/` не включать в Git и поставку порта.
- Проекты Ghidra, постоянные экспорты и результаты исследований хранить в
  `research/`, вне `build/`: проекты в `research/ghidra/`, доказательства в
  `research/evidence/`, архивы опытов в `research/experiments/`. Полные материалы
  `research/` не включать в Git и поставку; описания и сводки хранить в `docs/`
  и `analysis/`. Не сохранять все промежуточные ROM/ELF, generated banks и
  повторные тестовые кадры: оставлять текущую сборку и обоснованные контрольные
  образцы, выводы и исходные доказательства. Перед очисткой `build/` проверять
  входы сборочных скриптов.
- В `analysis/` хранить в Git уникальные данные оригиналов и компактные итоги.
  Крупные машинные прогоны оставлять локально с явными исключениями Git,
  публиковать сводки в `analysis/summaries/` по `analysis/report-policy.json`.
  После повторного запуска обновлять сводки `tools/reports/summarize_reports.py`;
  сводка не заменяет полный отчёт для машинных проверок.
- Анализ исходных EXE выполнять в Ghidra. Проверять SHA-256 образцов до
  и после анализа. Сохранять проекты, журналы и воспроизводимые скрипты.
- Различать файловое смещение, индекс NE-сегмента, адрес Ghidra и
  runtime-селектор DPMI. Адреса вставок WASDify не считать входами оригинала.
- Полезные материалы прежнего исследования находятся в `C:/Source/wasdify`;
  их происхождение и найденные ограничения описаны в `docs/originals/wasdify-findings.md`.
- Автоматический C-псевдокод хранить отдельно от редактируемых модулей движка.
  Не объявлять его собираемым C/C++ или проверенным эквивалентом оригинала.
- Для каждого перенесённого модуля проверять типы, far/huge pointers,
  calling convention и значимые ASM-эффекты по листингу. Обоснованные
  исправления ошибок оригинала документировать отдельно от восстановления.

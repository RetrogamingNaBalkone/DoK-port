# Эталонные запуски DOS-версий

24 октября 2026 года, задача [G00](tasks/G00.md). Этот документ описывает
проверяемые DOS-эталоны для восстановления поведения. Начальный сценарий
**повторён для обоих оригиналов**; поворот и короткое движение наблюдались.
Поздние сценарии остаются явно незавершёнными. Машиночитаемый статус:
[reference-manifest.json](../analysis/reference-manifest.json).

Цель GBA-порта: единый ROM с переключением RU/EN, общий профиль данных по
[gba-balance-proposal.md](gba-balance-proposal.md), 30 FPS. DOS-эталоны
запускаются отдельно для каждого оригинала: их различия нужно сохранить
в доказательствах, чтобы решения объединённого профиля были явными.

## Стенд и фиксация ввода

Используется общая установка DOSBox Staging, а не toolchain в проекте:
`%LOCALAPPDATA%/Programs/DOSBox-Staging/wasdify-webserver-20261024/`.
Заявленный SHA-256 EXE эмулятора:
`67a907289bad3e25a9be7dd4dc38d882c1c7e74949f8daa103a52476d99f24f5`.
Версия API: `0.83.0 (7b400)`. В конфигурациях итоговой серии
зафиксированы `svga_s3`, RAM 32 MiB,
`core=normal`, `cputype=pentium`, `cpu_cycles=60000`,
`cpu_cycles_protected=60000`. Видео/аудио SDL работают через `dummy`;
`mixer.nosound=true`, `sbtype=sb16`, base=220h, IRQ=7, DMA=1, HDMA=5.
Изображение не выводится на монитор, звук не воспроизводится и не захватывается.
Эти настройки нельзя использовать для вывода о точности звука или стоимости
обычного экранного вывода.

Предварительный запуск RUS без аргументов действительно выбрал VGA 320×200,
256 цветов, mode `13h` (строка `DISPLAY` в
`research/evidence/reference/ru-probe2/stderr.log`). Проба с `-r0` выбрала VESA 640×480,
mode `101h` (`research/evidence/reference/ru-probe/stderr.log`); VGA-стенд её не использует.
Нельзя называть `-r0` способом выбора VGA оригинала.

API этой сборки не предоставляет отдельного keyboard endpoint. Стенд
использует запись в гостевую таблицу клавиатуры; это
**инъекция состояния**, а не аппаратное нажатие клавиши хоста. EXE остаётся
неизменённым; исполнение и побочные эффекты создаёт сама DOS-игра. В журнале
нужны сканкод, порядок нажатий и отпусканий, продолжительность, выбранный
линейный адрес, способ поиска базы сегмента и стартовое состояние.
Результаты такой серии не проверяют IRQ1, BIOS-клавиатуру или точность
эмуляции физических клавиш.

Прежний стенд WASDify использовал таблицу RUS по `SS:0x2155 + scancode`,
счётчик по `SS:0x2152` и последний сканкод по `SS:0x2154`. Это **прежние
сведения, а не автоматически подтверждённые адреса текущего запуска ENG**.
Действующий SS может временно принадлежать обработчику прерывания.
Текущий `scripts/dos_reference.py` ищет единственное в первых 16 MiB
совпадение `OVERFLOW\0UNDERFLOW\0TLOSS\0PLOSS`, вычитает `0x1082`
(RUS) или `0x1132` (ENG) и проверяет пару размеров `(320,200)` по
data+`0xC1FC` или data+`0xC2AC`. Затем обращается по полученному линейному
адресу; DPMI-дескриптор этим способом **не проверяется**. Это отличается
от более строгого поиска LDT прежнего benchmark. Числовой сегмент HTTP memory API
интерпретируется как real-mode `segment * 16`: DPMI-селектор туда напрямую
передавать нельзя. Файловое смещение NE-сегмента, индекс NE, адрес Ghidra,
runtime-селектор и линейный адрес указывать раздельно.

В текущем стенде ENG использует сдвиг +`0xB0`: таблица клавиш data+`0x2205`,
счётчик data+`0x2202`, последний сканкод data+`0x2204`. Нажатие записывает
байт `3` в таблицу, увеличивает 16-битный счётчик и задаёт последний сканкод;
отпускание снимает бит 0. Продолжительности записываются по часам хоста,
без обещания точного совпадения игровых тиков между запусками.

Оригинальный `RUS/README.TXT` (CP866) описывает: стрелки — движение/поворот,
Shift со стрелкой — ускорение, Alt со стрелкой — смещение, Ctrl — огонь,
Space — дверь, Tab — карта, P — пауза, M/J — мышь/джойстик, Esc — выход.
Это документированная схема управления, не результат проверки каждого
действия в G00. Клавиши 1/2 меняют оружие при его наличии; README отдельно
предупреждает, что в начале нужно найти лазерный пистолет.

## Последовательность сценариев

Каждый сценарий ведётся отдельно для RUS и ENG. Новая серия начинается новым
процессом эмулятора и чистой рабочей копией. Неподвижный кадр не задаёт
одинаковое число игровых обновлений: игра может пропускать перерисовку.
Продолжительность по часам хоста нельзя подменять игровыми кадрами или
считать универсальной скоростью DOS-движка.

| ID | Сценарий и начальное условие | Что сохранить | Статус |
|---|---|---|---|
| `level1-start` | Новая игра, LEVEL1; пройти меню и предысторию | Ввод, стабильный индексный кадр и состояние героя повторены; настоящая VGA-палитра не захвачена | observed RU/EN |
| `turn-in-place` | Сохранённый старт LEVEL1, без перемещения | Right меняет heading при неизменных x/y/z; кадры и состояния сохранены | observed RU/EN |
| `wall-follow` | Отдельный чистый старт, маршрут к выбранной стене | Маршрут, углы, длительности ввода, кадры прохода и упора в стену; без телепортации | planned |
| `door` | Доступная дверь на записанном маршруте | Состояние до/после Space, закрывание, ключ/условия, если обнаружены | pending; только попытка Space |
| `pickup` | Предмет на записанном маршруте | Вид предмета, кадры до/после, уведомление, изменение HUD/инвентаря | planned |
| `shot` | Подобрано оружие и есть заряд | Ctrl, расход заряда, снаряд/попадание; отсутствие оружия отдельно не считать успешным выстрелом | pending; только попытка Ctrl |
| `enemy-wake` | Выбран конкретный враг с подтверждённым положением | Вход в область обнаружения, первый видимый ответ, движение и атака; отделить гипотезу о пороге от замера | planned |
| `death` | Воспроизводимый маршрут к получению урона | HUD перед смертью, переход состояния, жизни/повторный старт, экран | pending |
| `level-transition` | Достигнут штатный выход уровня | Условия выхода, финальный экран, загрузка следующего уровня, входное состояние | pending |

`planned` означает, что маршрут ещё предстоит определить; `pending` — что
сценарий предусмотрен, но доказательство его выполнения ещё не получено.
Ни один поздний сценарий не считается выполненным по одному стартовому кадру.

## Проверяемая статическая база

[world.md](world.md) даёт начальную позу по коду Ghidra и ресурсам:
RUS `(15120, -300, 22800)`, ENG `(15120, -300, 23280)`, heading=90.
Это **статический расчёт**, отдельно подтверждённый чтением работающей игры
в начальных сценариях ниже. Координаты
объекта: x по `+0x26`, вертикальная y по `+0x2A`, z по `+0x2E`.
Ось карты с исходными строками отражается:
`runtime_row = length - 1 - source_row`; сторона клетки — 480.

Начальная позиция героя в исходной MMap: RUS `(31,16)`, ENG `(31,15)`;
координаты от нуля, столбец/строка исходного LEVEL. Поэтому одинаковый ввод
двух оригиналов не обязан давать одинаковый вид и маршрут. Другие различия
карт и параметров LEVEL1–3 описаны в
[level-version-comparison.md](level-version-comparison.md). Нельзя объявлять
RUS/ENG эквивалентными по совпадению числа врагов или текстур.

## Наблюдения текущей серии

Основная серия: [RU01](../research/evidence/reference/ru-01/report.json),
[RU02](../research/evidence/reference/ru-02/report.json),
[EN01](../research/evidence/reference/en-01/report.json),
[EN02](../research/evidence/reference/en-02/report.json). Дополнительная проверка
с изолированными конфигами: [RU03](../research/evidence/reference/ru-03/report.json).
В каждом каталоге сохранены `dosbox.conf`, `stdout.log`, `stderr.log`,
индексные кадры `*.idx`, PNG и приватный `level1-memory.bin` (16 MiB).
Индексные кадры начинаются с физического `0xA0000`, длина 64000 байт.
PNG показывает индекс как серый цвет, а не исходную цветовую палитру.
Начальные кадры RU01 и EN01 просмотрены: игровая сцена и HUD видны.

В каждом свежем процессе после нахождения data-базы выдерживается 1 с,
затем подаются шесть Enter (`0x1C`, удержание 0,12 с, ожидание 1,5 с).
После каждого нажатия сохраняются кадр и 64 KiB data-сегмента. Для стабильного
кадра нужны три одинаковых чтения VGA с интервалом 0,05 с, максимум 50 попыток.
Это критерий стабильности чтения, а не три доказанно завершённых игровых кадра.

| Язык | Начальная поза x,y,z / heading | Здоровье / энергия / жизни / счёт | SHA-256 начального `.idx` |
|---|---|---|---|
| RUS, три свежих процесса | `15120,-300,22800` / 90 | 100 / 0 / 3 / 0 | `2998ed9d6f592e16ddd662b467e6635d15272e3181d5baec09f09d4c88ae2a1c` |
| ENG, два свежих процесса | `15120,-300,23280` / 90 | 100 / 0 / 3 / 0 | `72993890dfcf84a6e63f7be16f5beb881b868090c6d39bcb00d7da09b18c22a9` |

Линейные базы data в отчётах: RU `0x1D38E0`, ENG `0x1D7090`;
герой: RU `0x1FE7FE`, ENG `0x20D38A`. Это адреса конкретных запусков,
не файловые смещения или стабильные адреса для будущего процесса.
Герой ищется по единственной комбинации ожидаемой позы и class=1; после
нахождения из этой же памяти читаются heading и последующие изменения позы.
Поиск привязан к заранее восстановленной стартовой позе; это не общий
детектор объекта героя на произвольном этапе игры.

При `--actions` идут Right (`0x4D`, 0,35 с), Forward (`0x48`, 0,6 с),
Space (`0x39`, 0,12 с), Ctrl (`0x1D`, 0,4 с); после каждого — 0,5 с
ожидания, кадр и чтение героя. Наблюдения RU01/RU02: heading 90→80/82
при неизменных координатах; ENG01/ENG02: 90→83/81. Forward меняет x/z.
Это подтверждает поворот и движение, но **не проход вдоль выбранной стены**.
Финальные позы различаются между повторами; схема по времени хоста
не даёт покадрового повторения и не доказывает различия скорости локализаций.

Space/Ctrl оставлены как `use-attempt`/`fire-attempt`: соответствующие кадры
совпали с предыдущим кадром Forward. Начальная энергия нулевая, вооружённый
выстрел не подтверждён. Нет основания считать проверенными открытие двери,
подбор, попадание, пробуждение/атаку AI, смерть или переход уровня.

Повторение (выбрать новые, ещё не существующие каталоги):

```powershell
C:/Source/wasdify/.venv/Scripts/python.exe scripts/dos_reference.py ru --output research/evidence/reference/ru-new-01 --actions
C:/Source/wasdify/.venv/Scripts/python.exe scripts/dos_reference.py ru --output research/evidence/reference/ru-new-02 --actions
C:/Source/wasdify/.venv/Scripts/python.exe scripts/dos_reference.py en --output research/evidence/reference/en-new-01 --actions
C:/Source/wasdify/.venv/Scripts/python.exe scripts/dos_reference.py en --output research/evidence/reference/en-new-02 --actions
```

Запуски последовательны, HTTP по умолчанию `127.0.0.1:8137`. Занятый порт
вызывает отказ; стенд завершает только свой процесс. Текущий скрипт запускает
DOSBox с `--noprimaryconf --nolocalconf`, чтобы не наследовать пользовательский
конфиг. EN02 и RU03 выполнены с этими флагами; RU01/RU02/EN01 созданы до
этого уточнения. Их `stderr.log` сообщает об отсутствии primary config;
начальные кадры совпали с серией с флагами. Условия каждого запуска
сохранены в его собственном отчёте, а не выравниваются задним числом.

## Происхождение и ограничения

- [decompilation.md](decompilation.md), [reproducing.md](reproducing.md):
  Ghidra 12.1.2, `x86:LE:16:Protected Mode`; C-псевдокод не исполняемый эталон.
- `C:/Source/wasdify/docs/games/dungeons-of-kremlin/versions.md`: происхождение
  и размеры двух известных EXE; внутренний номер релиза неизвестен.
- `C:/Source/wasdify/docs/games/dungeons-of-kremlin/benchmark.md` и
  `scripts/{profile_kremlin,run_kremlin_profile}.py`: источник прежнего способа
  инъекции/поиска LDT и ограничений. Там профилировались диагностические
  изменённые копии RUS; их FPS и снимки не переносятся в G00 как новые эталоны.
- `originals/pkr/RUS/README.TXT`: исходная документация управления и ключей
  `-r`, `-r1`…`-r4`. Обещанные режимы README не заменяют проверку EXE;
  известные изменения WASDify к оригиналам G00 не применяются.

Приватные кадры, состояния, игровые копии и дампы остаются под
`research/evidence/reference/` и не включаются в Git или поставку GBA-порта.

# G20C: Проверка отрисовки непрозрачных участков колонок

## Контекст и статус

Добавлено 27 октября 2026 года по запросу пользователя: выполнить до UI G20B.
**Статус: готово; native опыт завершён с отрицательным результатом.**
Это отдельный ограниченный опыт после G20A,
а не возобновление завершённого архитектурного исследования.

Сначала читать `AGENTS.md`, `docs/gba/plan.md`, `docs/gba/handoff.md`,
[итог оптимизации](../gba-optimization-handoff.md),
`analysis/gba/g20a-final-handoff.json` и `analysis/gba/g20a-final-costs.json`.
Контроль — ROM2775, CPU-слой120×128. Offline sparse-post audit подтвердил
точное восстановление колонок и оценил метаданные; native ускорение неизвестно.

## Задача

Реализовать и измерить отрисовку маскированных текстур по непрозрачным
участкам колонок (sparse runs/posts), пропуская прозрачные интервалы.
Не менять разрешение, геометрию, LIGHT16, AI, игровые правила и дальность.
Ноль непрозрачной текстуры остаётся чёрным пикселем; пропуск допустим только
для маскированного материала. Сохранить clipping, coverage и перекрытия.

Ограничиться этим опытом: не перебирать заново проигравшие архитектуры и
не начинать Performance. При отсутствии существенного общего выигрыша
зафиксировать отрицательный результат и перейти к G20B.

## Проверки и критерии готовности

- Парные native-clock mGBA замеры против2775 со звуком: пять тяжёлых видов,
  spatial440 и живые маршруты120 кадров на трёх уровнях, обе локализации.
- Проверить итоговую PPU-картинку, маски, масштабирование и перекрытия,
  включая динамику; указать фактический охват проверок.
- Измерить полное CPU-время, FPS предъявления, ROM/RAM/стек; не выдавать
  экономию одной стадии или долю прозрачных texels за выигрыш всего кадра.
- Сохранить контрольный ROM, воспроизводимые команды, ROM/ELF/map и отчёты.
  Принимать новый путь только по парным данным без регрессий картинки и игры.
- Документировать решение принять/отклонить и ограничения. Отрицательный
  результат закрывает опыт; достижение30FPS не является условием G20C.
- Обновить этот паспорт, план и handoff. G20 budget закрывать только по
  фактическим критериям; следующим этапом остаётся UI G20B.

## Результат

Реализован отдельный `hw_v128_sparse_posts`: post-LIGHT source runs,
точное преобразование Q16-интервалов, прежние clipping/coverage/overlaps,
opaque zero/black и динамический fallback. Основной2775 не заменён.

Парные native-clock/PCM RU/EN: heavy5 CPU+9,67–28,32%; spatial440 на каждом
языке (880 пар) даёт медианы CPU+1,03–5,64%, минимумы FPS ухудшились.
Живые turn120 и walking120 на3 уровнях×2 языка также медленнее контроля.
Все880 spatial,10 heavy,396 detail PPU пар exact;48 динамических mutation
пар exact. ARM4096 sparse/512 rectangle и suites sprites/interactions/AI-combat/UI
прошли;282 transitions/5002 PPU callbacks без mixed frames. Известный старый
Pause/Resume intermediate-frame issue этим не закрыт.

Метаданные498688B, ROM16438720B,
SHA `7dfe60cff69b2862cfef30c58bac43f64ef9e26d32a96aa9f77e66600d099e94`.
EWRAM261300/free844, IWRAM24544/free32 до8192 stack reserve;
main stack2528/margin5408, IRQ80/margin80. Размещение `edge_start` в ROM
проверено отдельным placement control: его цена только0,16–0,64% heavy CPU.

Решение: **отклонить этот путь, сохранить2775, продолжить с G20B**.
30FPS и бюджет G20 не достигнуты; Performance не создавался.
Это не отрицательный вывод обо всех возможных sparse kernels.
Полный охват, ограничения, команды и артефакты —
[native trial](../gba-sparse-posts-trial.md), `analysis/gba/g20c-sparse-posts.json`.
Сборки `research/experiments/g20c-sparse-posts/` и `research/experiments/g20c-sparse-repeat/` byte exact
по всем трём ROM; отдельная копия `artifacts/gba/DoK-port_sparse_posts_trial.gba`.
Физическая GBA и полное прохождение не проверены.

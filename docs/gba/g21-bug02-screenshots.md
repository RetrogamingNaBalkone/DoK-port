## Локализация по карте

Добавлен воспроизводимый анализатор, без сторонних Python-зависимостей:

```powershell
py -3.14 ports/gba/scripts/locate_bug02_screenshot.py
```

Он читает сохранённую копию PNG и прежние JSON исходных карт
`research/evidence/runtime/ru/LEVEL{1,2,3}-runtime.json`. Нового анализа EXE
не выполняет. Проверяет все 4096 положений героя на каждом уровне, используя
контуры стен из второй карты и преобразование `ui_map.inc`: зеркальный X,
клетка 3×3 пикселя, предполагается центрированная карта.

Из 425 пикселей контура RGB(148,74,33) лучшее совпадение — **LEVEL1,
клетка `(21,48)`, 415/425**. Следующие результаты LEVEL1:303/425 в `(20,48)`
и296/425 в `(22,48)`; лучшие LEVEL2/3:285/425 и197/425. Анализатор не моделирует
двери, посещённость и динамические объекты; несовпавшие 10 пикселей пока
не атрибутированы. Поэтому это сильная локализационная гипотеза, а не
восстановленное состояние пользовательской сессии.

Единственный белый пиксель маркера в координатах GBA — `(121,73)`.
При центрировании это `ink=256` в `ui_map.inc`, сектор **20–64°**.
Прокрутка карты, движение между снимками, точный угол и дробная позиция
не исключены. Карта не даёт точных мировых x/z внутри клетки.

Это существенно отличается от прежнего sweep: его LEVEL1 fixture находился
в `(57,52)`, LEVEL2/3 — на старте. Прежние750 кадров не покрывают новую

## Точное воспроизведение и изоляция текстуры

Пользователь уточнил: артефакт уже виден на игровом снимке; чтобы поймать
его, достаточно ходить и поворачиваться в этой комнате. Выполнены четыре
маршрута с реальным keypad, collision, AI, анимацией и боем: три по600
отрисовок и локальный212. Старт задавался fixture; для длительных маршрутов
HP/броня32767 позволяли не прерывать исследование. Использован capture hold
с дополнительным ожиданием VBlank; это не измерение производительности.
Открытого пользовательского окна mGBA не оказалось; работал отдельный core.

```powershell
py -3.14 ports/gba/scripts/probe_bug02_walk.py
py -3.14 ports/gba/scripts/probe_bug02_walk.py --cell 17 52 --heading 0 --out build/gba/bug02-walk-center
py -3.14 ports/gba/scripts/probe_bug02_walk.py --cell 17 52 --heading 0 --out build/gba/bug02-walk-dense
py -3.14 ports/gba/scripts/probe_bug02_walk.py --cell 21 48 --phase 73 457 --heading 22 --local --out build/gba/bug02-local-walk
```

Первые два прогона сохраняли каждый четвёртый PPU-кадр; после расширения
анализируются все кадры, контактные листы по-прежнему содержат каждый четвёртый.
Ранжирование тёмных полос — средство просмотра: спрайты и сама текстура тоже
дают высокий балл, автоматическим детектором BUG02 это не объявляется.
PNG-листы и JSON поз находятся в соответствующих каталогах `build/gba/`.

Рисунок пола позволил восстановить дробную позу: **LEVEL1,
x10153/y−300/z23497, heading22°, клетка `(21,48)`, фаза `(73,457)`**.
Исследовательские скрипты и C-перебор фаз сохранены локально в
`research/experiments/bug02-20261101/`. Углы0–359° и фазы с шагом15 были
сужены до шага1. Полное совпадение714 выбранных пикселей травы подтверждено
затем в mGBA; оно не означает восстановления всей динамической сессии.

Постоянная воспроизводимая проверка уже найденной позы:

```powershell
py -3.14 ports/gba/scripts/audit_bug02_screenshot.py
```

Она задаёт реального героя в указанную позу, разрешает20 отрисовок живого AI
(начальная мышь у потолка улетает), затем замораживает мир. Проверены:

- Центральное окно GBA `[110,145)×[0,38)` — **1330/1330 пикселей** точно
  совпали с пользовательским PNG после приведения RGB к15-битной палитре.
  Отличия HUD, оружия и акторов в остальных частях кадра не скрываются этим
  утверждением.714 пикселей пола также точны по всем цветовым каналам.
- В `[110,145)×[0,30)` — **1050/1050 пикселей** совпали с независимым
  декодированием активных HBlank-матриц, VRAM tilemap/tiles и палитры.
  Их даёт аппаратный BG; наложения CPU или спрайта в этом окне нет.
- BG2CNT — `0xb682` для ближней полосы и `0xb882` для следующей: материал
  один, LIGHT0/7 меняется по Y, одинаково для всех X. В строке8 все четыре
  контрольных X110/120/130/140 имеют один и тот же LIGHT0 и map screen22.
  Тёмный пиксель `(130,8)` — GPU UV `(4,6)`, palette index250, BGR5552215;
  это значение исходного рисунка, а не отдельное затемнение столбца.
- Ресурс потолка — **`ДПОТОЛОК1`**, CP866 hex `848f8e928e8b8e8a31`,
  исходник96×96; аппаратная плитка32×32. Извлечённый исходный рисунок
  сохранён для просмотра. В этой комнате FC glyph32/inset10, не низкий
  CPU-потолок inset400 из прежнего sweep `(57,52)`.
- Замена только этой текстуры одноцветной в памяти отдельного эмулятора
  даёт1050 одинаковых пикселей в проверенном окне и убирает полосу.
  Геометрия, карты, матрицы и производственный код не меняются. После возврата
  исходного банка **весь PPU-кадр** совпал с кадром до замены.

Для изоляции рисунка менялся источник банка в памяти core с обычной emulated
DMA-загрузкой. Прямая запись хоста в VRAM не инвалидирует декодированный
tile cache mGBA и не подходит для такого опыта. Файлы ROM/RES не изменялись;
SHA ROM и исходного RES проверены до/после. RES RUS:
`af7135fbcfc765c1e963682a29b108ffe90d652d96fa130cf9db6b217277b816`.
Core SHA-256: `5cac11c643d7f8dfa50c68855f2f2240ff7cc0b4cd0312dd9e17a639c85667e4`.

Текущие доказательства: `build/gba/bug02-reproduced/` —
`reproduction.json`, `reproduced.png`, соседние21/22/23°, `flat-texture.png`,
`restored.png`, `original-texture.png`. Постоянные контрольные копии —
`research/evidence/gba/bug02-20261101/reproduced/`, вне Git.

**Что установлено:** пользовательский эффект идентифицирован; в этой позе
тёмная полоса получается из рисунка потолка при текущей выборке UV.
Прежняя гипотеза о различном LIGHT соседних CPU-полигонов не объясняет этот
образец. Сбой DMA, наложение мыши и порча tilemap в проверенном окне не нужны
для его появления: каждый пиксель объясняется текущим аппаратным фоном.

**Что ещё не установлено:** насколько рисунок полосы усиливается именно
аппаратной32×32 выборкой/проекцией GBA по сравнению с исходной DOS-растеризацией.
Наличие тёмных досок в исходном RES не доказывает эквивалентность проекций.
Новый запуск исходного x86 raster или полный DOS-кадр здесь не выполнялся.
Поэтому BUG02 не закрывается как «поведение оригинала» и исправление картинки
не подменяется заменой/осветлением исходного рисунка. Следующий шаг G21 —
сверить UV/видимость этой области с оригиналом и выбрать обоснованную коррекцию,
если расхождение подтвердится. Далее G20D → G22.

Новые проверки: успешный запуск воспроизведения с assert для всех указанных
пикселей, flat/restore, `py_compile` трёх новых/изменённых Python-скриптов,
повторная локализация карты и `git diff --check`. Runtime, пользовательская ROM
и другие порты не менялись; аппаратного прогона и приёмки G21 нет.

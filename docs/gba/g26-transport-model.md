# G26: стоимость аппаратного потолка и решение по H10

## Решение для текущего релиза

1 ноября 2026: **G26 готова; новый native backend H10 не открывать**.
Проверена конкретная схема: кешировать готовые UI OAM и загружать только
изменённые строки оружия. Она помещается в память, но не устраняет постоянные
затраты второго affine-потока и построчного OAM. Даже оптимистическое удаление
всей добавки стадий UI/setup и copy оставляет проигрыш в сценах без низкого
потолка. Эту переделку не включать в текущий релиз; подбор grid/feedback/порогов
на старом transport не возобновлять. Следующий ID — **G27**.

Это решение о проверенном transport, не утверждение о невозможности любого
GBA-рендера. Границы измерений ниже не являются отложенной задачей. Production
остаётся G22; новая пользовательская ROM не выпускается.

## Контроль и измерительные образцы

Контроль `g22_split_active` собран из текущих исходников, затем повторно связан
после правки compile guard. Обе сборки и пользовательский кандидат совпали:
SHA-256 `53fdf1b1b868effecfd68c8feb87ffb60bcc72190a4d01f38d8684a781860247`.

На той же базе собраны два **диагностических** образца без нового алгоритма:

- `g26_ui_transport`: только `HW_UI_OBJ`. CPU продолжает рисовать низкий потолок,
  UI уходит в OBJ, foreground использует OAM streaming. Изолирует цену
  transport без экономии нового потолочного sampler.
- `g26_low_transport`: тот же путь плюс `HW_BG_LOWERED`. BG3 рисует низкий
  потолок, CPU публикует его coverage. Выбор режима фиксирован; grid/feedback
  не исполняются. Это контроль модели, не новая попытка подобрать пороги.

Общий Zig 0.13.0, Python 3.14, mGBA libretro/replacement BIOS; core SHA,
полные ROM SHA и source hashes находятся в machine report. Здесь адреса —
GBA memory-mapped, координаты — GBA-мир. DOS EXE не анализировались.

## Модель байтов, памяти и расписания

Источник — `hardware_bg.inc`, `hardware_obj.inc`, `hardware_ui_obj.inc`,
`hardware_direct.inc`, `gba_hw_scratch.h` и linker map именно этих образцов.
Аппаратные единицы сверены по [Tonc video](https://gbadev.net/tonc/video.html)
и [Tonc DMA](https://gbadev.net/tonc/dma.html): 1232 cycles/строку,
68 строк VBlank =83776 cycles, кадр =280896 cycles; HBlank =272 cycles.
Повторный HBlank DMA останавливает CPU; payload в байтах не равен cycles.

| Расход | G22 / Mode1 | UI probe | BG3 / Mode2 |
|---|---:|---:|---:|
| DMA0 affine на HBlank | 16 B | 16 B | 32 B |
| DMA2 BG control на HBlank | 2 B | 2 B | 4 B |
| DMA3 OAM на HBlank | 0 | 32 B | 32 B |
| Итого на видимую строку | 18 B | 50 B | 68 B |
| На 160 HBlank одного video frame | 2880 B | 8000 B | 10880 B |
| Один affine frame, включая строку-сентинел | 2900 B | 2900 B | 5796 B |
| Два завершённых affine frames | 5800 B | 5800 B | 11592 B |
| Отдельный Mode4 hold | не нужен | не нужен | 5796 B |

Первая строка affine/OAM публикуется CPU при rearm; таблицы имеют 161 запись,
но строка 0 не является дополнительным HBlank. Публикация front выполняется
в VBlank, а HBlank-передачи продолжаются **на каждом видеокадре**, в том числе
пока CPU готовит очередную сцену. Поэтому нельзя прибавить 8000 дополнительных
байт только один раз на готовый игровой кадр или объяснить всю разницу copy.

DMA1 обслуживает PCM. DMA0 и DMA2 зарезервированы affine/control. DMA3
в Mode2 используется и для immediate VRAM upload, и для OAM HBlank; immediate
записи source/destination/control защищены от VBlank IRQ, streaming после них
перезапускается. Просто выключить этот DMA нельзя: прежние 64 affine OBJ
с перекрывающимися полосами вместе с UI уже исчерпывали строчный OBJ budget.

Общие загрузки на **готовый draw**, а не каждый video frame:

- Foreground —16384 B в `06010000..06013fff` при 128 строках; одинаков в трёх
  образцах. UI —до6784 B, уже dirty/reuse; палитры —1024 B при смене view.
- Mode1: UI в `0600e000..0600fa7f`, оружие в `06006000`, BG0 map в `06007800`.
  Mode2: UI в `06014000..06015a7f`, оружие в `06016000..06017fff` с pitch,
  округлённым до четырёх tiles. Weapon stage допускает5120 B, OBJ atlas8192 B.
  Mode1 уже использует dirty weapon; Mode2 загружает все используемые строки
  и обнуляет padding, затем заново формирует normal OBJ UI.
- Шесть affine maps занимают24576 B в `06008000..0600dfff`. Mode2 заменяет два
  дубликата базовых maps картами низкого потолка: дополнительной полной map
  загрузки нет. Одна обновлённая world cell пишет6×16=96 B, cold window256
  cells —24576 B. Одношаговый сдвиг окна по оси —16 cells, диагональ —31.
- Texture phase update —3×1024 B на изменённый материал. Базовые материалы
  сохраняются; новый потолок не создаёт отдельного полного texture upload.

| Образец | EWRAM занято / свободно | IWRAM занято / свободно до стека |
|---|---:|---:|
| G22 | 261476 /668 B | 22912 /1664 B |
| UI probe | 261460 /684 B | 22912 /1664 B |
| Mode2 probe | 261460 /684 B | 22276 /2300 B |

Резерв стеков8192 B сохранён. Mode2 помещается благодаря alias **11592 B**
dual frames в хвосте legacy `covered[]`, а отдельные5800 B старых frames
заменяются5796 B hold. Это не бесплатная память: payload geometry cache
уменьшается с28637 до17041 B; при переполнении выполняется CPU rebuild.
Front hold необходим до окончания перехода в Mode4, где legacy renderer
переиспользует `covered[]`. Отказ от него нарушает lifetime читаемой DMA памяти.

В warm-сценах с PCM copy занимает примерно51–53 тыс. cycles у G22 и62–65 тыс.
у probes. Это стадия с реальным upload и обслуживанием IRQ, а не стоимость
одного DMA3. Предиктор `hw_upload_budget` оставляет запас: без изменений
UI/map/weapon48904 cycles для G22 и62904 для UI probe; объёмы dirty tiles,
map commands и animation blocks добавляются отдельно. Начинать такой пакет
произвольно поздно в VBlank нельзя. Cold uploads используют forced blank;
они не обязаны целиком помещаться в один обычный VBlank.

По18 warm/frozen поз на ROM (шесть тяжёлых +PERF01–03, RU/EN),6 прогревов,

Никаких primitive hooks или новых таймеров в рендер не добавлено.

RU+EN: UI transport **+3,678…+5,636%**, медиана+4,143%; Mode2
**−26,494…+14,389%**, медиана+9,795%. Не выдавать положительный L1 за общий

На L3 ухудшение CPU не всегда пересекает ступень предъявления, FPS в этих
позах прежний. Это frozen нагрузка, не новые live боевые FPS.

По18 actual PPU-пар RU/EN на probe: UI-only RGB exact; Mode2 меняет до1009
фоновых RGB-пикселей. Foreground, overlay, coverage и leases exact у обоих.
Дополнительно coverage проверена после timing во всех18 позах каждого probe.
Аппаратный низкий потолок использует другую текстурную выборку и **не является
exact-оптимизацией изображения**, несмотря на сохранение границ и перекрытий.

54 held snapshots подтверждают размеры оружия, dirty masks, DMA controls,
BG/OBJ diagnostics и prepare cost. Эти snapshots сняты отдельно без timing PCM
нагрузки и не подставляются вместо CPU-пар. `timer_sample()` уже возвращает
cycles: умножать `g_hw_bg_prepare_cycles`/`g_hw_obj_diag` на64 нельзя.

Современные пары воспроизводят характер старого lowered опыта: большие
локальные выигрыши потолочных L1 и проигрыш остальных сцен. Старые
−21,1/−31,1% относятся к ROM2775, новые−16,84/−26,46% — к G22, их нельзя
склеивать. Старые adaptive/grid/feedback результаты сохранены в исходных
отчётах; они не считаются измерениями этих ROM.

## Конкретный кандидат transport и причина отказа

Рассмотрена **dirty-OAM + dirty weapon upload**: при неизменных UI tiles,
keys и пяти полях weapon descriptor сохранять OAM, иначе заново упаковать;
оружие сравнивать с конечным pitched OBJ atlas, загружать только изменённые
строки, очищать padding при смене размеров. На Mode1↔2, Mode4, view/cold
обязательно инвалидировать. До32 B persistent ключа помещаются в684 B,
OAM уже сохраняется аппаратно; DMA3 расписание и8192 B стека остаются прежними.
Сравнение с нынешним `06006000` для Mode2 неверно: weapon находится в `06016000`.

Это устраняет часть UI упаковки/weapon copy, **но в измеренных held позах
оружия вообще нет**, dirty UI masks нулевые, а UI/OAM transport всё равно
дороже. Полная добавка copy Mode2 —10,7–12,8 тыс. cycles; даже её бесплатное
устранение недостаточно. Более щедрый бюджет: убрать одновременно всю добавку
стадии UI (включает low affine prepare) и copy относительно G22. Для L3:

| Поза | Полный проигрыш | Добавка UI/setup | Добавка copy | Остаток после условного бесплатного удаления обеих |
|---|---:|---:|---:|---:|
| 1544 | 86272 | 32384 | 11840 | 42048 cycles |
| 1623 | 73216 | 33024 | 11712 | 28480 cycles |
| 1940 | 89408 | 34624 | 11072 | 43712 cycles |

Это арифметическая чувствительность по медианам стадий, **не измерение новой
ROM и не строгая аддитивная модель IRQ**. Она заведомо щедрее реального
dirty-кеша: тот не удаляет affine prepare. Остаток включает повторный DMA,
размещение/код, IRQ и geometry cache; всё целиком приписывать DMA нельзя.
Изолированный UI probe уже показывает системное замедление всех стадий,
хотя выполняет прежний CPU sampler и имеет прежний размер IWRAM.

При сохранении fixed Mode2 в сцене без низкого потолка sampling-экономия
равна нулю, а transport сохраняется. Кеш UI не делает этот путь равноценным Mode1.
Старый adaptive CPU fallback устроен иначе: `hw_bg_fill_single` пакует одну
матрицу в dual slot, UI возвращается в BG0, DMA3 OAM отключается. Его HBlank
payload снова18 B; нельзя приписывать ему68 B fixed Mode2. Однако меньший
geometry-cache, mode selection и переходы остаются; предыдущие парные опыты
adaptive не дали общего выигрыша. Нового adaptive прогона здесь нет.
Подбирать снова момент переключения, не устранив причину, запрещено паспортом
G26 и не оправдано прежними adaptive результатами. Поэтому кандидат отклонён
на стадии модели; нового паспорта native-переделки не создано.

```powershell
py -3.14 -X utf8 tools/reports/summarize_reports.py
py -3.14 -X utf8 tools/reports/summarize_reports.py --check
git diff --check
```

Контрольная сборка прошла host/UI и Linux/Thumb cross-check. Исправлен только
compile guard: `hw_upload_budget` не вызывает отсутствующий BG0 map helper
у fixed UI-OBJ probe; G22 код и SHA от этого не меняются. Новых runtime
оптимизаций не принято. Подробные argv — `research/evidence/gba-g26/commands.json`,
там же raw evidence; logs/пробы — `build/gba/g26/`. Полный локальный отчёт —
`analysis/gba/g26-transport-model-20261101.json`, Git-сводка — `analysis/summaries/`.

Полный spatial/live sweep, новая регрессия переходов/воды/боя и физическая GBA
на этих диагностических ROM не выполнялись; они не предлагаются в поставку.
Модель lifetime не заменяет transition acceptance. Production ROM побайтно
прежняя; G21/BUG02, оригиналы и NDS/SDL2 не изменены. **Передача — G27**.

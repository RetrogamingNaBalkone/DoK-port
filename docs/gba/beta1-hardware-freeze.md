# G21: зависание Beta 1 на физической GBA

30 октября 2026 года. Предварительная диагностика по фотографии пользователя
и статическому анализу реализации. В первичном проходе исправление и аппаратное
воспроизведение не выполнялись; последующий проверочный ROM описан ниже.
Причина сбоя пока не установлена.

## Наблюдения и образец

Пользователь сообщил: GBA Beta 1, EZFlash Omega Definitive, **Clean Boot**,
полное зависание. Интерфейс съезжает **в момент зависания**, до этого выглядит
нормально. Фото приложено к чату; отдельной локальной копии фото нет.

На фотографии стены и дверь остаются узнаваемыми, пол/потолок покрыты
повторяющимися диагональными полосами. Повреждён также интерфейс: показатели
HP/патронов находятся внизу ближе к центру вместо верхних углов; части длинной
рамки сообщений видны сверху. Это не только неправильная перспектива пола.
Эталонный кадр той же сборки:
`build/gba/ui01-credits/hardware/hw_v128_entity_rect/ui-check/game-0.png`.

Локальные `artifacts/gba/DoK-port_UI01.gba` и
`build/gba/ui01-credits/hardware/hw_v128_entity_rect/dok-diagnostic.gba`
проверены `Get-FileHash -Algorithm SHA256`: обе имеют SHA-256
`cf30cf8ab1e21c35b2da1f13d3fb5cda8224b27efe32041ac9893fce5727df57`,
26645528 B, совпадают с манифестом Beta 1. Файл на microSD не проверен.

## Что подтверждено в коде

Все адреса ниже — адресное пространство GBA/MMIO, не файловые смещения,
адреса Ghidra, NE-сегменты или DPMI-селекторы. EXE оригиналов не анализировались.

Состав сборки проверен по `hardware/prototype-build.json` указанного каталога:
`HW_BG`, `HW_ROW_LUT`, `HW_BG_STREAM`, `HW_DIRECT`, `HW_EARLY_PRESENT`,
`HW_VERTICAL128`. **HW_UI_OBJ/HW_BG_LOWERED/HW_OAM_RAM не включены**.
Не переносить на Beta 1 ограничения этих отдельных прототипов.

- Интерфейс — обычный tiled BG0: `hardware_obj.inc`, `HW_UI_TILE_BASE=896`,
  UI VRAM `0x0600e000`, карта `0x06007800`; `hardware_direct.inc:hw_direct_map`.
  В `hw_obj_upload` записываются BG0CNT=`0x0f80`, BG0HOFS/BG0VOFS=0.
  Это не native HUD OBJ из другого прототипа.
- Пол/базовый потолок — affine BG2. `hardware_bg.inc:gba_hw_bg_vblank`
  сбрасывает DMA0CNT_H (`0x040000ba`) и DMA2CNT_H (`0x040000d2`) нулём,
  затем включает повторяющийся HBlank DMA: DMA0 передаёт матрицу/координаты
  в `0x04000020`, DMA2 — BG2CNT в `0x0400000c`.
- `renderer_probe.c`, ветка HW_EARLY_PRESENT, допускает начало upload
  при VCOUNT >=144. Это ещё видимая часть кадра: VBlank начинается с160.
  `hardware_bg.inc:hw_bg_upload` вызывает `gba_hw_bg_vblank` из main,
  **до** последующего ожидания VBlank. Имя функции не гарантирует VBlank.
  Фактический VCOUNT в момент конкретного сбоя не известен.
- Следовательно, сброс повторяющегося HBlank DMA из main не ограничен
  безопасным VBlank и потенциально может совпасть с аппаратным триггером.
  Отключение IRQ само по себе не отключает DMA/его триггеры.
- Звуковой `audio_backend.c:arm_dma` также прямо обнуляет DMA1CNT_H
  (`0x040000c6`) перед настройкой FIFO DMA (`0xf640`). Обычно это происходит
  после DMA IRQ; задержки обработки и возможные совпадения с новым запросом
  требуют отдельной проверки. `hardware_stop` сначала останавливает таймеры;
  это не тот же случай, что `arm_dma` при работающем таймере.

## Рабочая гипотеза и её границы

Главный найденный риск — **DMA lockup при остановке repeat DMA одновременно
с триггером**. Это описано Nintendo в
[AGB Programming Manual v1.1, раздел 12.4, печатные страницы122–124](https://www.manuallib.com/download/2023-10-17/AGB%20Programming%20Manual.pdf#page=122).
Для HBlank предлагается остановка в VBlank либо специальная последовательность
смены режима и выдержки; для FIFO приведена отдельная последовательность.
Краткая вторичная сводка —
[GBATEK, DMA Transfers](https://mgba-emu.github.io/gbatek/#gba-dma-transfers).

Наличие незащищённой последовательности в коде подтверждено; **попадание
в опасное временное окно именно на фотографии не доказано**. Форма полос
не определяет канал DMA или упавшую инструкцию. Совместное повреждение BG0
и BG2 требует также проверки VRAM/tilemap/регистров и выполнения CPU/IRQ;
одной остановки обновления affine-таблицы недостаточно, чтобы объяснить
перестановку элементов BG0. Переполнение/повреждение памяти и проблемы чтения
ROM пока не исключены. WAITCNT=`0x4317` в startup — стандартная настройка,
свидетельств разгона EWRAM в исследованных местах нет.

Clean Boot подтверждён пользователем. Не считать addon-патчи картриджа
основным объяснением и не выдавать повтор Clean Boot за исправление.
Предыдущие успешные проверки mGBA не доказывают отсутствия аппаратной гонки.

## Следующая проверка G21

1. Подготовить отдельную диагностическую сборку, останавливающую/перевооружающую
   HBlank DMA только внутри гарантированного VBlank; запретить early-present
   на144–159. Проверить также переходы Mode4/игра и ветку `hw_bg_disable`.
2. Отдельно проверить безопасное завершение/перенастройку FIFO DMA1 по12.4,
   либо сравнить контроль без звукового DMA. Не смешивать обе перемены
   в единственный опыт: иначе результат не локализует причину.
3. Сверить PPU, HUD, переходы и звук в эмуляторе, затем повторить сценарий
   на той же GBA/EZFlash. Записать SHA каждой тестовой ROM и исход сбоя.
4. При сохранении сбоя фиксировать CPU/IRQ heartbeat, stack guards,
   BG0CNT/HOFS/VOFS, DMA configuration и CRC карты/тайлов интерфейса.
   Регистры DMA SAD/DAD не показывают текущие внутренние счётчики передачи.

В первичном диагностическом проходе выполнены чтение кода/манифеста, проверка SHA и просмотр
эталонного PNG. Новая ROM не собиралась, runtime не менялся, тесты не запускались.
G21 остаётся в работе; физическая GBA теперь имеет отрицательный пользовательский
результат для Beta 1, а не только отсутствие проверки. Следующий ID — G21,
после него G22. NDS/SDL2 не затронуты.

## Проверочный ROM VBlankOnly, 30 октября

После запроса о следующем действии подготовлена отдельная диагностическая
сборка `hw_v128_vblank_only`. Дополнительное уточнение пользователя:
зависание происходит практически в самом начале LEVEL1.

Файл для копирования на microSD — `artifacts/gba/DoK-port_G21_VBlankOnly.gba`,
26645840 B, SHA-256
`389f5ff7991b21cea1e71eb2ff03d242a4efd2ea97a7d4609f7e91aa9f953df1`.
Рядом — `.sha256`; инструкция — `artifacts/gba/DoK-port_G21_VBlankOnly.txt`.
Исходный ELF/map/ROM и отчёты —
`build/gba/g21-vblank-only/hardware/hw_v128_vblank_only/` и его родительский
каталог. Компактная сводка — `analysis/gba/g21-vblank-only-20261030.json`.

### Изменения и границы опыта

- Диагностический вариант наследует текущие flags Beta 1, удаляет только
  `HW_EARLY_PRESENT` и добавляет `HW_VBLANK_ONLY`.
- Под `DOK_RENDER_HW_VBLANK_ONLY_PROTOTYPE` main ждёт VCOUNT160–223
  с доступными IRQ, выключает IME и повторно проверяет окно. Только затем
  публикует `hw_bg_front`, выключает/перевооружает HBlank DMA. Аналогичная
  защита стоит в `hw_bg_disable` при переходе к Mode4.
- IRQ-вход не ждёт видимую часть кадра: при запоздавшем VBlank IRQ вне этого
  окна перенастройка откладывается, счётчик `deferred` увеличивается.
- Новая диагностика `g_hw_dma_guard[8]`: magic `0x56424c31`, число rearm,
  число deferred, число disable, минимальный/максимальный VCOUNT начала,
  циклы ожидания, число завершений вне VBlank. Это GBA RAM, не лог на microSD.
- Звуковой backend и его FIFO DMA не изменены. Перенастройка видеовывода
  меняет общие тайминги, поэтому исчезновение сбоя поддержит гипотезу,
  но само по себе не докажет, какой именно DMA был первопричиной.
- Штатный вариант и `artifacts/gba/DoK-port_UI01.gba` не заменены.
  Контрольная сборка штатного варианта с изменёнными исходниками дала
  прежний SHA Beta 1 побайтно: диагностические ветви выключены по умолчанию.

### Команды воспроизведения

Общие Zig/Python/mGBA из существующей установки пользователя. Первоначальный
запуск штатного Zig objcopy был ограничен sandbox (`UnableToSpawnSelf` /
`AccessDenied`); после разрешённого запуска общей установки сборка прошла.
Отдельная копия toolchain не устанавливалась.

```powershell
py -3.14 -X utf8 ports/gba/scripts/build_gba_frontend.py --out build/gba/g21-vblank-only --variant hw_v128_vblank_only
$gbaVBlankBuild = 'build/gba/g21-vblank-only/hardware/hw_v128_vblank_only'
py -3.14 -X utf8 ports/gba/scripts/verify_gba_hardware_transitions.py --build-dir $gbaVBlankBuild --report build/gba/g21-vblank-only/transitions.json --mode4-transitions
py -3.14 -X utf8 ports/gba/scripts/benchmark_gba_hardware.py --build-dir $gbaVBlankBuild --reference-build build/gba/ui01-credits/hardware/hw_v128_entity_rect --report build/gba/g21-vblank-only/ppu.json --languages 0 1 --details
py -3.14 -X utf8 ports/gba/scripts/verify_frontend_gba.py --build-dir $gbaVBlankBuild --report build/gba/g21-vblank-only/frontend.json
py -3.14 -X utf8 ports/gba/scripts/verify_flow_gba.py --build-dir $gbaVBlankBuild --report build/gba/g21-vblank-only/flow.json
py -3.14 -X utf8 ports/gba/scripts/prototype_gba_bsp.py --base build/gba/g21-vblank-only/base --out build/gba/g21-vblank-control/hardware --variants hw_v128_entity_rect
```

### Результаты и следующий шаг

Host UI выполнен, Linux/Thumb скомпилированы. mGBA:
396 сравнений PPU RU/EN, включая HUD/оружие/сообщения, без отличий от Beta 1;
294 перехода/4968 video callbacks без смешанных кадров. Guard:
9605 перенастроек и6 отключений, VCOUNT160–208, deferred0, late ends0.
Frontend прошёл исходные экраны и два повтора музыки без underrun;
flow прошёл шесть миров, вступления/финалы, смерть/retry/Game Over,
создание нового мира и сохранение мира в паузе. EWRAM261476 B/free668;
IWRAM24428 B плюс отдельный резерв8192 B стеков/BIOS.
Это эмуляторные результаты, аппаратная устойчивость не подтверждена.
Замеры производительности в этой диагностике не являются целью опыта.
Просмотрен PNG LEVEL1. Из792 benchmark PNG оставлены три пары контрольных
кадров (`L1/L2/L3-median-ppu.png`), остальные786 повторных кадров удалены;
полные JSON с396 результатами сохранены. После побайтной проверки штатного
контроля его дубли ROM/ELF/generated banks удалены, JSON/map/log сохранены.
Входами повторной сборки служат сохранённые `g21-vblank-only/base`, assets
и исходники; каталог контрольного выхода входом не является.

На той же GBA/EZFlash запустить новый файл через Clean Boot, выбрать LEVEL1
и повторить действия из начала игры. Зафиксировать, появляется ли зависание
и съезжает ли HUD; если сбоя нет, продолжить5–10 минут. При сохранении сбоя
следующий отдельный опыт — FIFO DMA1 (контроль без звука либо безопасная
остановка по12.4), затем проверка BG0/VRAM и CPU/IRQ. Не объявлять G21
завершённой по успешному запуску в mGBA. Следующий ID — **G21**, затем G22.

## Аппаратный результат и принятие VBlank по умолчанию

30 октября пользователь после проверки предложенного VBlankOnly ROM сообщил:
«сбоя нет, играется». Это положительный пользовательский аппаратный smoke-test
на той же GBA/EZFlash Omega Definitive/Clean Boot, где Beta 1 зависала почти
в начале LEVEL1. Длительность проверки не названа;5–10 минут, другие уровни
и полное прохождение не подтверждены. Файл на microSD независимо не считан:
привязка результата к предложенному ROM основана на последовательности чата.

Результат поддерживает гипотезу гонки при остановке/перенастройке HBlank DMA.
Он не устанавливает точный канал или инструкцию: перенос вывода в VBlank
меняет общие тайминги, включая взаимодействие со звуком. Аудиокод не менялся.
Опыт без звука сейчас не нужен; вернуться к нему при повторении зависания.

В `build_gba_frontend.py` защищённый `hw_v128_vblank_only` принят как default.
Прежний `hw_v128_entity_rect` с early-present остаётся только явным выбором
для экспериментов. Обработчики/счётчики не менялись после аппаратного опыта.
Проверена обычная команда **без** `--variant`:

```powershell
py -3.14 -X utf8 ports/gba/scripts/build_gba_frontend.py --out build/gba/g21-vblank-default
```

Полученная ROM26645840 B побайтно совпала с предложенным и проверенным
пользователем VBlankOnly: SHA-256
`389f5ff7991b21cea1e71eb2ff03d242a4efd2ea97a7d4609f7e91aa9f953df1`.
Host UI выполнен, Linux/Thumb скомпилированы. Повторные эмуляторные прогоны
для этих же байтов не выполнялись: применимы сохранённые396 PPU exact,
294 transitions, frontend/music и flow из предыдущего опыта.

Текущий `artifacts/gba/DoK-port_UI01.gba` обновлён этими байтами; файл
`DoK-port_G21_VBlankOnly.gba` также оставлен. Пользователь может продолжать
игру на уже скопированном проверочном ROM. Выпущенный Beta 1, его тег,
файл `build/gba/releases/gba-beta1/Dungeons.of.Kremlin.Beta1.gba` и SHA
`cf30cf8ab1e21c35b2da1f13d3fb5cda8224b27efe32041ac9893fce5727df57`
не изменялись. Новая публикация/замена GitHub-ассета не выполнялась.

Отчёт обычной сборки — `build/gba/g21-vblank-default/frontend-build.json`;
аппаратный результат, проверка идентичности и актуальная роль baseline —
в `analysis/gba/g21-vblank-only-20261030.json`.
Повторные ROM/ELF/objects/generated banks из `g21-vblank-default` после
сравнения удалены; JSON/map/log сохранены. Полная текущая сборка остаётся
в `g21-vblank-only`; обычная команда заново создаёт repeat-выход из исходников
и `build/gba/assets`, не использует его как внешний вход.
Следующий шаг — продолжать G21 на защищённом ROM: проверять длительную игру,
переходы/паузу, другие уровни и обе локали на железе. G21 и общий бюджет
G20 остаются открыты, затем G22. NDS/SDL2 не затронуты.

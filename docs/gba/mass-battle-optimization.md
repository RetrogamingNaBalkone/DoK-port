# Массовые перестрелки GBA: PERF01/PERF02, 1 ноября 2026

Оптимизированы коллизии снарядов и вывод оружия. Результат проверен в mGBA
на исходных картах обоих языков. Новая ROM —
`artifacts/gba/DoK-port_G21_Battles.gba`; те же байты приняты как текущая
`artifacts/gba/DoK-port_UI01.gba`.

Размер 26 646 152 B, SHA-256
`be9f8b25836f556c9522e896a93bb5645c8ad855641525476998e07629508323`.
Повторная сборка в новом каталоге совпала побайтно. Исходный контроль —
VBlankOnly UI01, 26 645 840 B,
`389f5ff7991b21cea1e71eb2ff03d242a4efd2ea97a7d4609f7e91aa9f953df1`.
Опубликованная Beta 1 не заменена. Аппаратной проверки **этой** ROM нет.

## Причина

Подтверждены два независимых расхода:

1. `ports/gba/src/combat.c`, `target_cell`/`crossed_target`:
   каждый подшаг полёта заново перебирал все определения уровня, включая
   объекты того же класса, что и стрелок, и делил координаты каждого актора
   на размер клетки. Подшаги внутри уже проверенной клетки повторяли поиск.
   При залпе и последующей обработке нескольких квантов симуляции расходы
   складывались. В комнате с ружьём без стрельбы игрока контрольный максимум
   полного кадра составил 5 127 488 cycles, из них логика — до 4 012 416.
2. `ports/gba/platform/combat_probe.c`, `gba_combat_overlay`:
   масштабирование изображения оружия выполняло программное деление для
   выбора X исходного пикселя заново на каждой строке. Вывод оружия сам по
   себе дорог, а не только вспышка выстрела. В точном frozen сравнении
   LEVEL1 с ружьём, frame0/shift0, полный кадр сократился с 1 274 048
   до 700 992 cycles при одинаковом PPU-изображении. В живых перестрелках
   медиана UI-стадии снизилась примерно с 600–690 тыс. до 117–132 тыс. cycles.

Гипотеза о достижении 5000 шагов проверки видимости не подтвердилась:
в двух режимах всех комнат capped rays = 0, максимум — 37 итераций.
AI не замедлялся и не прореживался. Статическая отрисовка остаётся крупным
расходом: в варианте без оружия медиана raster достигает 613–790 тыс. cycles.
Эта работа не закрывает общий бюджет G20 или отдельные кандидаты G20D.

## Изменения

- Список ID потенциальных целей строится один раз на вызов combat poll,
  только при обработке летящего снаряда. Стрелкам класса9 нужен список
  класса1, стрелкам класса1 — класса9. Внутри класса сохранён исходный
  порядок ID; для прочих владельцев сохранён общий поиск в порядке объектов.
  Позиции, здоровье и flags читаются в момент столкновения, включая изменения
  после предыдущего попадания. Кеш не переживает poll.
- Попадание проверяется по полуоткрытым границам клетки без деления
  координат каждого актора. Подшаг внутри уже проверенной клетки не повторяет
  поиск. Начальная клетка, промежуточная клетка диагонального перехода,
  точное касание угла, порядок акторы/стена и выход за карту сохранены.
- X оружия вычисляется точной рекуррентной суммой частного и остатка один
  раз для строки выборок. Для tiled-вывода также заранее считаются X-адреса.
  Текущая строка изображения и база строки назначения вычисляются вне
  внутреннего цикла. В очищенную отдельную область staging оружия копируются
  и нулевые пиксели; прозрачность OBJ остаётся прежней. Bitmap-путь сохраняет
  прозрачную запись. Размеры, nearest-выборка и округление не изменены.

Статическая EWRAM прежняя: 261 476 B, свободно 668 B. IWRAM-код/данные
заканчиваются на `0x03005f6c`: до начала выделенного стека остаётся 148 B.
Локальные таблицы используют стек; максимальная наблюдённая глубина
2584 B, нетронутый запас 5352 B, IRQ/BIOS учитываются отдельно.
Новых постоянных RAM-кешей нет. Баланс, дальность, звук, геометрия,
длительности анимаций и VBlank DMA-протокол не менялись.

## Воспроизведение и результаты

Координаты клеток нулевые, X направлен вправо по карте, Z вниз;
центр `(x*480+240, -300, z*480+240)`. Heading — игровое значение GBA.
Данные: `research/evidence/runtime/ru/LEVEL{2,3}-runtime.json` и принятый
пакет `build/gba/assets/assets.bin`. Это адресация клеток порта,
не файловые смещения EXE и не адреса Ghidra. Нового анализа EXE не было.

| Сцена | Предмет на исходной карте | Герой, heading | FPS до → после, RU |
|---|---|---|---|
| LEVEL2, последний ключ | Z `(32,47)` | `(31,47)`, 90 | 9,31 → 14,66 |
| LEVEL3, западный ключ | Z `(23,25)` | `(23,25)`, 0 | 7,21 → 13,90 |
| LEVEL3, юго-восточный ключ | Y `(52,52)` | `(53,52)`, 0 | 9,76 → 15,75 |
| LEVEL3, северо-восточный ключ | X `(51,8)` | `(51,10)`, 0 | 8,86 → 13,08 |
| LEVEL3, ружьё и Бабы-яги | W `(17,30)` | `(20,30)`, 270 | 8,45 → 12,54 |

Покрыты все три ключа LEVEL3, без предположения о порядке их сбора.
Для каждой сцены выполнено по 600 кадров на RU/EN с непрерывным A
(ружьё, тестовый боезапас32767) и отдельно по 600 без стрельбы игрока.
Для выживания в стационарном стенде выставлены здоровье/броня32767.
Карты и враги исходные; пробуждение через штатную видимость, часы,
AI, снаряды и звуковые события работают. Это помещение героя в комнату,
а не прохождение маршрута от начала уровня. FPS — по реально предъявленным
VBlank, CPU cycles исключают ожидание публикации.

В перестрелке RU максимум полного кадра у западного ключа LEVEL3 сократился
с 6 428 288 до 2 080 768 cycles, в комнате с ружьём —
с 8 755 968 до 3 148 096. В режиме только вражеского огня последнее
значение составляет 5 127 488 → 3 119 104; средний FPS — 11,32 → 11,57.
На остальных сценах без оружия улучшение среднего FPS меньше либо отсутствует.
Это сохраняющийся расход сцены, а не доказательство устранения всех просадок.

Из-за ускорения 600 кадров охватывают разное игровое время: позиции,
число снарядов и момент гибели врагов в живых парах различаются.
Эти прогоны не считаются покадровым доказательством эквивалентности.
Для эквивалентности отдельно выполнены:

- 396 frozen actual PPU/coverage сравнений, включая 216 состояний оружия
  (12 кадров двух видов оружия ×3 положения ×3 уровня ×2 языка): отличий нет;
- независимый rational grid oracle: 330 случаев начальной/промежуточной
  клетки, стен, порядка пересечений и точных углов, задержки416/832/3328;
  контроль до оптимизации тоже проходит, полные строки результатов совпали;
- дифференциальный host-тест с исходным `combat.c` из коммита
  `4741642e77d93fab4a5f571b2264960d85be597e`: 480 сценариев,
  15 360 poll, полные состояния мира/боя и порядок событий совпали.
  Включены залпы, смешанные владельцы, перекрывающиеся/мёртвые/выбывшие
  акторы, края и выход за карту, клетки480/511, все LEVEL/RU/EN;
- G13 ARM weapons/flight/pool/occupancy, G15 ARM 28 групп врагов;
- 16 живых close-hit случаев на каждую ROM с обычным подбором оружия;
- 294 перехода, 4183 PPU callbacks: смешанных кадров нет, DMA guard160–208,
  late ends0; долг движения <416, баланс тиков точный, audio underruns0.

## Команды и доказательства

Общий Python3.14, Zig0.13 и mGBA libretro используются из пользовательской
установки, как в `docs/building.md`. Контрольную ROM нужно сохранить
**до** применения оптимизации; её ожидаемый SHA указан выше.

```powershell
py -3.14 -X utf8 ports/gba/scripts/build_gba_frontend.py --out build/gba/battle-before
# После применения оптимизации:
py -3.14 -X utf8 ports/gba/scripts/build_gba_frontend.py --out build/gba/battle-final
py -3.14 -X utf8 ports/gba/scripts/build_gba_frontend.py --out build/gba/battle-repeat
py -3.14 -X utf8 ports/gba/scripts/verify_battle_equivalence.py
```

Для `before`/`final` выполнялись обе команды (подставить каталог):

```powershell
py -3.14 -X utf8 ports/gba/scripts/benchmark_battles_gba.py --build-dir build/gba/battle-final/hardware/hw_v128_vblank_only --report build/gba/battle-final/rooms-long.json --samples 600
py -3.14 -X utf8 ports/gba/scripts/benchmark_battles_gba.py --build-dir build/gba/battle-final/hardware/hw_v128_vblank_only --report build/gba/battle-final/rooms-fire.json --samples 600 --fire
```

Полный отчёт — локальный `analysis/gba/g20-battles-20261101.json`;
компактный итог с метриками и SHA —
`analysis/summaries/g20-battles-20261101.json`. В полном отчёте сохранены
покадровые выборки и хеши отдельных проверок в `build/gba/battle-final/`.
Обязательные входы повторной сборки — прежний пакет, исходники и генераторы,
а не промежуточные ROM. Исходный контроль и итоговый ELF/map сохранены.

PERF01/PERF02 и добавленный пользователем LEVEL2-сценарий обработаны
с эмуляторной регрессией. Следующий ID — G21: BUG01/BUG02 и оставшаяся
приёмка. Эти проверки не закрывают BUG01 и не объявляют общий G20 готовым.
G20D остаётся отдельным опытом, G22 не начат. NDS/SDL2 не затронуты.

# G20/G20D: точная оптимизация потолка и masked-колонок

1 ноября 2026 года. Совместный проход по запросу пользователя: проверить
разумные способы ускорения GBA без фиксированной цели FPS. BUG02 отложен,
G22 с изменением качества в этот проход не входит.

**Выбран узкий совместный кандидат:** два точных деления span с одним
reciprocal и компактная пакетная обработка полностью открытых masked-групп.
В пяти тяжёлых видах CPU уменьшается примерно на 1,6–3%; крупного общего
резерва FPS этот проход не обнаружил. Отрицательные результаты относятся
к проверенным реализациям, а не к пределу GBA.

## Контроль и воспроизводимость

Контроль — актуальная UI01 с исправлением BUG01, 26 648 812 B, SHA-256
`a584bb1bcd9defaf636a8a9853ff1d72f376c18c82ea24912ff70c06c061f12c`.
Свежая сборка `qualification/clean-control` и повторное связывание контроля
в `qualification/hardware` совпали с ней побайтно. Историческая ROM `389f5f…`
из исходного паспорта G20D не подменяет этот контроль.

Корень доказательств — `build/gba/g20d/qualification/`; машины нового чата
должны воспроизвести команды, а не считать локальные файлы частью поставки.
Общие Zig 0.13.0, Python 3.14, mGBA libretro core
`5cac11c643d7f8dfa50c68855f2f2240ff7cc0b4cd0312dd9e17a639c85667e4`.
Штатная частота 16 777 216 cycles/s, replacement BIOS, существующий WAITCNT,
PCM 22050 Hz. Это эмуляторные измерения, не физическая GBA.

Сборка разделяет каждый вариант `prototype_defines` и сохраняет исходники,
ELF/map/ROM, build report и хеши входов. Новых данных из EXE не извлекали;
адреса — адреса ELF GBA, координаты мира и смещения пакета, не NE/DPMI.
Оригиналы не редактировались. Другие порты не менялись.

## Проверенные пути

Варианты добавлены в `prototype_gba_bsp.py`; переключатели не действуют
на прежний default `hw_v128_vblank_only`.

| Вариант | Наблюдение на тяжёлых видах | Решение |
|---|---|---|
| `g20d_zero` | Пропуск нулевых edge UV-делений, до 0,35% CPU | Точен, но небольшой выигрыш и рост hot code; отдельно не выбран |
| `g20d_pair` | Zero + общий reciprocal пары, до 1,03% CPU | Проверен; для совместного варианта оставлена пара без zero-проверок |
| `g20d_pair_only` | Только парное точное деление | Компонент выбранного пути |
| `g20d_masked_cache` | Переключение на per-pixel путь с кешем texel, тяжёлые виды на 1,16–6,34% медленнее | Отклонён; это стоимость всего варианта, не изолированного кеша |
| `g20d_masked_open` | Нет per-pixel coverage test внутри полностью открытой группы, L2 около −1,6% CPU | Полезная основа |
| `g20d_masked_zero` | Проверка общего нулевого слова перед выборкой группы, L2 около −0,6% против контроля | Точен, но хуже open: подготовка съедает экономию |
| `g20d_masked_unroll` | Open + развёртка двух выборок, L2 около −2,6…−2,7% CPU | Проверен; для совместного пути нужна более компактная форма |
| `g20d_active` | Перенос выбора активных рёбер на события, helper в ROM; L1 до +2,89% CPU | Отклонён |
| `g20d_active_hot` | Тот же helper в ARM IWRAM; L1 около −1,6%, почти исчерпана IWRAM | Не выбран как общий путь |
| `g20d_active_thumb` / `g20d_exact` | Thumb helper экономит код, но совместный вариант ухудшает L1/3640 примерно на 2,46% | Отклонён |
| `g20d_pair_open` | Пара + открытые группы, около −1,45…−2,04% CPU | Промежуточный контроль |
| `g20d_compact` | Пара + компактная развёртка и короткая формула маски, около −1,61…−3,02% CPU | Выбран для отдельной проверенной ROM |

Прямое сложение всех быстрых флагов не помещалось в IWRAM: в частности,
pair+open с zero-проверками превышал лимит на 32 B. Резерв стеков 8 KiB не
уменьшали. Компактная форма, отказ от лишних zero-проверок и формула
`(row_mask << count) - row_mask` позволили уложиться в исходный лимит.
Эта формула работает и при обнулении старшего бита на границе coverage word;
группа не пересекает восьмистрочную границу тайла.

Ошибочные промежуточные сборки и link failures не входят в измерения.
В частности, первые опыты кеша конфликтовали с регистрами счётчика batch;
полезным результатом считается только исправленный вариант с прошедшим
PPU-контролем. Контроль и выбранная ROM не используют этот кеш.

## Почему картинка сохраняется

`dok_gba_plane_divide_pair` принимает два signed int32 числителя и общий
положительный делитель 1…16384, возвращает два signed результата через
AAPCS `uint64_t` (r0/r1). Q32 reciprocal, коррекция остатка и восстановление
знака совпадают со scalar helper, включая INT_MIN, нулевой числитель и divisor1.
Игровой потолок сохраняет поклеточные UV и округление; общий world-UV не введён.

Masked-путь сохраняет источник, Q16 V/step, alpha0, tiled-адресацию, coverage
и оба счётчика written/transparent. Предварительно проверяет маску группы:
полностью закрытая пропускается старым способом, смешанная остаётся на
прежнем цикле, полностью открытая не проверяет каждый coverage bit заново.
Компактная развёртка допускает нечётный остаток и конец coverage word.
Непрозрачный цвет0 по-прежнему выводится black alias, не превращается в дыру.

Аудит восьми готовых ARM draws классифицирует фактические masked-вызовы:
в тяжёлых L2/1592 и L2/2871 встречаются классы 3/4 и 3/4/6 соответственно,
стен класса2 там нет. Прямой ошибки маршрутизации opaque стен не обнаружено.
Класс определяется по текущему face image index и исходной таблице definitions;
это ограниченная трасса, не утверждение обо всех возможных игровых состояниях.

Шесть прогревочных кадров, затем 30 предъявлений; симуляция заморожена,

| L1/3640/225 | 1 311 776 | 1 290 592 | −1,61% | 11,95 → 11,95 |

FPS считается по прошедшим VBlank, а не как частота CPU-части кадра. Вблизи
границы предъявления небольшой выигрыш CPU может дать скачок FPS; его нельзя
распространять на другие ракурсы. Несколько cycles порядка шага таймера 64
не трактуются как значимая регрессия/ускорение.

Пространственные, живые и итоговые данные входят в
`analysis/gba/gba-final-budget.json` и сводку
`analysis/summaries/g20d-optimization-20261101.json`.
Полный локальный индекс — `analysis/gba/g20d-optimization-20261101.json`.

На spatial440 отдельно для каждого языка медианная экономия полного CPU:
L1 0,34/0,38%, L2 0,67/0,65%, L3 0,33/0,29% (RU/EN). Максимальный выигрыш
на отдельном виде — 6,27%; отрицательные случаи до +0,22% CPU также сохранены.
Минимумы RU и EN одинаковы: L1 10,86→11,95, L2 9,95→9,95, L3 14,93→14,93 FPS.

## Разделение подготовки и выборки

Три отдельных `*_kernel_profile` ROM переносят orchestration в ROM ради места
для инструментирования. Включены обычные inclusive plane timers и обёртки
над настоящими ARM sampler, включая masked-вызовы из rectangle ASM.
`kernel_work` содержит ticks/calls потолка и masked, шаг — 64 cycles.

Для потолка отчёт показывает inclusive, sampler и разность: последняя включает
edge/row setup, coverage и обёртки. Время sampler тоже содержит timer/call
overhead и PCM IRQ. Эти числа объясняют распределение, но не складываются
с production CPU и не доказывают выигрыш всего кадра. Для вертикалей отдельно
показывается masked sampling, без объявления остального raster чистым setup.
Повтор готового ARM draw в `audit_raster_work.py` проверяет хеш всех
поступивших в sampler Q16 UV/spans, coverage и публичную статистику; Unicorn
не используется как модель циклов GBA.

Пример instrumented L1/3640: inclusive потолок762624→742784 cycles,
sampler368576→367424, разность394048→375360. В L1/520 соответственно
561984→547200,309440→296704 и252544→250496. Изменение sampler времени
при прежнем sampler-коде показывает влияние IRQ/расположения/таймеров:
нельзя весь delta приписывать парному divider. Production-строки выше
остаются основным доказательством выигрыша.

## Проверки и ограничения

Воспроизводимый harness проверяет раздельные A/B и совместный вариант,
spatial440 для RU и EN, два живых маршрута по 120 предъявлений на каждом
уровне/языке, actual PPU вместо пустого fast-video буфера. ARM oracle проверяет
каждый делитель paired helper, знаки/нулевые значения/INT_MIN, AAPCS и память;
сохранены sampler/rectangle, проекция и coverage vectors. В masked vectors
добавлены полностью нулевые и блочные прозрачные источники.

Общая регрессия включает frontend/latency/UI/flow/credits/audio/clock/water/
sprites/transitions, бой, 28 групп AI-combat, projectile cells, centered shots,
midrange/close hits, ceiling sides, story/automap; свежая frontend-сборка и
повторное связывание выбранной ROM обязаны совпасть. Сценарии Pause/Resume
не объявляют BUG02 исправленным. Проверка на физической GBA, original BIOS,
полное навигационное прохождение и минимум всех игровых состояний не выполнены.
Artificial all-awake overload не решён этим узким raster-проходом.

Выбранный вариант прошёл396 detail PPU +880 spatial PPU, все кадры и coverage
exact. Для A отдельно396 PPU; остальные11 вариантов — по18 PPU, всего990
парных сравнений до spatial. Восемь replay поз выбранного варианта сохраняют
все Q16 UV/spans и статистику.49152 пары делений,65536 scalar делений,
4096 surface vectors,512 masked vectors и512 rectangle vectors прошли.
Это разные проверки, их не складывают в число PPU кадров.

EWRAM261476 B (свободно668), IWRAM24572 B (свободно4 до отдельного резерва
8192 B). Main stack high-water2584 B / нетронутый запас5352 B, IRQ80 B /
нетронутый запас80 B. Новый код занял144 B IWRAM, ROM выросла на136 B;
рабочих буферов, heap и новых VRAM-областей нет. Наблюдаемые стеки подтверждают
эту выборку, не все будущие пути. Windows host suite и Linux/Thumb
cross-compilation прошли; cross-бинарники не исполнялись.

## Повторение и поставка

Из корня репозитория:

```powershell
py -3.14 -X utf8 ports/gba/scripts/check_g20d.py --stage build
py -3.14 -X utf8 ports/gba/scripts/check_g20d.py --stage measure
py -3.14 -X utf8 ports/gba/scripts/check_g20d.py --stage checks
powershell -NoProfile -ExecutionPolicy Bypass -File ports/gba/scripts/build-native.ps1 -CrossChecks
py -3.14 -X utf8 ports/gba/scripts/report_g20d.py
py -3.14 -X utf8 tools/reports/summarize_reports.py
```

`--stage all` объединяет первые три команды. Полные argv и логи находятся
в `commands-*.json`/`*.log`. Итоговый budget ссылается на текущий проход;
исходный бюджет 26 октября сохранён отдельно как история, без старого FPS gate.

После проверки входов harness удалены11 ранних пробных деревьев и30 файлов
ROM/ELF/map проигравших вариантов. Их хеши — `qualification/cleanup.json`,
исходные snapshots/flags, отчёты и логи сохранены. Оставлены актуальный контроль,
отдельные A/B, выбранный вариант, диагностические профили и чистые повторы.
Для повторения всех опытов сначала выполнять `--stage build`.

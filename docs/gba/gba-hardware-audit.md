# GBA: аппаратный резерв и альтернативы представления сцены

Новый [native world OBJ hybrid](gba-world-obj-native-trial.md): большие исходные
текстуры/masked objects, перспективные strips и residency реализованы.40 native
poses/6 Mode4 cycles passed, но все5 heavy PCM видов медленнее2775; не выбран.
Source-art probe повторён с правильным HBlank bit5:54/56 exact,2 pressure
failures явные. Чистый GPU/sector-fed output этим гибридом не опровергнут.
Предыдущий opaque64×64 audit ниже не является итогом нового пути.

Актуальный порядок после уточнения пользователя: [сначала выбор архитектуры](gba-architecture-selection.md).
Прежнее указание закончить ограниченный adaptive trial выполнено отрицательным
feedback checkpoint и заменено: не продолжать локальные правки до сравнения
крупных конвейеров. Начат самостоятельный segment-BSP scene compiler;
нативный рендер и FPS этого представления ещё не проверены.

27 октября 2026. Ответ на вопрос, не пропущены ли возможности самой GBA.
**Исчерпание аппаратных и алгоритмических возможностей не доказано.**
Измеренные неудачи BSP и отдельных шейдеров не доказывают оптимальность
нынешней архитектуры. Оценка оставшихся10–25% CPU в `gba-render-costs.md`
относилась к доработкам текущего пути, а не к верхнему пределу GBA.

## Что задействовано и что ещё не проверено

| Механизм | Нынешнее использование | Непроверенный резерв / ограничение |
|---|---|---|
| Affine BG2 и HBlank | Аппаратное текстурирование пола/базового потолка с настройками по строкам | Уже даёт основной архитектурный выигрыш; одна матрица на строку не описывает произвольные плоскости разных глубин |
| Affine BG3, Mode2 | Отдельный опыт низкого потолка на исходной высоте−561 | CPU−21/−31% в двух тяжёлых L1-видах, но обычные маршруты хуже; постоянный Mode2 не выбран |
| OBJ и affine OBJ | Масштабирование CPU слоя120×128 до240×144; native direct-source hybrid со стенами/объектами испытан | Гибрид не выбран по PCM timing; pure GPU/sector-fed output остаётся отдельной возможностью |
| HBlank OAM multiplex | В Mode2 сцена выводится четырьмя переиспользуемыми OBJ, записи меняет DMA3 | Освобождает OAM для UI; цена HBlank-трафика и лимит работы OBJ на строку остаются |
| DMA0..3 | BG-матрицы, PCM, BG control, выгрузка; DMA3 также OAM stream в опыте | DMA копирует данные, не выполняет UV/LIGHT; CPU при передаче останавливается |
| ARM/IWRAM, Thumb/ROM | Горячие ARM kernels в IWRAM, холодный код в ROM; fixed point, prelit ROM columns, exact reciprocal division | Возможна лучшая раскладка/переработка kernels; свободного IWRAM у2775 только168B до сохранённого резерва стеков8192B |
| WAITCNT/prefetch | В startup задан4317h, без EWRAM overclock | Проверка альтернативной раскладки остаётся возможной; это не незадействованное ускорение3D |
| Mode5 bitmap, page flip | Новый самостоятельный backend на нём не построен |160×128×16bpp и аппаратное растяжение полезны для software3D, но наш CPU слой уже120×128×8bpp; Mode5 лишит его нынешнего сочетания с tile affine-полом |
| Windows / OBJ window | Не проверены как новый способ отсечения сцены | Могут помогать в специальных конфигурациях; аппаратные окна маскируют слои, а не решают глубину произвольной геометрии |
| Mosaic / blending | Не выбраны как новая оптимизация sampler | Mosaic даст CPU-выигрыш лишь после сокращения числа рассчитанных отсчётов; blending имеет общие коэффициенты слоя, не заменяет произвольный LIGHT каждого пикселя |

Ограничения affine-фонов и видеорежимов: [Tonc affine BG](https://gbadev.net/tonc/affbg.html),
[bitmap modes](https://gbadev.net/tonc/bitmaps.html). Для OBJ доступны32 affine
матрицы: [Tonc affine OBJ](https://gbadev.net/tonc/affobj.html). Эффекты и маски:
[Tonc graphic effects](https://gbadev.net/tonc/gfx.html). Передачи и остановка CPU:
[Tonc DMA](https://gbadev.net/tonc/dma.html). Различие ARM/IWRAM и ROM:
[Tonc interrupts](https://gbadev.net/tonc/interrupts.html).
Выводы о применимости этих механизмов к нашим сценам — инженерная оценка,
а не утверждение источников о DoK.

Прямые OBJ для врагов/декораций могут убрать software sampling/масштабирование.
Однако нужна корректная видимость за стенами, уступами и дверями: разрезание
спрайта, маски или выбор гибридного пути. Часть непрозрачных стен постоянной
глубины также может подходить аппаратным прямоугольникам. Для наклонной стены
одного affine-преобразования недостаточно для точной перспективы: понадобятся
полосы или приближение. Возможны швы, искажение текстур и исчерпание OBJ/матриц.
Это обоснованные отдельные прототипы, но их общий выигрыш пока не измерен.

## Что означает «воксельный движок»

В GBA нет отдельного voxel/3D accelerator. Слово «воксели» описывает данные
и алгоритм, а не дополнительный аппаратный блок. Нельзя по внешнему виду игры
делать вывод о её внутреннем представлении или сравнивать только FPS.

Например, Guillaume Dubail описывал движок Stuntman как полигональный:
mapping, сортировка граней, анимация моделей; он связывал его разработку с
опытом V-Rally3. Это свидетельство разработчика, а не измерение DoK и не
доказательство архитектуры всех эффектов этих игр:
[интервью30.04.2003](https://www.p-nintendo.com/articles/interviews/guillaume-dubail-229627/p/3).

Быстрый terrain-подход Voxel Space хранит одну высоту и цвет для каждой точки
земли. Рисует вертикальные участки и использует простой буфер видимости по
колонкам; возможен LOD по расстоянию. Алгоритм и исполняемый пример:
[Sven Mäcke, VoxelSpace](https://github.com/s-macke/VoxelSpace).
Такое представление само по себе не описывает пол и нависающий потолок в одной
позицииXY. Несколько слоёв или полноценный объём возможны, но требуют другого,
более сложного обхода. Это ограничение базовой карты высот, не запрет воксельных
интерьеров вообще. Вокселизация наших стен также не гарантирует ускорения:
точный перенос их текстур/освещения может вернуть значительную часть работы.

Реальный открытый GBA voxel-прототип описывает software traversal и заливку
граней, растянутые на несколько аппаратных кадров:
[sk-io/gba-voxel-engine](https://github.com/sk-io/gba-voxel-engine).
Это пример устройства алгоритма, не оценка предельной скорости всех voxel
движков и не основание объявлять удачные коммерческие реализации невозможными.

## Практическое решение

Продолжать только мелкие оптимизации и считать отсутствие30FPS свойством
самой GBA было бы преждевременно. Нынешний гибридный путь уже использует важные
2D-возможности, но ещё не прошёл сравнение с прямым OBJ-рисованием части сцены
и более специализированным обходом видимости/группировкой поверхностей.
Прежний grid-BSP опыт не равен полноценной секторной/portal/PVS архитектуре.

Следующие обоснованные направления: закончить ограниченное сравнение выбора
Mode1/Mode2 по стоимости; затем проверить один самостоятельный путь для
дорогих вертикальных граней/объектов. Не строить полный voxel-движок без
промежуточного доказательства экономии на реальных интерьерах. Процедурные
материалы остаются отложенными по прежним отрицательным результатам.
Критерии остановки из `gba-render-costs.md` действуют: новая идея сама по себе
не оправдывает бесконечное исследование. Универсальные15+/24,1/30 ещё не доказаны.

Продолжение: grid4 выбор также не окупился, адаптивная ветка отложена.
Простейшему opaque64×64 OBJ пути не подошла ни одна грань в17 исследованных
видах: стенам96×192 требуется разбиение, прочие объекты в основном masked.
Сложный OBJ backend остаётся непроверенным. Отдельные
[96/72 quality trials](gba-row-quality-trial.md) дали10–12% /18–21% экономии CPU;
это новое сравнение на hardware backend, не прежний отрицательный low-res
опыт на полностью программном рендере.

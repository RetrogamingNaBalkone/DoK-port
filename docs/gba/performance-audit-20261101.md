# Независимый аудит быстродействия GBA, 1 ноября 2026

## Вывод и границы

Аудит текущего кода и сохранённых исследований, исходный Git HEAD
`b68b428d0f4675cc4bca00f54118dacd260d34ba`. Рабочее дерево перед аудитом чистое.
Это пересмотр гипотез, не новые измерения FPS и не реализация оптимизаций.
EXE не анализировались, оригиналы и сборки не изменялись. Ссылки на функции
относятся к исходникам GBA; cell/depth — координаты мира, не адреса NE/Ghidra.

**Доказательств, что отвергнутая готовая реализация на самом деле быстрее
из-за ошибки таймера, не найдено.** Найдены более узкие возможности, которые
не закрываются отрицательными опытами, лишняя диагностическая работа и пробелы
в методике приоритизации. Нельзя ни обещать общий прирост, ни считать перебор
G20A/G20D доказательством оптимальности.

По новому решению пользователя порт один. Отдельная Performance-сборка,
профиль поставки и её релизная приёмка исключены из очереди. Контрольные ROM
и временные A/B-кандидаты остаются инструментами проверки единственного порта.
G21/BUG02 остаётся отложенной веткой; аудит её не закрывает.

## Где код действительно делает лишнюю или спорную работу

1. `ports/gba/src/renderer_sparse_posts.inc:sparse_column` сначала вызывает
   `hw_empty_column_count`, затем `dok_gba_tiled_opaque_gaps` для runs. Значение
   `available` нужно также для раннего полностью закрытого отказа, но точный
   подсчёт используется в `available-written` для статистики прозрачности.
   Замена точного подсчёта на короткий any-open или общий проход — конкретная
   H02/H06. Удалить ранний отказ без замера тоже может быть проигрышем.
2. `renderer.c:raster` и `renderer_rect.inc` суммируют written/transparent;
   `renderer_surface_raster_body.inc` суммирует каждый sampler. По поиску
   потребителей это диагностика/tool output; `faces_drawn` зависит от записи,
   а экспериментальный feedback использует `pixels_written` как стоимость.
   Поэтому удалить все возвраты без разбора нельзя. Точность диагностических
   чисел не является самостоятельным требованием к игровому изображению.
3. В `renderer_surface_raster_body.inc` четыре ребра подготавливаются на каждый
   quad, затем вычисляются UV и LIGHT каждой строки. Поклеточная точность нужна
   для exact oracle текущей реализации, но сама по себе не доказывает игровую
   ценность каждого округления. H03 может принять малые различия отдельно от
   ошибки геометрии. BUG02 ещё раз показывает, что сохранение нынешних UV не
   равнозначно доказанной точности DOS-проекции.
4. `renderer_static_cache.inc:hw_static_begin` при совпавшей камере проверяет
   wall state и сравнивает 4096 B TMap; восстанавливает геометрию, а не пиксели.
   Это объясняет различие warm spatial и движения. Замена memcmp на revision
   возможна только при покрытии всех записей карты, reset и тестовых mutation;
   пока это мелкая подгипотеза H08, не доказанный крупный резерв.

Нельзя объявлять лишними coverage вообще, прозрачность, силуэты дверей и низкие
потолки: они определяют видимость/навигацию. Нельзя удалять image/surface leases
вместе с невидимыми пикселями: они участвуют в пробуждении AI. Прямой bitmap уже
возвращал на CPU базовые плоскости ценой 0,531–0,738 млн instrumented cycles;
убрать tiled transport без учёта этой цены — неверная постановка опыта.

## Методика приёмки следующего опыта

- База для нового сравнения — G20D `g20d_compact`, SHA-256
  `f40a13f56b70cfec5e673c7e0b80c659a48f35e30e7bad2e236ef7967a59a359`.
  Сначала воспроизвести её; UI01 с `a584…` и старую 2775 не смешивать с ней.
  Проверять effective defines: `prototype_gba_bsp.py` переопределяет
  `hw_v128_entity_rect` после создания старых вариантов; одинаковое семейство
  имён не гарантирует одинаковый контроль. Это риск нового сравнения,
  не найденная ошибка исторических парных отчётов с SHA.
- `benchmark_gba_spatial_sweep.py` делает шесть прогревов и frozen camera;
  `hw_static_begin` начинает capture лишь после нескольких стабильных кадров.
  Такие замеры нужны, но они не оценивают cold/moving setup. Добавить длинный
  маршрут с одинаковыми input timestamps и стартовым состоянием, стоячие бои
  PERF01–03, двери, вода, переходы и крайние близкие ракурсы RU/EN.
- `live_measure(...samples=120)` ограничивает предъявления. При разных FPS
  проходит разное игровое время, меняется нагрузка AI/снарядов. Сохранить его
  как smoke/load test, а причинное сравнение делать по одинаковой длительности
  симуляции и контрольным состояниям; frozen replay изолирует renderer.
- Измерять uninstrumented полный CPU и предъявление отдельно. Указывать
  медиану, p95, худшие интервалы и input latency; повторять A/B с одинаковым
  warmup/PCM/BIOS/core/WAITCNT. Не трактовать один VBlank-порог как общий процент.
  Таймерные профили не складывать с production CPU; сравнивать ROM layout.
- Exact-кандидаты: PPU, coverage, leases и игровое состояние совпадают;
  диагностические счётчики H02 проверяются отдельно и не блокируют оптимизацию
  только из-за намеренно изменённого контракта. Minor-кандидаты: карта отличий,
  серии ходьбы/поворота, нативный размер 240×160; силуэты и возможность увидеть
  цель/предмет важнее среднего pixel diff. Принятие видимого компромисса явно
  фиксировать, не выводить «незаметно» только из RGB5 или малого числа пикселей.
- Память текущего G20D: EWRAM free 668 B, IWRAM free 4 B до отдельного stack
  reserve. Сначала layout, затем новый cache/kernel. Проверка новой ROM на
  устройстве остаётся отдельной частью приёмки, старый аппаратный успех её
  не заменяет. Нет фиксированного FPS gate и обещания процентов.

## Проверки этого аудита и следующий шаг

Прочитаны план/handoff/паспорта G22, G20D, исходники raster/surface/sparse/
static cache/low choice, определения вариантов и benchmark drivers; сопоставлены
отчёты G20A/G20C/G20D, row-quality, sector/GPU и raster audit. Выполнены поиск
потребителей статистики, проверка Markdown-ссылок изменённых документов и
`git diff --check`. Новые benchmark, сборка, PPU и аппаратные тесты не запускались:
runtime не менялся. Исторические числа выше — из указанных отчётов, не независимый
повтор измерений и не новое подтверждение их физических результатов.

Следующий ID **G22**: H01, затем ограниченные H02–H05; H06–H09 по результатам
атрибуции. H10/H11 не запускать без указанного нового основания. Результат
настоящего запроса — этот обновлённый список и согласованные правила единого
порта; реализации гипотез в этот аудит не входят.

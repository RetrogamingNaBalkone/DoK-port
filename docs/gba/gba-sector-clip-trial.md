# G20A: секторный BSP, отсечение колонок и общие спаны

27 октября 2026 года. Два отдельных native-прототипа реализованы и проверены,
**оба не выбраны**. Это уже замена конвейера видимости и потолка, а не новый
builder поверх прежних клеточных четырёхугольников. Текущий ROM2775 сохранён.
Сводка с SHA всех отчётов: [g20a-sector-trial.json](../../analysis/gba/g20a-sector-trial.json),
collector: `ports/gba/scripts/report_gba_sector.py`.

Текущий goal остаётся открытым. Его граница — итоговый архитектурный handoff
с анализом оставшихся расходов; отдельная Performance-сборка в него не входит.

## Что заменено

- Offline segment BSP обходится от ближнего поддерева к дальнему. Четыре слова
  closed-X закрывают уже скрытые колонки; границы узлов охватывают CPU-геометрию.
  Статические стены и уступы больше не попадают в глобальный массив сортировки.
- Низкие потолки сохранены на высоте−561. Проверено, что BSP-листья с ними
  являются полными прямоугольниками:75/80/0 на L1/L2/L3 в каждой локализации.
  Они формируют одну общую маску потолка, которую рисует ARM span sampler
  с мировыми UV. Прежних потолочных quad на каждую клетку в этом пути нет.
- У каждой из120 колонок есть верхняя граница видимости, ближайшая стена
  и история границ потолка/уступов. Записи появляются только при увеличении
  верхнего отсечения; в QA максимум4 записи, резерв64. Нет depth/owner
  по каждому пикселю и нет предварительного sampling альфы объектов.
- Двери, предметы, актёры и прочие динамические грани рисуются отдельным
  проходом сзади вперёд, с исходными UV, crop и LIGHT. Статические границы
  отсекают колонки до окончательного masked/opaque sampler. Исходный builder
  продолжает публиковать те же признаки видимости для игровой логики.

`hw_v128_sector_clip_hot` сохраняет аппаратные базовые плоскости, tiled CPU
foreground120×128, OBJ-предъявление и native HUD. У
`hw_v128_sector_bitmap_hot` настоящий линейный framebuffer120×128/pitch128,
две Mode4 страницы, affine BG2 с PA128/PD228 и обычные OBJ только для HUD/оружия.
Scene OBJ, упаковки bitmap в тайлы и HBlank multiplexer у второго пути нет.
Пол и базовый потолок текстурирует CPU отдельными ARM world spans: те же
32×32 материалы, LIGHT0/7/15, фазы воды и глубина3600, что у аппаратных плоскостей.
Низкий потолок сохраняет исходный размер текстуры и16 LIGHT rows.

Горячие leaf/ceiling функции размещены в доступной IWRAM у обоих вариантов;
у гибрида туда также поместился bbox. Перенос ускорил первый ROM-черновик,
но не изменил решение. Остаток IWRAM204/428 байт до резерва8192 байта стека.
Это существенное ограничение специализации: generic dynamic orchestration
остаётся в ROM. Не объявляем полученные числа пределом всех Doom-подобных
рендеров или доказательством бесполезности BSP.

линейный вывод немного удешевляет foreground sampling. Экономия на OBJ/HBlank
не покрывает эту добавку. Сокращение числа потолочных областей само по себе
не устраняет цену span setup, мировых UV, выборки и записи пикселей.

## Корректность и границы доказательства

`ports/gba/scripts/verify_gba_sector.py` проверил по40 поз на вариант, RU/EN, включая
6 Pause/Mode4/Resume cycles и12 отдельных TMap/FCMap edits с возвратом в native:

- Original dynamic projected geometry и image/surface leases exact.
  При изменённой карте гибрид возвращает все исходные faces/surfaces; bitmap
  возвращает faces/leases, но закономерно добавляет legacy CPU backgrounds.
- 4800 колонок проверены прямыми лучами к исходным wall segments независимо
  от runtime BSP; roof mask — по исходным клеткам карты.6 endpoint columns
  имеют объяснённую неоднозначность до2 world units. Для roof oracle отдельно
  посчитаны10188 world-grid boundary rows,1102 соседние строки округлённого
  края крыши и4 opaque edge rows; они исключены явно. Остальные603106
  проверенных roof rows не расходятся с oracle; wall-depth exclusions0.
- 27992 пикселя общих потолочных спанов и97590 пикселей объектов проверены
  по исходным текстурам/альфе/порядку. Для объектов oracle использует контракт
  статических clip histories; независимым доказательством самих histories
  это не является. Geometry rays и roof-mask oracle независимы от них.
- Bitmap дополнительно проверен на202580 программных фоновых пикселях
  по original glyph maps и на1 536 000 пикселях фактического Mode4+OBJ PPU.
  Coverage backing, guards и стеки прошли в указанном scope.
- 18 парных PPU видов гибрида: native HUD/оружие exact. В сцене до17314 RGB
  пикселей изменены вследствие мировых UV, новой проекции/порядка и округления.
  Это не количество пропусков геометрии и не доказательство визуальной приёмки.
  Bitmap PD228 также меняет дублирование вертикальных строк относительно
 16 отдельно растянутых OBJ bands. Physical GBA/moving visual acceptance нет.

Offline compiler проверяет единый roof resource у всех inset400 definitions
каждого view, включая неиспользованные на карте, и непрозрачность stored flags
всех исходных side images. У surfaces используются флаги side image;
sprite_flags воды относятся к другому изображению и сюда не переносятся.

У раннего bitmap V2 обнаружены PCM underruns при выводе строк; его результаты
не приняты. Рабочая гипотеза — слишком короткие интервалы обслуживания IRQ
между DMA critical sections; физической трассировки задержки не было.
V3/final оставляют окно обслуживания прерываний между короткими DMA.
Приведённые unprofiled heavy/live тесты проходят с underruns0.

## Кэш картинки и следующая развилка

`ports/gba/scripts/audit_gba_image_cache.py` измерил доступность точного повторного
использования камеры на2775:9 RU маршрутов по120 кадров с PCM. Верхняя
оценка возможностей exact-camera reuse при повороте —3/1/6 кадров по мирам,
при ходьбе+повороте —4/1/2; при стоянии —120/120/120. Оценка допускает один
неполный соседний builder при чтении счётчиков. Это **не FPS готового image
cache** и не проверка reprojection. Точный кэш не является главным ответом
для движения; может остаться отдельной оптимизацией стоящей камеры.

Остановить локальную доводку этих двух секторных вариантов. Осталось отдельно
дать disposition чистому/sector-fed GPU output: прежний CPU+OBJ coverage hybrid
и нынешний CPU sector renderer не заменяют такую проверку. Image reprojection
с потерями, дальняя темнота и будущие Performance-уступки не считаются уже
реализованными. После этой оставшейся архитектурной развилки — выбор основной
ветки, ограниченная доводка и итоговый handoff с оставшимися расходами.

плейтест G21 можно выполнить с известными ограничениями скорости, выпуск
текущей сборки требует явного решения о качестве и недостигнутом бюджете.

## Контрольные результаты

1. **После G01:** настоящий `.gba`, видимый экран, ввод, кадровый счётчик,
   linker map. Это проверка платформы, а не порт игры.
2. **После G02–G05:** оригинальный уровень загружается из ROM и виден из
   восстановленной позиции героя; есть измерения RAM и времени кадра.
3. **После G06, G06A, G07 и G08:** по уровню можно ходить и поворачиваться с коллизиями.
   Для этого не ждём полной реализации AI или меню.
4. **После G09–G15:** основная игровая механика, предметы, бой и враги работают.
5. **После G16–G18:** звук, интерфейс и переходы замыкают игру.
6. **После G20–G21:** проверенная GBA-версия с измерениями и воспроизводимой сборкой.

## Архитектурные правила

- Анализировать поведение оригинала и отличия RUS/ENG раздельно. Целевой релиз —
  один ROM с выбором языка; язык не меняет геометрию или баланс. Общий стартовый
  профиль берётся из `docs/gba/gba-balance-proposal.md`; источники каждого отличия,
  новые гибридные параметры и временный выбор карт отражать в manifest.
  Оригинальные варианты нужны для сверки, но не становятся дополнительными
  режимами релиза без отдельного решения.
- Не копировать DOS-указатели, vtable и платформенные драйверы на GBA.
  Сохранять игровые правила, порядок событий, диапазоны и округления.
- Не загружать весь RES в GBA RAM и не парсить текст LEVEL во время игры
  без обоснования. Разбор и конвертация ресурсов — работа инструментов ПК;
  неизменяемые данные по возможности остаются в ROM.
- Цель производительности — 30 FPS. Fixed-point, формат текстур и внутреннее
  разрешение выбирать после проверки диапазонов и измерений. Игровое время
  не должно зависеть от фактически достигнутой частоты вывода; соответствие
  цели доказывать замерами полной игры, а не считать выполненным заранее.
- Mode 4 — кандидат для первого индексного рендера, а не принятое навсегда
  решение. Учитывать 16-битные записи в VRAM, двойную буферизацию и стоимость
  вывода; при другом режиме документировать причину.
- Native-снимки с маской известности — эталон для инструментов. Для runtime
  использовать компактные типы с понятными ссылками/индексами и бюджетом памяти.
- Один общий toolchain и эмулятор на машине, без переносимых копий в проекте.
  Не менять глобальную среду без необходимости; точные пути фиксировать.

Аппаратные ограничения проверены по
[GBATEK](https://mgba-emu.github.io/gbatek/): EWRAM 256 KiB, IWRAM 32 KiB,
VRAM 96 KiB; Mode 4 — 240×160, индексная палитра и две страницы.
Это размеры областей, не весь доступный бюджет игры: нужны стеки, код,
буферы и системные резервы. Детальный бюджет — задача G02.

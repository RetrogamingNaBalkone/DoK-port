# GBA: аудит растеризации и общих UV потолка

30 октября 2026 года, по запросу пользователя. Runtime, ROM и графика не
менялись. Добавлен воспроизводимый счётчик работы готового ARM-кода.
**В тяжёлых проверенных видах растеризация занимает 71–80% CPU кадра.
Главный резерв LEVEL1 — поклеточная подготовка и выборка низкого потолка;
в LEVEL2 дороже вертикальные грани с прозрачностью.** Одного обнаруженного
ошибочного цикла, устранение которого объяснило бы все провалы, нет.

## Образец, адреса и метод

Измерена текущая VBlankOnly UI01:
`build/gba/g21-vblank-only/hardware/hw_v128_vblank_only/dok-diagnostic.gba`,
SHA-256 `389f5ff7991b21cea1e71eb2ff03d242a4efd2ea97a7d4609f7e91aa9f953df1`.
Это тот же pin, который принят по умолчанию после аппаратного опыта.
mGBA core SHA-256:
`5cac11c643d7f8dfa50c68855f2f2240ff7cc0b4cd0312dd9e17a639c85667e4`.
Новая сборка и новый анализ EXE не выполнялись. Все адреса ниже — адреса
исполнения **GBA ELF**, не NE-сегменты или адреса оригинальных PKR/PKE.

Три независимых вида данных:

- Обычный mGBA sweep: RU, исходные карты, Y=−300, неподвижная камера,
  замороженная симуляция, PCM 22050 Hz, 6 кадров прогрева и 30 предъявлений.
  Capture hold в измеряемых интервалах выключен, audio underruns=0.
- Отдельный проход с существующими таймерами примитивов: 12 предъявлений.
  Даёт inclusive атрибуцию; его времена нельзя складывать с обычным проходом.
- `audit_raster_work.py`: mGBA готовит RAM и завершённый кадр, затем Unicorn
  повторяет `dok_renderer_draw` из неизменённого ELF/ROM. Hooks считают входы
  функций и параметры sampler. На всех 8 позах coverage и все 44 байта
  публичной статистики побайтно совпали с mGBA. Это счётчик операций,
  **не модель циклов GBA и не PPU-проверка**. Таймеры стадий при replay пропущены.

Полные локальные отчёты: `build/gba/raster-audit-20261030/{current,profile,work}.json`.
Компактный результат с хешами: `analysis/gba/raster-audit-20261030.json`.
Предварительный sweep с `--verify-output` не использован для доказательства
PPU: при fast-video его RGB-буфер пуст. Итоговый timing выполнен без этого флага.
Физическая GBA, живой бой и минимум полного прохождения здесь не измерялись.

## Фактическая стоимость

| Уровень / клетка / угол | CPU cycles, медиана | FPS предъявления | Raster / CPU |
|---|---:|---:|---:|
| L1 / 520 / 225° | 1 382 944 | 11,95 | 79,8% |
| L1 / 3640 / 225° | 1 311 776 | 11,95 | 78,5% |
| L1 / 2242 / 90° | 505 440 | 29,86 | 64,7% |
| L2 / 1592 / 135° | 1 447 296 | 9,95 | 78,1% |
| L2 / 2871 / 225° | 1 507 040 | 9,95 | 79,7% |
| L3 / 1544 / 315° | 898 912 | 14,93 | 70,7% |

Inclusive потолочное время в двух тяжёлых L1-видах — примерно 490/666 тысяч
cycles; вертикальные грани — 488/304 тысячи. В L2/2871 вертикали занимают
около 791 тысячи, потолок — 244 тысячи, уступы — 106 тысяч. Sort в этих
кадрах около 8–17 тысяч: замена сортировки не решит основной расход.
«Вертикали» включают стены и спрайты, а не только прозрачные объекты.

## UV и ограниченное число высот

U/V — координаты внутри текстуры, не дополнительные высоты. Проверенные
FCMap inset: 0, 10 и 400; базовые 0/10 уже обслуживает аппаратный фон.
CPU-потолок в штатных картах имеет одну высоту `400−961=−561` и одну
текстуру на уровень. Его LIGHT16 уже подготовлен в ROM.

`renderer_surface_raster_body.inc` всё ещё обрабатывает каждую клетку отдельно:
для четырёх рёбер рассчитывает X/U/V slopes, затем depth slope; на каждой
непустой строке выбирает рёбра, интерполирует UV и делит две разности на
ширину span. Ни число высот, ни prelit не устраняют эти вычисления.

| Вид | Вызовы потолка | Span sampler | Точные деления | Из них числитель 0 |
|---|---:|---:|---:|---:|
| L1 / 520 / 225° | 19 | 245 | 737 | 76 |
| L1 / 3640 / 225° | 47 | 314 | 1 183 | 170 |
| L1 / 520 / 90° | 9 | 129 | 321 | 147 |
| L1 / 3640 / 90° | 16 | 187 | 479 | 217 |

**Подтверждённая лишняя операция:** передача нулевого числителя в точный
divider. Из UV концов ребра следует, что вдоль каждой стороны исходной
текстуры меняется только одна из U/V. Общий цикл всё равно рассчитывает обе.
Можно исследовать специализацию рёбер, не вызывающую divider для нулевой
компоненты, и совместное использование reciprocal для двух делений одного
span. Это локальные точные кандидаты; новая реализация и выигрыш не измерены.

Для идеальной горизонтальной плоскости общая высота действительно позволяет
рассчитывать преобразование строки экрана в мировые координаты один раз за
кадр/строку. **Но существующие локальные UV не равны такой мировой формуле.**
Replay проверил фактические Q16 du/dv перед sampler:

- L1/520/225: на всех 46 строках с несколькими клетками встречаются разные
  пары du/dv.
- L1/3640/225: 53 из 54 строк содержат несколько клеток; на всех этих 53
  строках пары du/dv различаются. На одной строке различается также LIGHT.

Различия следуют из целочисленной проекции вершин, поклеточных делений,
округления и clamp. Нельзя просто взять du/dv первой клетки и применить ко
всей строке с обещанием прежних пикселей. Общая высота позволяет новый
специализированный путь, но он требует отдельного контракта округления и
парного сравнения картинки. Простое объединение клеток меняет UV.

Ранее [sector clip/span trial](gba-sector-clip-trial.md) уже заменял клеточные
quad общей маской и мировыми UV. **Весь тот конвейер** проиграл контролю
1,37–1,87× CPU; это не отдельный замер стоимости UV и не запрет на узкий опыт
специализации внутри действующей архитектуры. Повторять полную замену как
ещё не проверенную идею нельзя.

## Остальные проверки и приоритет

1. **Закрытые потолочные строки не объясняют основной провал L1.** Вызовы
   sampler действительно не предваряются полным отсечением каждого span,
   но в L1/520/225 полностью закрыт лишь 1 из 245, в L1/3640/225 — 5 из 314.
   Из 4 845/5 863 проверяемых точек закрыты только 170/330. Ещё один проход
   coverage ради этих случаев может стоить дороже сэкономленного sampling.
   Экспериментальный `HW_SURFACE_CLIP` не включён в текущий default.
2. **Много прозрачных выборок в L2 — подтверждённая стоимость.** В L2/1592
   masked sampler получает 9 749 точек: 1 007 уже закрыты, 4 991 открыты,
   но дают прозрачный ноль; только 3 751 записывают пиксель. В L2/2871:
   10 383 / 889 / 7 684 / 1 810 соответственно. Это даёт предмет для
   специализации, но [sparse-post trial](gba-sparse-posts-trial.md) уже
   проиграл полный кадр. Доля нулей сама по себе не доказывает выигрыш runs.
3. **Делители уже оптимизированы.** `planes.S:dok_gba_plane_divide` — короткий
   exact reciprocal helper; `memory.c:__aeabi_{u,i}div` также использует
   reciprocal для делителя меньше 65536. Во всех 8 replay позах вызовы
   runtime divider имели узкие делители; длинная shift/subtract ветка не
   объясняет эти тормоза. Нельзя умножать число вызовов на стоимость полного
   32-битного программного деления.
4. **Запасной runtime LIGHT готовит весь столбец до частичного coverage.**
   Это видно в конце `renderer.c:raster`, однако в проверенных masked
   колонках replay не встретил этот stack-buffer путь. Статический риск
   не выдаётся за измеренную причину текущих тяжёлых видов.
5. **Память и размещение ограничивают специализацию.** По текущему map:
   EWRAM 261 476 B (668 B свободно), IWRAM code/data 24 428 B, ещё 148 B
   до отдельного резерва стеков/BIOS 8 KiB. Потолочный sampler и его setup
   уже находятся в IWRAM (`surface_raster_hw=0x03003440`,
   `dok_gba_tiled_surface=0x03004fd4`). Rectangle setup остаётся в ROM.
   Большой новый RAM-кеш или перенос всего кода в IWRAM не являются
   бесплатными правками.

Следующий обоснованный опыт: узкая специализация **существующего** CPU-потолка
для одной высоты/известной текстуры, сначала устранение нулевых компонент и
повторной подготовки одинакового делителя, затем измерение setup отдельно
от sampling. Общие мировые UV — отдельный вариант с проверкой картинки.
Нового FPS-выигрыша аудит не заявляет; G20 остаётся открыт, G21 продолжается,
следующий плановый ID — G21, затем G22. NDS/SDL2 не затронуты.

## Воспроизведение

```powershell
$gbaRasterBuild = 'build/gba/g21-vblank-only/hardware/hw_v128_vblank_only'
$gbaRasterCases = @('1:520:225','1:3640:225','1:2242:90','2:1592:135','2:2871:225','3:1544:315')
py -3.14 -X utf8 ports/gba/scripts/benchmark_gba_spatial_sweep.py --build-dir $gbaRasterBuild --report build/gba/raster-audit-20261030/current.json --samples 30 --cases @gbaRasterCases
py -3.14 -X utf8 ports/gba/scripts/benchmark_gba_spatial_sweep.py --build-dir $gbaRasterBuild --report build/gba/raster-audit-20261030/profile.json --samples 12 --profile --cases @gbaRasterCases
py -3.14 -X utf8 ports/gba/scripts/audit_raster_work.py --build-dir $gbaRasterBuild --report build/gba/raster-audit-20261030/work.json --cases @gbaRasterCases 1:520:90 1:3640:90
```

Счётчик требует текущий 128-row/cover4/direct/prelit backend, mGBA и Unicorn
из общих пользовательских установок. Проверки coverage/statistics выполняются
внутри команды. Хеш готовой ROM проверен до и после аудита.

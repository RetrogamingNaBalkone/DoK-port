# Ресурсы первого GBA-рендера

G10 использует все16 строк LIGHT и три реальные GAMEP в общей сцене:
[актуальная спецификация](surfaces-lighting.md). Прежний банк G06A не
размножается: его row0 — identity в проверенных данных, остальные строки
накладываются во время рисования. Пакер явно проверяет эту предпосылку.
Ограничения и измерения G05 ниже описывают историческую первую сборку.

G05. Единый пакет G03 содержит общий профиль и русскую базовую геометрию
для обоих языков. Переключение RU/EN меняет текст и ресурсное представление,
сохраняя камеру и игровой мир. Первый статичный renderer не доказывает
полной эквивалентности DOS и не устанавливает достигнутые FPS сам по себе.

Проверка host/ARM завершена 25 октября 2026 года: все три кадра RU → EN → RU
совпали по 38 400 индексам, включая независимо собранный FONT8 HUD, и по
512 байтам палитры. Геометрия и ограничения реализации:
[gba-renderer-geometry.md](gba-renderer-geometry.md). Исходные данные пикселей, полный пакет,
FONT8 и визуализации остаются в ignored `build/`.

## Палитра

В пакете G03 ID назначены сортировкой имён: `GAMEP1`=19, `FONT8`=18,
`FONT16`=17, `LIGHT1/2/3`=23/24/25. Это проверено независимо по resource
directory. Для LEVEL1 global palette binding выбирает GAMEP1, 768 байт:
256 RGB-троек VGA, компоненты 0…63. Код должен разрешать binding по ID,
а не полагаться на это совпадение номеров в будущей версии пакета.

Преобразование VGA6 → GBA RGB555:

```c
uint16_t color = (r6 >> 1) | ((g6 >> 1) << 5) | ((b6 >> 1) << 10);
```

Bits 0…4 — красный, 5…9 — зелёный, 10…14 — синий; bit15=0.
В palette RAM записывается little-endian halfword. Порядок каналов исходного
ресурса RGB, переставлять R/B из-за записи слова не требуется.
Для PNG компонент переводится в RGB8 как `component * 255 / 63` с целочисленным
усечением. PNG для проверки GBA-палитры может отдельно раскрывать RGB555
через `component5 * 255 / 31`; это немного другое квантование.

В GAMEP1 индекс 0 — единственный `(0,0,0)`, индекс 7 — `(63,63,63)`.
Для первого текстового HUD это чёрный фон/контур и белые цифры без изменения
палитры игровой сцены. Исходные таблицы LIGHT остаются индексными; сначала
выполняется LUT, потом применяется преобразованная display palette.

## FONT8 и CP866

FONT8 — 2048 байт: 256 глифов × 8 строк × 1 байт, без заголовка.
В строке старший бит слева:

```text
row = font8[glyph_byte * 8 + glyph_y]
pixel_on = (row >> (7 - glyph_x)) & 1
```

`glyph_x/glyph_y` находятся в 0…7. Индекс глифа — байт CP866,
не UTF-8 code unit и не Unicode code point. Строку UTF-8 сначала кодировать
в CP866; в GBA-пакете исходные сообщения уже хранятся как CP866-байты.
FONT16 аналогично содержит 256 глифов × 16 строк, 4096 байт.
Основания: форматные проверки `tools/originals/analyze_resources.py`, исходный
Ghidra `font_draw_glyph` и каталог ресурсов G03.

Утверждённая компоновка — [gba-ui.md](gba-ui.md): поле 240×144,
сообщения y=144…159, HP/energy числами в углах поля, ключи при наличии.
FONT8 даёт 30 столбцов × 2 строки в нижней области. Исходное сообщение LEVEL
ограничено 39 байтами; оно помещается после переноса на следующую строку.
Рисование, перенос и клип должны ограничиваться 240×16 и не менять поле.
Первый статичный ROM выводит короткий заголовок «Уровень 1» / «Level 1»
одной строкой; перенос произвольных исходных сообщений этим кадром не проверен.
Счётчик keys героя — битовая маска; нулевое начальное значение LEVEL1
не следует заменять демонстрационным значком ключа.

## Независимые геометрические ориентиры

Начало общего LEVEL1: `(15120,-300,22800)`, heading90, sin32768/cos0,
D200, scale8, focal4096, исходный center159/79. Это русская базовая камера
G03; исходная английская Z23280 сюда не переносится.

G04 подтвердил две door-плоскости glyph `0x64` в исходных клетках
`(24,16)` и `(24,17)`: x11760, z22560…23040 и22080…22560,
y−640…0. При этой камере depth3360 и factor1840 дают DOS bounds
`[145,59,172,95]` и `[118,59,145,95]`. Это проверенные native render records,
а не вручную подобранный прямоугольник: [rendering-reference.md](../originals/rendering-reference.md).

Для принятой GBA-компоновки координаты исходного поля масштабируются
по X на 3/4, по Y на 9/10. Если политика — целочисленное масштабирование
готовых DOS-координат с округлением вниз, ожидаются `[108,53,129,85]`
и `[88,53,108,85]`, вместе `[88,53,129,85]`.
Пересчёт относительно нового центра119/71 может дать иной пиксель на границе;
округление должно быть указано явно и проверяться как часть договора renderer.
Quad bounds не равны bounds ненулевых пикселей прозрачной дверной текстуры.

Center plane уменьшает среднюю глубину на signed `scaledWidth >> 2`,
затем отрицательный key ограничивается нулём; для обеих дверей это
`3360−480/4=3240`. Edge planes сохраняют среднюю глубину endpoints.
Проверка использует правило G04 из [rendering-geometry.md](../originals/rendering-geometry.md)
и контролирует сортировку всех полученных плоскостей по убыванию key.

## Воспроизведение и результат

После native-сборки и получения capture файлов platform verifier:

```powershell
C:/Source/wasdify/.venv/Scripts/python.exe ports/gba/scripts/verify_renderer_host.py --arm-dir build/gba/gba-renderer
```

Скрипт независимо разбирает каталог пакета и LEVEL1 startup через oracle G03,
проверяет binding каждой фактически построенной плоскости с исходным sprite,
размер `18+width*height`, диапазоны U/V, глубины и сортировку. Native tool
дополнительно проверяет неизменность runtime, оба frame guards и отказ для
неподдержанной камеры/null workspace; checker проверяет три ошибочных CLI.

Для отдельного capacity probe тот же production-код собирается с ёмкостью1:

```powershell
$env:ZIG_GLOBAL_CACHE_DIR = 'C:/Source/DoK-port/build/zig-cache'
& "$env:LOCALAPPDATA/Programs/Zig/0.13.0/zig.exe" cc -std=c11 -Wall -Wextra -Werror -O2 -I include -DDOK_RUNTIME_ROM_ONLY -DDOK_RENDER_FACE_CAPACITY=1 ports/gba/src/runtime.c ports/gba/src/rom_assets.c ports/gba/src/image.c ports/gba/src/projection.c ports/gba/src/renderer.c ports/gba/tools/render_tool.c -o build/gba/renderer-host-check/dok-render-one-face.exe
C:/Source/wasdify/.venv/Scripts/python.exe ports/gba/scripts/verify_renderer_host.py --arm-dir build/gba/gba-renderer --capacity-tool build/gba/renderer-host-check/dok-render-one-face.exe
```

Результат — `DOK_RENDER_CAPACITY=3`, guards целы, runtime неизменён,
успешный frame/palette не записаны. Это проверка реального переполнения
ёмкости на настоящем LEVEL1, а не синтетический вызов идентичного алгоритма.

Финальный private report: `build/gba/renderer-host-check/verification.json`;
для каждого языка сохранены raw IDX, RGB6, RGB555, JSON camera/faces/stats,
FONT8 atlas и PNG в VGA6/GBA555. Просмотрены
`build/gba/renderer-host-check/ru/with-ui.png` и версия EN: видны текстурные
стены, решётка и читаемые HP100/E0/заголовки. Bottom16 не содержит сцены.

В каждой языковой сцене рассмотрено130 клеток, построено/нарисовано28
плоскостей,23 wall cells и4 center cells, выполнено3 near clips,
записано28 699 пикселей, пропущено76 прозрачных texels и15 billboards.
Все source bindings и обе дверные плоскости прошли независимую проверку.
Нативные кадры без HUD у RU/EN совпадают побайтно. ARM сравнивается с
**завершённой видимой страницей VRAM**, а не с EWRAM workspace во время
следующей отрисовки; полный HUD реконструируется отдельно из FONT8.

# Формат ресурсов RES и первый переносимый модуль

Этап 2, 23 октября 2026 года. Проверены оригинальные PKR.RES/PKE.RES,
идентифицированные по SHA-256 из `analysis/inventory-*.json`.
Основа доказательств — декомпиляция и инструкции загрузчиков обеих версий,
независимый разбор файлов и сравнение всех блоков с реализацией на C11.

## Каталог

В начале файла находится little-endian `uint16` количества записей.
Далее следуют записи по 30 байт. В обеих версиях 146 записей;
каталог заканчивается на `0x111E`, сразу за ним начинаются данные.
Все блоки в предоставленных образцах непрерывны. После последнего блока
остаётся один неиндексируемый байт RUS и четыре байта ENG; их назначение
пока не установлено. Они фиксируются в отчёте и не выдаются как ресурс.

| Смещение в записи | Размер | Значение |
|---|---:|---|
| `+0x00` | 16 | Имя, строка до NUL в однобайтной кодировке CP866 |
| `+0x10` | 4 | Размер блока, little-endian |
| `+0x14` | 4 | Абсолютное файловое смещение блока |
| `+0x18` | 2 | Runtime-флаги кеша; после чтения каталога обнуляются |
| `+0x1A` | 4 | Runtime far-pointer кеша; после чтения каталога обнуляется |

Байты после NUL в имени и последние шесть байтов записи содержат остаточные
значения. Они не являются надёжными метаданными ресурса. Копировать запись
из файла как готовую структуру с указателями нельзя.

| Назначение | RUS, адрес Ghidra | ENG, адрес Ghidra |
|---|---|---|
| Открытие каталога, чтение `count*30`, сброс кеша | `10E0:0000` | `1058:0C02` |
| Освобождение кеша | `10E0:0105` | `1058:0D0D` |
| Последовательный поиск имени | `10E0:0251` | `1058:0E6B` |
| Получение потока по файловому смещению | `10E0:03F2` | `1058:100C` |
| Загрузка и кеширование ресурса | `10E0:046B` | `1058:1085` |

Поиск сравнивает байты с учётом регистра, включая завершающий NUL;
при дубликатах выбирается первый. В новом модуле это сохранено.
Отсутствие имени в оригинале ведёт в обработчик ошибки и возврат индекса 0;
новый API явно возвращает `DOK_RES_NOT_FOUND`, чтобы ошибка не превращалась
в чтение первого ресурса. Это осознанное отличие интерфейса, а не изменение
уже перенесённой игровой логики.

## Содержимое обеих версий

| Категория | Блоков в каждой версии | Степень восстановления |
|---|---:|---|
| Изображения с 18-байтовым заголовком | 77 | Размеры и несжатые индексы пикселей |
| FONT8 / FONT16 | 2 | 256 глифов, 8 бит на строку |
| Палитры VGA | 5 | По 256 RGB-троек с компонентами 0–63 |
| Таблицы LIGHT1–LIGHT3 | 3 | По 4096 байт; полная логика выбора яркости ещё не перенесена |
| Описания LEVEL1–LEVEL3 | 3 | Секции, размеры, карты, инвентаризация определений объектов |
| Прочие тексты | 9 | Выгрузка исходных байтов и CP866 → UTF-8 |
| Блоки с сигнатурой `FD 04 53 56 4D` | 23 | Предположительно звук; декодер ещё не реализован |
| Остальные блоки | 24 | Выгружены без интерпретации; среди них анимации |

Классификация основана на именах, форме данных и проверках размеров.
Сигнатура звука сама по себе не доказывает восстановление его формата.
Полные каталоги и SHA-256: [RUS](../analysis/resources-ru.json),
[ENG](../analysis/resources-en.json).

Продолжение этапа 3: все 24 блока категории `unparsed` распознаны как
[контейнеры анимаций](animations.md). Разобраны и проверены 154 кадра каждой
версии. Таблица выше и JSON этапа 2 сохраняют историческую классификацию;
проверка анимаций записывается в отдельные `analysis/animations-*.json`.
На этапе 4 [разобраны и звуковые блоки](sound.md): 23 ресурса каждой версии,
несжатый mono PCM8, WAV-экспорт и проверенные signed-преобразования.

Изображения имеют ширину/высоту `uint16` по `+0/+2`, флаги по `+4`,
параметры разрезания по `+6/+8`, число пиксельных байтов `uint32` по `+10`
и runtime far-pointer по `+14`. Пиксели начинаются с `+18`.
Для всех 77 распознанных изображений выполняется
`payload_size == 18 + width*height`, а поле `+10 == width*height`.
RUS `10F8:02D9` после чтения заново задаёт указатель `base+18`,
сбрасывает `+8` и устанавливает `+6=1`. Поэтому указатель и параметры
из файла не следует считать готовым состоянием загруженного изображения.
Назначение `+6/+8` дополнительно подтверждено `10F8:0592` и прежним анализом
обрезки WASDify; режимы прозрачности ещё не перенесены.

В `research/evidence/resources/<ru|en>/` сохранены все исходные блоки как `0000.bin` и т. д.
Тексты дополнительно выгружены в UTF-8, изображения и атласы шрифтов — в PGM.
PGM изображения показывает **индексы как серый цвет**, а не окончательные
цвета сцены. Экспорт не применяет палитру, прозрачность или анимацию.
Имена выходных файлов берутся из индекса, чтобы имя из архива не стало путём.

## Различия версий существеннее перевода текста

У всех 146 ресурсов совпадают имена; 134 блока имеют одинаковый SHA-256.
Различаются README, шесть BINTRO/EINTRO, ENDTXT, три LEVEL и POPAL.
На этапе 3 POPAL разобран: отличаются только три пикселя последнего кадра;
подробности — в [описании анимаций](animations.md). Причина различия не установлена.

Карты также отличаются побайтово:

| Уровень | MMap | TMap | FCMap |
|---|---:|---:|---:|
| LEVEL1 | 4 клетки | 4 клетки | 12 клеток |
| LEVEL2 | 0 | 56 клеток | 0 |
| LEVEL3 | 0 | 11 клеток | 0 |

Например, символ героя `M` в MMap LEVEL1 находится в RUS `(31,16)`,
а в ENG `(31,15)`, при координатах от нуля. Это различие данных карты;
проверка его влияния в работающей игре в этом этапе не выполнялась.
Нельзя автоматически заменить обе локализации одним общим LEVEL-файлом.
Координаты и исходные байты различий записаны в
[level-map-differences.json](../analysis/level-map-differences.json).

Все шесть LEVEL-файлов задают сетку 64×64×1, сторону ячейки 480,
высоту ячейки 960. MMap/TMap/FCMap содержат по 64 строки по 64 **байта**;
пробелы значимы. Встречаются секции Game Ini, Palette, Light, Game Object.
Сейчас разобран контейнер и каркас текста; полная грамматика параметров
каждого класса и исполнение команд ещё не восстановлены.

## Реализация и проверки

`include/dok/res.h`, `src/res.c` — независимая от SDL читалка на C11.
Она не выделяет память и не разыменовывает DOS-указатели; возвращает
проверенные диапазоны в неизменяемом буфере, которым владеет вызывающий код.
`tools/res_tool.c` проверяет архив и выдаёт индекс с FNV-1a каждого блока.
FNV здесь нужен для независимого сравнения C/Python; идентичность образцов
и извлечённых файлов фиксируется SHA-256.

Синтетические тесты проверяют усечённый каталог/блок, неверное имя,
переполнение размера/смещения, попадание блока в каталог, точное сравнение
имён, порядок дубликатов и игнорирование мусора кеша. На реальных образцах
сверены имена, смещения, размеры и FNV-1a всех 292 блоков; SHA-256 каждого
выгруженного блока повторно проверен после записи.

Новые смысловые метки и семь частичных типов добавлены в оба проекта Ghidra
скриптом `AnnotateKremlin.java`. Свежие C/ASM-выдержки лежат в
`research/evidence/stage2/<language>/`. Первичный экспорт в `decompiled/` сохранён как
снимок этапа 1; его автоматически не перезаписывали этим исследованием.

# Подготовка мира и начальное состояние

Этап 6, 24 октября 2026 года. Восстановлены загрузка таблицы объектов,
преобразование карт и размещение актёров. Добавлены `include/dok/world.h`,
`src/world.c` и инструмент `dok-world`. Это начальная модель сцены с проверенными
полями состояния; исполнения событий, движения и рендеринга пока нет.

Образцы PKR/PKE и RES неизменны. SHA-256 до/после анализа, контрольные суммы
артефактов и результаты побайтовой сверки:
[stage6-verification.json](../analysis/stage6-verification.json).

## Один объект на glyph

LEVEL создаёт объект для каждого определения и сохраняет far-указатель в
таблицу на 256 glyph. Загрузчик мира копирует эту таблицу целиком из временного
буфера LEVEL в world+`0x30E`. Обход клеток не вызывает фабрику и не клонирует
объекты. Следовательно, одинаковый glyph в нескольких клетках ссылается на
**один и тот же объект**. В переносимой модели индекс объекта совпадает с
индексом определения LEVEL; таблица `glyph_index` хранит index+1.

Объекты без клеток тоже сохраняются: они могут понадобиться как шаблоны,
например, для снарядов. Для неразмещённого актёра координаты не объявляются
известными. Если glyph героя/монстра повторяется, каждый проход записывает
новую позицию в общий объект; итоговая позиция принадлежит последней клетке
в порядке runtime-обхода: строка, затем столбец. Это поведение встречается в
оригинальных данных, а не только в искусственном тесте.

Методы поиска/назначения/удаления динамического слота (`1098:017d`, `0278`,
`0205` PKR) тоже аннотированы. Поиск допускает свободный слот или объект с
битом `0x0400` в flags, сначала уничтожая старый объект; счётчик world+`0x73C`
увеличивается при выдаче слота. Динамическое создание/удаление в C ещё не
перенесено: для него нужны события и управление временем жизни ресурсов.

## Три карты и система координат

Буфер LEVEL и runtime используют разный порядок плоскостей. Сопоставление
доказано строками имён в Data51, ветвями основного парсера и копированием в
`world_initialize`:

| Секция | Смещение относительно буфера LEVEL | PKR runtime DS | PKE runtime DS | Плоскость нового world API |
|---|---:|---:|---:|---:|
| MMap | 0x0710 | 0x608A | 0x613A | 0 |
| TMap | 0x1814 | 0x718E | 0x723E | 1 |
| FCMap | 0x2918 | 0x8292 | 0x8342 | 2 |
| Посещённость | отсутствует | 0x9396 | 0x9446 | 3 |

В `dok_level` прежний порядок остаётся **TMap, MMap, FCMap**; в `dok_world`
порядок **MMap, TMap, FCMap, visited** задан enum. Исходный LEVEL не меняется.
Native-код копирует резерв по 4356 байт на плоскость, но рабочие 64×64 клетки
упакованы с шагом width. Новый API хранит только рабочие клетки.

Подготовка мира:

1. Обнулить visited.
2. Поменять местами верхние и нижние строки всех трёх карт.
3. Заменить каждый `.` на пробел и проверить наличие соответствующего объекта.
4. В TMap суммировать `+0x56` предметов класса 3, у которых `+0x54 == 99`.
5. По MMap разместить только классы 1 и 9.

Сумма предметов хранится в знаковом слове world+`0x710`; в C явно сохранено
переполнение по модулю 65536. Во всех шести оригинальных уровнях сумма нулевая;
синтетический тест проверяет ненулевую сумму с переполнением. Это поле связано
с предметами категории 99; универсальную валютную механику по одному счётчику
восстанавливать преждевременно.

Для клетки `(column, runtime_row)`:

```text
x = cell_side * column      + floor(cell_side / 2)
z = cell_side * runtime_row + floor(cell_side / 2)
y = sign_extend_16(NEG16(height_parameter))
runtime_row = length - 1 - source_row
```

Позиция в native-объекте: x+`0x26`, y+`0x2A`, z+`0x2E`. Ось y вертикальная,
высоты имеют отрицательный знак. `NEG AX` выполняется до расширения в 32 бита:
для −32768 получается −32768. Это явно воспроизведено, без зависимости от
переполнения знакового C-типа. У героя `+0x9E = y+26`, `+0xA0 = y−26`; у
монстра оба поля равны y. Эти слова тоже сужаются по модулю 65536.

Native-код копирует блок позы размером 30 байт, включая поля, которые при
старте явно не инициализирует. Новый код переносит только подтверждённые
координаты и параметры движения; неизвестные байты не объявляются нулями.

В обоих EXE начальный индекс нижней строки при отражении равен **width−1**,
а число обменов — length/2. Для прямоугольных карт это подозрительно и может
выходить за рабочую область. Новый builder принимает только квадратные карты
1…64 и height=1; он не выдаёт математически исправленное отражение за точное
поведение оригинала. Cell Side допускается 1…32767: native-переменная знаковая.

## Проверенные поля конструкторов

Новая модель хранит байты начального native-состояния и **маску известности
каждого байта**. Это временное представление для восстановления и сверки, а не
сериализованный DOS save или окончательная раскладка C++-классов движка.
`dok_world_read_u/s` читает 1/2/4 байта только при полной известности диапазона.
При ошибке результат чтения не меняется. В backing storage неизвестных байтов
лежит ноль, но он не является подтверждённым значением оригинала.

Воспроизведены:

- Общие class, glyph, flags, width/height, marker; count=0/capacity=4 владельца
  событий; бюджет анимации `+0x24=0`, начальный frame `+0x50=0`.
- Для flags&`0x0800` — первый кадр и параметры A/B в `+0x20/+0x22`, interval
  в `+0x52`. Native начинает с frame=−1 и вызывает next; валидные ресурсы дают 0.
- Для актёров 1/5/9 — mode=3, нулевые step_distance, команды, аккумуляторы,
  шаговые счётчики; ready=1, поле `+0x98=1`, предыдущий glyph=пробел.
- Для героя — layer=4, lives=3, девять null weapon slots, selected/pending=0,
  score=0 и поле `+0xDA=0`; затем параметры жизни/энергии/инвентаря из LEVEL.
- Для монстра — state `+0xA2=0`, байт `+0xE6=0`, известные части двух списков;
  затем параметры монстра из LEVEL, включая символьный `+0xE7`.
- Для переключателя и двери — подтверждённые нулевые состояния, байты двери
  `+0x54=2`, `+0x55=1`, слово `+0x60=1`, исходные flags в `+0x6A`.
- Для снаряда — первая анимационная запись в `+0x54/+0x56/+0x52`, glyph=пробел,
  состояния=0; после чтения LEVEL знак L3C меняется, y берётся из height_parameter,
  `+0x5E` выводится из `+0x5C` через signed arithmetic shift right.
- Для оружия — `+0x83=4`; для эффекта класса 12 — frame=18 и interval=0.
- Все числовые/символьные поля обработчиков классов и скопированные уведомления
  с завершающим NUL. Имена ресурсных ссылок доступны через исходное определение.

Не переносились vtable, адреса выделенной памяти, native-ссылки на изображения,
звук и анимации, указатели списков, inline-копия заголовка изображения двери,
побочные эффекты UI, регистрация в глобальном списке событий и само воспроизведение.
Нулевые weapon slots подтверждены кодом и отмечены известными; ненулевые DOS
указатели не подменяются host-адресами. Класс 9 выбирает изображение кадра 0,
но не записывает его far-указатель в переносимый снимок.

Выбор метаданных анимации использует уже проверенные `dok_res`/`dok_animation`.
Пустая/повреждённая анимация возвращает ошибку, вместо native-разыменования
или бесконечного перебора. Интервалы сохраняются как 16-битные значения;
игровая шкала времени и вызов событий ещё не реализованы.

## Результаты проверки

`analyze_worlds.py` независимо вычисляет начальное состояние Python-кодом из
оригинальных LEVEL и анимаций. С C побайтово сверяются три преобразованные карты,
visited, каждый известный байт, маска известности, сумма предметов, выбранный
герой и число размещений. Полные модели остаются в `build/worlds/`; отчёты
[worlds-ru.json](../analysis/worlds-ru.json) и
[worlds-en.json](../analysis/worlds-en.json) содержат координаты и метаданные.

| Уровень, каждая локализация | Определений | Клеток с актёрами | Уникальных размещённых актёров | Повторные glyph, CP866 hex |
|---|---:|---:|---:|---|
| LEVEL1 | 115 | 63 | 61 | AA, EA |
| LEVEL2 | 117 | 60 | 58 | 90, 91 |
| LEVEL3 | 158 | 102 | 101 | E3 |

Итого: 6 миров, 780 объектов, 450 размещений по клеткам, 440 уникальных
размещённых актёров, 69623 известных байта начального состояния. Не все
определения монстров размещены; это фиксируется отдельно, координаты им
не выдумываются.

Подтверждённая начальная позиция героя LEVEL1:

| Локализация | x | y | z | heading |
|---|---:|---:|---:|---:|
| RUS | 15120 | −300 | 22800 | 90 |
| ENG | 15120 | −300 | 23280 | 90 |

Разница z равна одной ячейке 480: следствие различающихся MMap после отражения.
Это расчёт по коду и данным, не замер запущенной DOS-игры. Ни Python/C-сверка,
ни успешная сборка не доказывают полную эквивалентность игрового поведения.

В G00 начальные xyz/heading отдельно подтверждены динамическими запусками
неизменённых RUS/ENG: [reference-runs.md](reference-runs.md). Это подтверждение
позы LEVEL1 не распространяется автоматически на все поля этапа6 или механику.

Синтетический тест проверяет неизменность входных карт, порядок плоскостей,
нормализацию точек, повторные glyph и последнее размещение, отрицательные высоты,
NEG16(−32768), сумму категории 99 с переполнением, порядок constructor/reader,
первый кадр с отрицательным интервалом, SAR отрицательного нечётного урона,
неизвестные поля, границы буферов и отсутствие ресурсов. Снимок размещённого
героя также прочитан существующим `dok_native_read_player`.

Проверены шесть Windows-тестов и кросс-компиляция `dok-world-linux` и
`world-arm7tdmi.o`. Linux/ARM-код не запускался; ARM object не является GBA ROM.
C-модуль не выделяет память, его объекты и четыре карты предоставляет caller.
Буферы входа/выхода должны быть раздельными; после ошибки частичный результат
нужно отбросить.

```powershell
./scripts/build-native.ps1 -CrossChecks
C:/Source/wasdify/.venv/Scripts/python.exe scripts/prepare_world.py
./scripts/annotate-stage6.ps1
C:/Source/wasdify/.venv/Scripts/python.exe scripts/analyze_worlds.py
./build/native/dok-world.exe originals/pkr/RUS/PKR.RES LEVEL1
```

Для повторного запуска Ghidra нужны таблицы `build/stage6/<ru|en>/requested-roles.tsv`:
их воспроизводимое создание описано скриптом `prepare_world.py`.

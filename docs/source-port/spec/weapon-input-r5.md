# Завершение уровня, смена оружия и зависание после IDKFA

5 ноября 2026 года. Прямые запросы пользователя в рамках SP22/SP09 и
последующее сообщение о повторной блокировке оружия. Основой служат
существующие SDL input/main/frontend, восстановленный Weapons и прогоны
на трёх оригинальных RES. EXE/RES не изменялись; нового анализа EXE нет.

## Интерфейс и ввод

На экране завершения уровня одна кнопка «В меню» / “Menu”. Она и Esc/B
возвращают в главное меню и завершают текущую сессию. Многостраничный текст
остаётся доступным через PgUp/PgDn и L1/R1; подсказка сообщает об этом.
В ресурсах статус выбранного файла назван «Выбран» / “Selected”.

Живые действия `weapon1`, `weapon2`, next/previous объединяются в один
запрос `Weapons::cycle` за sample. Поэтому 1, 2 и оба направления колеса
переключают на другое полученное оружие; с нулём/одним оружием ничего
не меняется. Удержание цифры не повторяет запрос. Диагностический replay
по-прежнему понимает числовой `select_weapon` как прямой выбор слота:
его формат и прежние проверочные записи не изменены.

В обоих стандартных клавомышиных пресетах колесо вверх — next, вниз — previous.
INI v1 использует значения mouse binding 6/7 для колеса, 1–5 остаются кнопками.
Загрузчик принимает 0–7. Старый stock-профиль с обоими нулевыми назначениями
next/previous получает колесо по умолчанию; custom-профиль сохраняет явные
пустые значения. Настройка «Мышь / колесо» позволяет переназначать направление,
показывает его имя, обнаруживает конфликт и сохраняет выбор.

`wheel_binding` нормализует перевёрнутое направление SDL и preciseY.
Колесо создаёт импульс на один sample; он не превращается в удержание
и не вызывает повторное событие отпускания карты. Clear/focus/выключение
мыши удаляют импульс. Меню продолжает использовать колесо независимо
от игрового выключателя мыши. Несколько импульсов до sample объединяются.

## Подтверждённый дефект скрытия

Пользователь уточнил: блокировка возникает после попытки переключения
после IDKFA. Проверены его текущие настройки без изменения файла:
обычный профиль, мышь включена, 1/2 и колесо назначены правильно.

Прежние 147 timing/pickup/fire сценариев и шесть разнесённых во времени
SDL toggle-процессов проходили, но не покрывали повторный запрос в состоянии
`WeaponState.state == 4` между скрытием старого оружия и player handoff.
Именно это окно воспроизведено новым тестом.

Старый `hide_current` возвращал уже скрытое оружие в state 0, хотя его
weapon_tick уже отменён. Player weapon_switch ждал state 4, которого больше
некому достичь: gun_state=0, gun_events=0, смена и стрельба блокируются.
IDKFA не меняет этот автомат: чит лишь сразу делает оба оружия доступными.

Исправление: `hide_current` не перезапускает скрытие при state 4. Ранее
запланированный handoff продолжает работать, актуальный pending slot
остаётся доступен его callback. Времена кадров, заряд, стоимость выстрела,
native callbacks и их очередь не меняются. Это документированное исправление
ошибки порта, а не новое утверждение об эквивалентности DOS-кода.

## Доказательства и ограничения

Unit `repeat_switch_while_hidden` сначала упал на прежнем коде с сообщением
“Repeated cycle froze weapon hide/show state machine”. После guard проходят
скрытый handoff, последующая смена и стрельба на каждом профиле; 147 прежних
timing/pickup/sustained-fire сценариев также проходят. Проверены ноль/одно оружие.

`check_weapon_handoff.py` сравнивает неизменённую опубликованную r4 и исправленный
EXE: три игры × два backend × before/after. На старом EXE сырые повторные
нажатия воспроизводят state 0 без callbacks и неизменный заряд после огня;
исправленный EXE стреляет, переключается и снова стреляет. Это подтверждение
конкретного механизма, а не запись физических таймингов пользовательского ввода.
Полные доказательства локальны в `research/evidence/source-port/`.
Неисправный EXE и его SDL2.dll сохранены отдельно как контроль в
`research/experiments/sp22-weapon-handoff-r5/`; контрольный EXE имеет SHA-256
`FD12D4987CEFBCEA8D3D96BB05E4D95840E2142A4747FDB692CE2FAA354508AC`.

Физические мышь/геймпад в автоматическом прогоне не проверялись.
Общий аудит SP22 и аппаратная A08 остаются открытыми; GBA/NDS не затронуты.

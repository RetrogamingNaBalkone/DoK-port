# Проверка базы RC2: меню ресурсов, дверь LEVEL3 и попадания

7 ноября 2026 года. Исходная ревизия `83c70a99b9f63e0baacb095cfa0378d677172788`.
Рабочее дерево перед задачей чистое. Объём: Windows SDL2; GBA/NDS не менялись.

## GAMEP1 на актуальной базе

На этой ревизии уже удалён пункт «Об игре», вызывавший GAMEP1 в RC1.
Однако **актуальная база тоже падала** при обновлении каталога ресурсов:

1. Загрузить OG и PKR (либо PKE), выбрать Kremlin и открыть предысторию.
2. Перетащить отличающийся, но допустимый RES выбранной редакции.
3. ResourceSources снимает выбор конфликтующей редакции; refresh_sets удаляет
   её из доступных наборов. Frontend::datasets выбирает оставшийся Old Gold.
4. Экран README остаётся прежним и запрашивает отсутствующий в OG GAMEP1.

В реальном процессе воспроизведено для PKR и PKE. При исчезновении единственного
набора вместо исключения наблюдался access violation `0xC0000005`.
Обратный переход — из вступления OG к оставшемуся PKR — падал с
`Missing resource: BSPR4`: номер уровня 4 сохранялся у Kremlin.
GAMEP4 был бы следующим несовместимым запросом, но **реальный первый отказ — BSPR4**.

Тест использует локальную копию RES с изменённым одним символом README/INTRO4B;
исходные файлы не меняются, SHA-256 проверяются. Это воспроизводимый конфликт
источников, не утверждение, что пользователь запускал именно две версии RES.

Исправление: если выбранная редакция отсутствует в обновлённом каталоге,
её экраны заставки/предыстории/уровня/загрузки/исхода и сообщения с возвратом
на такой экран заменяются главным меню; музыка останавливается штатной командой.
Глобальные настройки и браузер ресурсов сохраняют свой маршрут.
Проверка использует last_dataset, поскольку старые Archive уже уничтожены
в refresh_sets до вызова Frontend::datasets. Разыменование прежнего набора
недопустимо. Подстановка чужой палитры и подавление Missing resource не используются.

## Дверь первого встреченного ключа LEVEL3 (PKR/PKE)

Координаты ниже — **нулевые (столбец, строка) исходного LEVEL**, от верхнего
левого угла. Runtime Z развёрнут: `runtime_row = 63 - source_row`; сторона клетки 480.
PKR и PKE совпадают по этим декларациям и размещению.

| Объект | Исходные данные |
|---|---|
| Дверь `k` | TMap (56,9)…(56,14); key mask 8; mode +5E=0; delay +66=0 |
| Сенсор `f` | FCMap (57,12)…(62,12); target +66=`k`; bits +67=0x800 |
| Первый встреченный ключ `Y` | TMap (52,11); железный ключ, stat 10, mask 2 |

**Таймера у k нет**: сенсор вызывает обычный Use, первое срабатывание открывает,
следующее закрывает. Соседние клетки одной полосы не срабатывают повторно,
но выход с полосы и возвращение запускают Use снова. На время движения двери
повторный Use игнорируется. Все шесть клеток k принадлежат одному объекту.

**Запереться можно:** открыть k, покинуть полосу, вернуться на неё после полного
открытия, затем пройти внутрь до завершения закрытия. Закрытие ждёт освобождения
дверного проёма, но после ухода игрока в комнату завершается. Внутри нет сенсора f;
ручной Use проверяет mask 8, а железный ключ имеет mask 2. Probe проходит внутрь
через move_actor_to шагами по 120 единиц с продвижением часов на 41,6 мс между
шагами; после освобождения проёма дверь полностью закрывается. Карман не соединён
с остальной картой при закрытой k. Проверена достижимость с реальными флагами
коллизий после удаления актёров из MMap: даже после боя альтернативного пути нет.
Открытие железным ключом дверей a (31,23)/(31,24) не помогает: из кармана к ним
нет пути при закрытой k. Поведение двери/карты в этой задаче не изменяется.

Если имеется в виду **медный ключ X (51,55)**, это другая комната: вход u
(51,52)/(52,52), mask 0, AUTO=1, delay 40000. Автозакрытие задано оригиналом;
две последовательные задержки примерно по 4 секунды. Такая дверь доступна
обычному Use с обеих сторон без ключа и повторно открывается изнутри.

Данные взяты непосредственно из оригинальных RES и разобраны независимо
level_reference.py, затем проверены load_level/World. Основание семантики Use
и сенсоров: существующий Ghidra-аудит [SP10](../tasks/SP10.md), RU NE/Ghidra
1068:347E, OPEN/CLOSE/AUTO 3262/334E/3427, sensor 091E;
EN NE/Ghidra 1020:3B33, OPEN/CLOSE/AUTO 3917/3A03/3ADC, sensor 0E1C.
Это не файловые смещения. Нового анализа EXE в этой задаче не проводилось.

## Попадания на границах клеток

Последующее решение пользователя реализовано в [SP-OPTIONAL-HITS](../tasks/SP-OPTIONAL-HITS.md):
исправление доступно отдельной настройкой, по умолчанию выключенной.
Ниже сохранён результат исследования классического режима.

**Да, ограничение сохранено на актуальной базе.** Projectiles::event ищет цель
в одной клетке MMap по координатам снаряда (затем TMap), без проверки соседних
клеток по расстоянию до позы/видимого спрайта монстра. Актёр записан в MMap
по клетке своего центра. Поэтому траектория в соседней клетке может пройти
вплотную к монстру и не вызвать monster_hit.

Проверка: монстр в одной единице от границы; параллельная траектория через
ту же координату попадает, через координату в двух единицах от монстра,
по другую сторону границы — не попадает. Проверяются обе стороны границы
для PKR LEVEL3, PKE LEVEL3 и OG LEVEL4: 12 сценариев.
Это проверка текущей клеточной модели, не новый DOS-плейтест.
Связь с оригиналом — существующий [native-аудит снарядов](projectile-native-audit.md):
flight callbacks PKR 1068:26E8, PKE 1020:2D8B, OG 1AE1:22FA (Ghidra).
Исправление модели попадания требует отдельно документированной адаптации;
в данной задаче боевой код сохранён.

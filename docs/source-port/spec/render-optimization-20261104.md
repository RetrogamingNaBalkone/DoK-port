# Оптимизация software и GL — 4 ноября 2026

Участок SP20. Начальный HEAD: `147f3197e5d73949fc59b2b479f6bfb485befed4`,
рабочее дерево перед задачей чистое. Изменения относятся только к SDL2.
Оригиналы не изменялись; новых выводов об EXE нет. Адреса ниже — функции
портового C++, а не NE-сегменты или runtime-селекторы.

## Цель и метод

Пользователь уточнил цель: RK3326, **native GL 1024×768, 60 FPS**.
Software остаётся запасным режимом и тоже оптимизируется без изменения
изображения; 60 FPS в native software1024×768 не требуется. После расчётного
достижения бюджета дальнейшие оптимизации откладываются до реального устройства.

Критерий изображения — точные индексы и RGBA относительно того же backend
до изменений. Допуск равен нулю. Геометрия, дальность, FOV, время симуляции,
частота анимаций, сортировка и качество nearest/linear не упрощаются.
Стенд описан в [render-benchmark.md](render-benchmark.md).

Замеры: Windows11, Ryzen7 9700X, RTX5070, NVIDIA610.88, Release Zig0.13.0 /
Clang18.1.6, SDL2 2.32.10. Частоты и фоновая нагрузка не фиксировались.
Сравнивать распределения повторных серий, а не отдельные минимумы.

## Реализованные изменения и контракты

- `SoftwareScene::render`: текущая фаза воды и `(phase, extent)` двери
  кешируются отдельно от неизменного источника. Флаги изображения каждый кадр
  восстанавливаются как раньше: иначе сохранённый winding менял бы software.
  Все 18 фаз воды и дверные фазы проверяются старым full-набором.
- GPU использует ссылки на динамические кадры, уже имеющие bit8; прочие
  кадры сохраняют копирующий fallback. Пиксели и flags источников не меняются.
  После последнего вызова Draw ссылки больше не нужны: очередь GL содержит
  вершины и GPU ID. Неиспользуемый software framebuffer при GPU-проходах
  очищается только после software-рисования, сохраняя прежний пустой результат.
- `raster.cpp`: три специализированных цикла для horizontal, opaque vertical
  и transparent vertical. Адрес назначения наращивается с постоянным шагом;
  unsigned ADD сохраняет wrap32, signed high word эквивалентен SAR16.
  Проверка границ текстуры, LIGHT, прозрачность и порядок записей сохранены.
- `Hud::classic_mode`: координаты колонок вычисляются один раз; одинаковые
  растянутые строки панели копируются. Native мир не масштабируется.
- `GpuCamera::project`: временные точки и clipped vertices на стеке, точное
  прежнее число вершин и порядок арифметики. В `SoftwareScene` карты выбираются
  один раз за проход вместо поиска строкового ключа у каждого соседа клетки.
- GL content hash: сохранённые байты сравниваются с входом, ключ включает размер.
  По умолчанию это происходит при каждом polygon и ловит изменение содержимого
  по тому же адресу. Явный `world(palette, true, true)` разрешает проверку только
  при первом использовании буфера в данном проходе. Контракт: до окончания
  подачи полигонов буфер жив и неизменен. Игровая сцена этому соответствует;
  `flush_world` завершает контракт, следующий world всегда проверяет байты снова.
  Winding не входит в ключ пикселей. CPU snapshot cache сбрасывается при
  превышении 1024 записей в начале кадра; уничтожается вместе с GL-контекстом.
- GL проверяет невидимость по тем же float clip X/Y/W, которые отправляет GPU.
  Пропускается только полигон, все вершины которого строго снаружи одной грани.
  Первая LIGHT-таблица прохода учитывается даже для такого полигона.
- GL собирает исходные fan-треугольники в прежнем порядке, без сортировки по
  материалам. Пакет использует до семи отдельных исходных текстур и восьмой
  sampler для LIGHT. Новый пакет нужен при исчерпании слотов или смене blend /
  filtering. Размер, slot и прозрачность передаются как постоянные на полигон
  атрибуты. UV не перекладываются в атлас. Immediate API сохранён для probes.
- LIGHT/palette составлены в точную RGBA8-таблицу 256×16. Прозрачность всё ещё
  определяется исходным index0. Интерполяция цветов и alpha не изменены.
  Таблица обновляется при изменении палитры или байтов LIGHT. В shader осталось
  3 texture reads для nearest и 12 для linear вместо 5 и 20 по исходному тексту;
  это не утверждение о числе аппаратных GPU-инструкций.
- Uniform locations, вершины и staging RGBA переиспользуются. UI-текстуры
  разделены по размеру и обновляются через TexSubImage2D; более 16 размеров
  сбрасывают UI cache в начале следующего кадра. Неизменный UI не конвертируется
  и не загружается повторно (точное сравнение байтов); полностью прозрачный
  texel UI отбрасывается, depth для UI по-прежнему отключён.
- `Hud::desktop` возвращает const-ссылку до следующего вызова. Ключ учитывает
  ширину, атрибуты героя, оружие, score, сообщение и палитру. Пока идёт эффект
  здоровья или смены оружия, ключ включает время. Проверяется 80-шаговая
  последовательность против принудительного repaint с той же историей.

## Аудит лишней работы игрового цикла

Найдены и устранены расходы, **не входящие в render-бенчмарк**:

- `main` дважды сериализовал все настройки в INI на каждом кадре, чтобы сравнить
  строки. `merge_settings_edits` теперь возвращает факт изменения persistent
  значений. Подтверждение видео и изоляция CLI-настроек сохранены.
- `SdlAudio::volume/pause` получали прежние значения каждый кадр, повторяя
  блокировку аудиоустройства. Вызовы SDL выполняются только при изменении.
  Callback читает громкость под прежним SDL audio lock; управляющий кеш —
  только для главного потока, звуковые события не задерживаются.
- FPS-текст и его bitmap перестраиваются только при смене числа/набора.
  Software overlay переиспользует SDL-текстуру вместо create/destroy за кадр.
- Оружие больше не перебирает часть изображения, которая целиком за границами
  framebuffer. Начальные UV и целочисленное масштабирование прежние.

Не найдено постоянного production-хеширования World: хеш карт в main вызывается
только явной командой `state` тестового ui-script. PNG, readback, сравнение
кадров и проверка состояния в стенде расположены вне измеряемого участка.
`SDL_Delay(1)` и VSync не удалялись ради искусственного повышения счётчика FPS.

Диагностический `--profile-submission` существует **только в тестовом стенде**:
добавляет таймеры вокруг polygon/flush и выводит средние в native log.
Обычный запуск их не вызывает; `profile_submission` отмечен в native.json.
Диагностические времена не смешивать с обычными timing-сериями и не называть
GPU time: ожидания драйвера могут попадать внутрь CPU-вызовов.
Compare отвергает смешение обычного и диагностического режима.

## Измеренные результаты

Target stress: PKR/PKE LEVEL1–3, по48 сцен на набор/backend/filter, всего288.
База `target-cache-baseline`: warmup10/samples120, уже с первым кешем дверей,
воды и content hash. Итог `target-ui-cache-{1,2}`: две последовательные серии,
warmup20/samples240. Профили других процессов не запускались одновременно
с итоговыми timing-сериями. Это frozen presentation, включая залпы и impact;
они не заменяют измерение непрерывного игрового цикла и сменяющихся кадров HUD.

Медиана p50 по48 сценам, мс:

| Набор / режим, 1024×768 | После первого кеша | Итог1 | Итог2 |
|---|---:|---:|---:|
| PKR software | 1,874 | 1,087 | 1,065 |
| PKE software | 1,863 | 1,092 | 1,123 |
| PKR GL nearest | 1,192 | 0,251 | 0,245 |
| PKE GL nearest | 1,190 | 0,248 | 0,246 |
| PKR GL linear | 1,209 | 0,317 | 0,320 |
| PKE GL linear | 1,209 | 0,317 | 0,315 |

Дополнительное снижение времени относительно первой итерации: software
около40–43%, GL nearest79%, GL linear74%. Это не полный выигрыш относительно
исходного HEAD: до первого кеша GL640×480 имел медиану около2,93 мс,
software320×200 —0,267 мс; разрешения этих серий нельзя смешивать с target.

Худшие показатели GL по всем сценам, обоим наборам и обеим итоговым сериям:

| Метрика | Nearest | Linear |
|---|---:|---:|
| Максимальный p50 сцены, мс | 0,2900 | 0,3942 |
| Максимальный p95 сцены, мс | 0,5309 | 0,5932 |
| Условный FPS по p50, K30 + резерв4,67 мс | 74,8 | 60,6 |
| Условный FPS по p95, та же модель | 48,5 | 44,5 |

**Номинальный расчётный порог достигнут по худшему p50, но не по p95.**
Не объявлять это доказательством стабильных60 FPS или прохождением tail-latency
критерия. Windows jitter/драйвер и реальный GPU не откалиброваны на RK3326.
Дальнейшая проверка — устройство; пользователь разрешил остановку оптимизаций
после расчётного попадания, а аппаратная приёмка SP20 остаётся открытой.

Диагностический профиль до immutable-pass: LEVEL2 final volley около0,05 мс
на геометрию,0,20 мс в polygon,0,006 мс на отправку пакета. Повторная проверка
одних и тех же байтов внутри прохода оказалась существеннее самой отправки.
Полный лог: `build/sdl2/benchmarks/submission-profile/`, режим profile=true.
Промежуточные варианты принимались только после точного сравнения288 кадров;
например, один batching без устранения повторных byte scans не дал заметного
суммарного ускорения. Число вызовов API само по себе не заменяет замер.

## Расчётный ориентир RK3326

[Rockchip](https://www.rock-chips.com/a/en/products/RK33_Series/2018/0514/900.html)
указывает Cortex-A35 до1,5 ГГц и Mali-G31. В опубликованных Geekbench5.5.1
[RK3326](https://browser.geekbench.com/v5/cpu/24267644) имеет integer single-core70,
[Ryzen9700X](https://browser.geekbench.com/v5/cpu/23731943) —2147: отношение30,67.
Это чужие Android ARMv7/Linux x86-64 прогоны, не калибровка нашего C++/GLES.

Обсуждённая с пользователем рабочая модель:

`T_est_ms = K * T_PC_ms + 4.67`, `FPS_est = 1000 / T_est_ms`.

Центральный сценарий K=30, чувствительность K=20/40. Резерв4,67 мс — допущение
на симуляцию, звук, загрузку/вывод и запас; измеряемому рендеру остаётся12 мс.
Соответствующие ориентиры на ПК: **0,60 / 0,40 / 0,30 мс**.
Для GL это условный screening-критерий, а не физически точная модель:
его total включает glFinish, CPU/GPU перекрываются, коэффициенты драйвера/GPU
не равны CPU-коэффициенту. Малое значение gpu_wait не равно малому GPU time.

В отчёте отдельно приводить медиану сцен, максимальный p50 сцены и максимальный
p95; не выдавать среднюю лёгкую сцену за худший режим. Windows jitter не
отбрасывается молча, но его пересчёт ×30 не доказывает такие же паузы на Linux.
После расчётного попадания в бюджет следующая проверка — устройство, профиль
частот/прошивки, GLES, полный игровой кадр с симуляцией и present.

## Воспроизведение

Из корня репозитория, каждый record/compare использует новый каталог:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File ports/sdl2/tools/build.ps1 -Configuration Release
py -3.14 -B ports/sdl2/tests/test_render_benchmark.py
build/sdl2/windows/dok_gl_probe.exe
build/sdl2/windows/dok_flowing_surface_probe.exe originals/pkr/RUS/PKR.RES originals/pkr/ENG/PKE.RES
py -3.14 -B ports/sdl2/tools/check_frontend.py

py -3.14 -B ports/sdl2/tools/render_benchmark.py record --res originals/pkr/RUS/PKR.RES --res originals/pkr/ENG/PKE.RES --output build/sdl2/benchmarks/target-new --matrix target --suite stress --warmup 20 --samples 240
py -3.14 -B ports/sdl2/tools/render_benchmark.py compare research/evidence/source-port/render-benchmark/target-cache-baseline build/sdl2/benchmarks/target-new --output build/sdl2/benchmarks/target-new-comparison
```

`target-cache-baseline` уже содержит первую итерацию кешей; сравнение с ним
показывает дополнительное ускорение, а не полный прирост относительно HEAD.
Исходная база до любых оптимизаций — `baseline-v4`/`matrix-v4`; длинный stress
профиль исходного VGA/GL640 — `perf-before-1` (warmup10, samples120).
Для full использовать три RES, `--suite full --warmup 2 --samples 2`; для
старой матрицы — три RES, `--suite quick --matrix full`. Эти короткие серии
проверяют только пиксели. Изображения/полные отчёты локальные, вне Git/поставки.

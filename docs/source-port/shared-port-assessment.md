# Оценка общего Source Port для Old Gold, PKR и PKE

**Один Source Port для всех трёх вариантов технически реалистичен.**
Предпочтительная основа — общее переносимое ядро, SDL2-бэкенд и три явных
профиля: `old_gold`, `kremlin_ru`, `kremlin_en`. Доказательств достаточно,
чтобы начинать такой проект. Утверждать готовность единого движка или
эквивалентность оригиналам пока рано.

Оценка от 26 октября 2026 года основана на локальных оригиналах,
[новой декомпиляции OG](old-gold-decompilation.md), существующем исследовании
PKR/PKE и проверке всех трёх RES. Внешние описания игр для вывода не нужны.

## Что уже подтверждает общую основу

| Подсистема | Наблюдение | Вывод и уверенность |
|---|---|---|
| RES | Одинаковая структура каталога: count16 и записи 30; C-читалка прочитала все 82 блока OG | Общий reader уже пригоден; высокая |
| Изображения | Все 49 отдельных изображений OG прошли существующий C-декодер заголовка 18 и сравнение пикселей с Python | Общий декодер хранения; высокая |
| Анимации | Все 12 анимаций OG прочитаны тем же форматом 8+10×N+images; совпали интервалы/параметры/пиксели | Общий декодер кадров; высокая. Scheduler требует поведенческой сверки |
| Звук | Все 10 SVM OG прочитаны C/Python; заголовок 36 и диапазоны совпали | Общий reader; высокая. Звучание и backend policy различаются |
| Карты | OG LEVEL4 и шесть LEVEL PKR/PKE: 64×1×64, MMap/TMap/FCMap, общий словарь glyph | Общая модель мира и инструменты; высокая |
| Объекты | Фабрика OG `1ae1:0003`: классы 0…13, класс 11 отвергается; то же семейство классов у PKR/PKE | Общая система компонентов с адаптерами; высокая для структуры |
| Герой | Общие offsets здоровья/заряда/ключей/жизней/счётчика денег; та же последовательность stats и смерти | Можно разделить правила, проверяя различия; средняя/высокая |
| Враги | OG `1ae1:32ac`: wake вместо урона спящему, затем SUB health/clamp; PKR/PKE имеют ту же схему | Общая машина состояний перспективна; средняя до трасс |
| UI | CP866 FONT8/FONT16, сообщения, dirty flags, одинаковые группы показателей | Общие шрифты/текст; отдельные компоновки HUD |

Проверка охватывает **все** графические и звуковые блоки OG, а не один
пример. Для PKR/PKE ранее проверялись оба полных набора. Совпадение формата
не означает совпадение алгоритмов рисования, частоты обновления и игрового
поведения. Числа функций также не доказывают эквивалентность исходников.

## Где нужны различия профилей

| Свойство | Old Gold | PKR | PKE |
|---|---|---|---|
| Исполняемый оригинал | MZ, real mode | NE/DPMI | NE/DPMI |
| RES | 82 блока | 146 блоков | 146 блоков |
| Уровни | Один `LEVEL4` | `LEVEL1`–`LEVEL3` | `LEVEL1`–`LEVEL3` |
| Cell Side / Height | 336 / 672 | 480 / 960 | 480 / 960 |
| Сбор денег | 105 рублей, условие выхода | Нет размещённых рублей | Нет размещённых рублей |
| Оружие | Палочки; category3/+150 | Ружьё/лазер; +50 | Ружьё/лазер; +50 |
| Снаряды | Короткое описание speed/word/damage | Есть отдельные impact/miss animations | Как PKR по исследованной грамматике |
| Исходный видеовывод | VGA mode 13h, 320×200 | VESA и собственные буферы | VESA и собственные буферы |
| Исходный звук | Speaker/PIT или SB direct DAC, terminal0 | SB/DMA | SB/DMA |
| Представление | Русский текст, собственный HUD и графика | Русский набор | Английский набор; также иные параметры |

На практике это две ветви движка и три совместимых игровых профиля.
**PKE не следует сводить к переводу строк PKR.** Например, у двух бояр
LEVEL1 скорость 60→20 и дистанция активации 20000→9000, у другого здоровье 42→12;
меняются course periods и масштаб/скорость некоторых существ.
[Ранее проверенные различия](../enemy-parameters.md),
[полные таблицы](../enemy-tables.md),
[сравнение уровней](../level-version-comparison.md) задают исходные данные
для этих профилей. Общий вариант баланса можно предложить позже как
отдельный режим; для воспроизведения оригиналов нужны исходные значения.

## Предлагаемая архитектура

```text
Выбор профиля и оригинального RES
                 │
       общий контейнер и декодеры
                 │
   адаптер LEVEL: Old Gold / Kremlin
                 │
   независимая модель определений и мира
                 │
   simulation: input → события → объекты
                 │
   rasterizer + palette / HUD / audio policy
                 │
      SDL2: окно, ввод, звук, время
```

Адаптер читает авторские данные и создаёт переносимые определения.
Нельзя копировать DOS far pointers, vtable и native object layouts в память
современного процесса. Ресурсные ссылки становятся индексами или handles;
размеры, арифметика и последовательность событий задаются явно.
Модель мира должна хранить параметры геометрии, а не фиксировать 480/960.

Границы различий лучше выразить несколькими явными настройками профиля:
диалект LEVEL, схема снаряда, параметры камеры/растеризатора, HUD,
заставки/завершение, аудиопуть. Таблицы врагов, предметов и оружия нужно
брать из выбранного RES. Сходные обработчики объединять после проверки
их контрактов; отличающиеся формулы оставлять отдельными стратегиями.

Первый renderer может выдавать индексный кадр и палитру в SDL2; параметры
оригинального изображения и масштаб вывода следует разделить. Высокое
разрешение, свободная мышь, новые сохранения и микшер нескольких голосов
добавляются как явные улучшения после проверяемого базового режима.

Существующие переносимые `src/res.c`, декодеры assets/animation/sound
представляют прямую точку повторного использования. Игровые модули `src/`
нужно проверять на зависимость от конкретного баланса и ограничений памяти.
GBA-компоновка, конвертированный ROM-пакет и его ограничения не должны
становиться форматом данных настольного порта. SDL2 получает отдельную
сборочную цель и свою документацию; статус GBA остаётся независимым.

## Проверенные препятствия и оставшиеся риски

1. **LEVEL не полностью совместим.** Существующий `dok-level.exe` отвергает
   OG на строке 115 (`LEVEL error2`), первом описании снаряда. Это ожидаемое
   различие грамматики, подтверждённое OG reader `1ae1:21ea` против PKR
   `1068:2547` / PKE `1020:2bea`. Расширить reader надо через диалект;
   подстановка нулевых impact resources без проверки неверна.
2. **Сегментный ASM и computed flow.** В OG уже потребовались четыре
   jump-table overrides; остаются предупреждения, register parameters
   и рукописные циклы. Автоматический C нельзя компилировать напрямую.
3. **Арифметика, время, порядок событий.** Совпадения объектов недостаточно:
   деление, SAR, ADD16, deadlines, задержка оружия, разгон и коллизии
   требуют независимых эталонов каждого оригинала.
4. **Звук Old Gold.** Сэмплы 0…64, terminal0 и Speaker/PIT отличаются от
   обычного воспроизведения буфера PCM. Сначала сравнить DOS-записи
   Speaker и SB, затем выбрать точную или улучшенную политику SDL2.
5. **Полный game flow.** Нужны отдельные проверки смерти/возрождения,
   денег и финиша OG, трёх уровней и заставок PKR/PKE, сброса между сессиями.
   Эти сценарии не доказываются декодированием ресурсов.

## Порядок разработки и критерии

Первый полезный результат — одно host-приложение, которое выбирает один
из трёх профилей, читает его оригинальный RES и показывает начальный мир
с правильной геометрией и палитрой. Он проверит архитектуру до переноса
всех систем. Затем — движение/двери, предметы/оружие/AI, game flow и звук.
Последовательность отражена в [отдельном плане](plan.md).

Для каждой общей подсистемы нужны адресные соответствия и эталонные
примеры из OG, PKR и PKE. Сверять следует с выполнением оригинальных
x86-фрагментов или записями DOS, а не только между новой C- и Python-моделью.
Критерий общего порта: каждый профиль проходит собственные сценарии,
включая 105 рублей OG и реальные различия PKR/PKE, при единой кодовой базе.

Главная трудоёмкость — восстановление и проверка поведения. SDL2-вывод
и единая сборка относительно ограничены по объёму. Оценку в днях до
первого общего вертикального среза сейчас давать ненадёжно; следующий
этап должен измерить объём именно адаптера LEVEL и renderer.

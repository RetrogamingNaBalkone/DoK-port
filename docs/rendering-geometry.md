Проверено 24 октября 2026 года в сохранённых Ghidra-проектах обоих оригиналов.
Эта спецификация описывает доказанные формулы и начальный набор геометрии;
она не объявляет полный renderer восстановленным. Общий контекст —
[rendering.md](rendering.md), текстуры/свет — [rendering-assets.md](rendering-assets.md),
динамические снимки — [rendering-reference.md](rendering-reference.md).

## Calling convention, указатели и арифметика

Выбранные функции используют far-вызовы и возврат `RETF`; вызывающий код
удаляет аргументы (`ADD SP,...`). Характерный пролог `MOV AX,SS; NOP; INC BP;
PUSH BP; MOV BP,SP; PUSH DS; MOV DS,AX` важен: DS становится селектором SS,
а обращения к исходной позе, изображениям и render records выполняются через
`LES` и явный ES. Far-pointer занимает offset16 + selector16; возвращаемые
указатели — DX:AX. Нельзя переносить один AX как полноценный указатель.

Например, камера принимает far-pointer созданного контекста по BP+6,
далее 52-байтный пакет аргументов с BP+0x0A. В пакете проверены:
D32+0, W16+4, H16+6, viewport scale16+0x18, capacity16+0x1A,
XYZ32+0x1C/0x20/0x24, heading16+0x28, framebuffer far+0x2E.
Остальные поля пакета этим описанием не объявляются padding или нулями.

Для переноса вычислений нужны явные операции:

```text
wrap32(v) = младшие32 бита, интерпретированные как signed32
sar32(v,n) = арифметический сдвиг signed32, округление вниз
idiv32(a,b) = signed division с усечением к нулю
```

Двухоперандный `IMUL EAX,...`/`IMUL EDX,...` оставляет **только младшие32 бита**.
Последующее `SAR` не превращает его в точное 64-битное произведение. ADD/SUB
также выполняются в32 битах. `CDQ; IDIV r/m32` делит signed64 sign-extension
уже полученного signed32 числителя; это не восстановление старших битов IMUL.
Нулевой делитель и INT32_MIN/−1 вызывают исходный divide error. Host-проба
возвращает failure с неизменённым output для этих двух случаев.

## Камера, углы и фиксированная точка

Обозначим исходную позицию героя P=(Px,Py,Pz), координату вершины V=(X,Y,Z),
sin/cos из таблицы — Sθ/Cθ, viewport scale — k, параметр камеры — D,
параметр ширины экрана Q12 — K.

```text
dx = wrap32(X-Px)
dz = wrap32(Z-Pz)
lateral = sar32(wrap32(wrap32(dx*Cθ) + wrap32(dz*Sθ)),15)
depth   = sar32(wrap32(wrap32(dz*Cθ) - wrap32(dx*Sθ)),15)
N = wrap32(wrap32(sign_extend16(k)*D) * sign_extend16(K))
factor = idiv32(N,wrap32(depth+D))
sx = wrap32(sign_extend16(cx) + sar32(wrap32(lateral*factor),15))
sy = wrap32(sign_extend16(cy) + sar32(wrap32(wrap32(Y-Py)*factor),15))
```

Здесь действительно стоит **depth+D**, а не depth. Замена на обычное f/z
меняет геометрию около героя. При heading90 Sθ=32768,Cθ=0: направление
положительной глубины — **−X**, вправо на экране — **+Z**. При heading0
положительная глубина — +Z, вправо — +X. Эти утверждения относятся к render
transform; назначения кнопок и знак шага движения здесь не восстанавливаются.

Доказательства в ASM:

| Операция | RUS | ENG |
|---|---|---|
| low32 products, depth subtraction, SAR15 |10b0:01bb–01fd|1040:01c1–0203|
| lateral products, ADD32, SAR15 |10b0:0211–024b|1040:0217–0251|
| signed16 k, D32, signed16 K, low32 numerator |10b0:024f–0265|1040:0255–026b|
| billboard signed quotient |10b0:0d9b–0dbf|1040:0db9–0ddd|
| billboard x projection, low32/SAR15/centre |10b0:0dc3–0e0c|1040:0de1–0e2a|

В частности, ENG K читается по **DS:0A44**, RUS по **DS:0934**. Это не сдвиг
+B0: он применим к приведённым ниже camera globals, но не ко всем данным.

Таблицы генерируются при старте: 361 signed32 записи для углов0…360,
синус с offset0, косинус с offset0x5A4. Ghidra-сегменты — RUS1180, ENG10C0.
В статическом EXE соответствующая BSS нулевая; `trig-tables.tsv` экспортирует
именно её и явно помечает, что это не runtime sin/cos.

Генератор RUS10c8:003b–00d3 / ENG1058:003b–00d3 вычисляет угол через
`n * double(3.14159265359) / float(180.0)`, вызывает математическую библиотеку,
умножает результат на float32768.0 и преобразует в integer.
`1000:1ccd–1ce6` временно устанавливает RC=11b в x87 control word (`OR` старшего
байта на0x0C), выполняет `FISTP qword`, восстанавливает control word и возвращает
младшие32 бита в DX:AX. Это **усечение к нулю**; Ghidra `ROUND()` здесь вводит
в заблуждение. Точные722 значения двух runtime tables в каждой локализации
отдельно найдены в снимках G00 и совпали с указанной формулой: см. reference report.

## Viewport и исходный масштаб

Камера вычисляет включительные границы из signed16 W,H,k:

```text
hx = sar16(W,1); hy = sar16(H,1)
ex = sar32(wrap32(k*hx),3); ey = sar32(wrap32(k*hy),3)
L=hx-ex; R=hx+ex-1; T=hy-ey; B=hy+ey-1
cx = low16(sar32(L,1)+sar32(R,1))
cy = low16(sar32(T,1)+sar32(B,1))
```

Это не `(L+R)/2` с усечением к нулю: два SAR выполняются отдельно.
Доказательства: RUS1100:0118–01b7, ENG1060:1048–10e7.
При старте world builder явно записывает D=200 (RUS1098:3428, ENG в
соответствующем world builder перед camera initialize), копирует XYZ/heading
героя без добавления высоты глаз. Snapshot подтверждает:

| Поле | RUS и ENG LEVEL1 |
|---|---:|
| D / k / K |200 / 8 / 4096|
| Параметры W / H |320 / 161|
| Clip L,T,R,B |0,0,319,159|
| Principal point cx,cy |159,79|
| Screen framebuffer |320×200|
| Реальное игровое поле в памяти |320×160|

Начальные позиции камеры равны проверенным позициям героя:
RUS15120,−300,22800; ENG15120,−300,23280; heading90 в обоих случаях.
Дополнительного camera eye offset в этой ветке нет.

Для K=4096,k=8,D=200 величина N=6553600. В непрерывной интерпретации
эффективный focal length равен200 пикселей, а eye расположен на D позади
опорной точки вдоль forward. Дальняя симметричная оценка horizontal FOV
`2*atan(160/200)≈77.32°` — производная интерпретация формулы, не найденная
в EXE константа FOV. Асимметрия cx159 и включительных границ сохраняется
целочисленной формулой.

В VGA320×200 память пикселей и визуальное отношение сторон различны:
при показе кадра4:3 вертикальный масштаб равен1.2. Поэтому игровое поле
320×160 визуально соответствует320×192. На GBA с квадратными пикселями
сохранение этих пропорций даёт **240×144**, оставшиеся16 строк — область
сообщений по пользовательскому решению. Это решение компоновки GBA,
не изменение исходных camera globals. Подробности — [gba-ui.md](gba-ui.md).

## Вертикальные плоскости и clipping

Вход — world origin O=(x0,y0,z0), signed16 width w,height h и cardinal
orientation. Верхняя координата y0−h, нижняя y0. Для edge constructor:

| Orientation | Первый endpoint X,Z | Второй endpoint X,Z |
|---|---|---|
|0|(x0,z0)|(x0+w,z0)|
|90|(x0,z0+w)|(x0,z0)|
|180|(x0+w,z0+w)|(x0,z0+w)|
|270|(x0+w,z0)|(x0+w,z0+w)|

Для center constructor плоскость проходит через середину клетки:
0/180 имеют z=z0+sar16(w,1),90/270 имеют x=x0+sar16(w,1);
направление endpoints меняется между противоположными orientations.
Доказательства конструкций: RUS10b0:005f–019f и06aa entry до rotation;
ENG1040:0000/06b6 соответствующие ветки. Для90 точный участок
RUS10b0:00aa–00f9 задаёт x=x0+w/2, Z от z0 до z0+w.

Если **оба** endpoint depth<=0, плоскость отбрасывается. Если один depth<0,
его lateral и координата U интерполируются до depth0 signed32 low-product
с `CDQ/IDIV`; второй endpoint остаётся. Нулевой depth не вызывает деления
на ноль при D200. Один положительный и один нулевой endpoint допускаются.
После этого применяются factor=N/(depth+D) и screen-x overlap с clip.

RUS10b0:0201–020d / ENG1040:0207–0213 — reject; RUS0290–0330 и ENG0296–0336 —
две ветки near clipping. Общая вертикальная плоскость с перестановкой стороны
и texture U отличается от billboard: последний требует depth>0 и имеет
camera-facing endpoints lateral±sar16(width,1), одинаковую глубину обеих сторон.

Center-plane draw RU10b0:05b2 / ENG1040:05be меняет image flag0x20 в зависимости
от порядка projected endpoints. Это не основание объявлять весь flag0x20
универсальным зеркалированием; дальнейшее использование описано в assets spec.

## Горизонтальные плоскости

RUS10b0:1007 / ENG1040:102b строит четыре угла ячейки и две плоскости:
Y=y0 и Y=y0−height с отдельными изображениями. RUS10b0:15f4 / ENG1040:1624
строит одну плоскость Y=y0. Во всех вершинах сначала рассчитывается low32
выражение rotation; если все четыре depth<=0, объект отбрасывается.

Для отдельного отрицательного depth действует особая исходная ветка:
вместо SAR15 выполняется **SAR20 от того же неперемасштабированного low32
rotation numerator**. Это не clipping многоугольника по near plane и не
обычный depth/32 после уже выполненного округления. Затем denominator всё
равно равен depth+D. Это отличие обязательно сохранять либо явно отделять
как сознательную правку. Точный дальнейший raster clipping краёв/диагонали
этим документом полностью не перенесён.

Текстурированный объект содержит два массива четырёх вершин X/Y/Z32 и два
far image pointers; draw вызывает горизонтальный raster дважды.
Одноплоскостной вызывает его один раз. Порядок двух изображений и их роли
нужно сохранять вместе с class0 getters, а не заменять общей flat-plane моделью.

## Определения классов → исходная геометрия

Обход рассматривает карты в runtime orientation из этапа6:
MMap по DS608A/613A, TMap718E/723E, FCMap8292/8342 (RU/EN).
Из glyph извлекается общий объект через таблицу world+0x30E, index*4.
Один glyph не превращается в отдельный объект на каждую клетку.

| Слой/условие | Доказанный путь |
|---|---|
|TMap class2|до четырёх cell-edge плоскостей, закрытые соседним class2 стороны пропускаются|
|TMap class3/9/10/6|billboard после обработки поверхности|
|TMap class4/7|cell-centred плоскость orientation0 или90; ветки учитывают соседние class2/4/7|
|FCMap +0x54>=0 при не-class2 TMap|две текстурированные горизонтальные плоскости|
|FCMap +0x54<0 при не-class2 TMap|одна горизонтальная плоскость|
|MMap class9 и class3|дополнительные billboard paths|
|Отдельные слоты flags&0x1000|отдельный обход объектов и billboard path|

Номера классов проверяются внутри RU1098:30c1 / ENG1030:3571; примеры
center-plane calls RU49e7/4a77/4e5d/4eed, ENG5405/5508/5938/5a3b.
Конкретные двери/G00 дополнительно подтверждены сохранёнными native records,
а не только видом картинки: [rendering-reference.md](rendering-reference.md).

Размеры TMap изображения читаются через object+0x44: width word+0,
height word+2, scale — signed word object+0x17. **Умножение16-битное**:
RUS1098:3583–35ac / ENG1030:3b29–3b57. Сохраняется lowAX; высота затем
sign-extends через CWDE. Таким образом, это не безусловный Cell Side/Height.
Для обычной стены96×192 при scale5 получается480×960; для двери96×128 —480×640.
Текущий image pointer выбирается virtual slot+8 (может обновить анимацию),
flags берутся из object+0x15. Нельзя всегда брать исходный Sprite resource,
если объект анимирован или crop изменил текущий image.

Base Y берётся из signed height_parameter текущего FCMap объекта (+0x19):
`y0=sign_extend16(NEG16(height_parameter))`, включая wrap для−32768.
Пример RUS1098:35ce–360d. Для двух horizontal planes signed16 extent считается
как `Cell Height+1−FCMap[+0x54]−FCMap[+0x19]` с16-битными INC/SUB
(RUS3612–3626), footprint side — Cell Side. Для blank FCMap LEVEL1:
0x54=10,height_parameter0,Cell Height960 → extent951; floorY0,ceilingY−951.
Значение400 для `+` меняет эту геометрию; объявлять его уроном по имени glyph нельзя.

Статические wall edge planes дополнительно учитывают FCMap соседа:
heightArg = low16(TMapImageHeightScaled−neighborFCMap[+0x54]+1).
Texture V стартует от signed division
`imageHeight*neighborFCMap[+0x54]/Cell Height`, с последующим16-битным сужением.
Пример RUS1098:3d28–3d7e / ENG1030:444c–44c9. Отдельные FCMap-соседи с
различающимся+0x54 порождают дополнительные вертикальные границы.
Это объясняет, почему G05 не должен автоматически превращать любой непустой
TMap glyph в одинаковый куб и почему значение+0x54 должно оставаться доступным.

Полная булева комбинация соседей для class4/7, dynamic opening/crop и все
варианты FCMap ступеней ещё не объявляются реализованным переносом.
Доказанные типы плоскостей и формулы достаточны для отдельного статического
G05 subset, ограничения которого необходимо показать явно.

## Порядок и видимость

Создание геометрии сканирует ограничивающий прямоугольник клеток по Z,
внутри по X. Границы получаются из четырёх точек вокруг опорной позиции:
сдвиг2*Cell Side по sin/−cos, ближняя ширина±1*Cell Side, дальние коэффициенты
9*Cell Side и±6*Cell Side; затем AABB clamp в границы карты.
Это ограничение перебора клеток, не найденная константа FOV или дальняя
плоскость обычного raycaster. Конкретные переполнения этого builder вычисляются
в смешанной16/32-битной арифметике; независимый перенос всей AABB ветки пока pending.

Каждый render record содержит byte flags+6 и signed32 sort key+7.
Center plane и billboard уменьшают глубину на width>>2; edge plane и
horizontal quads используют среднее определённых depth endpoints, после чего
отрицательный key ограничивается нулём. Это не единый евклидов distance sort.

RU1100:0000 / ENG1060:0f30 выполняет gap-sort по key **по убыванию**:
большая глубина стоит раньше. Затем culling идёт с конца, от ближних к дальним,
с таблицей открытых колонок (word1/0), clip X clamp в0…1299.
Flags bit1 — eligibility/visible; bit2 позволяет закрывать колонки.
Полностью закрытые объекты очищают bit1 и key. Это coarse column occlusion,
не полноценный z-buffer и не гарантированная попиксельная видимость.

Draw list идёт вперёд (далёкое → ближнее), проверяет bit1 и вызывает virtual
slot+8 каждого render record: RU1100:0551–05a4 / ENG1060:14af body.
Стены/billboards вызывают vertical raster; horizontal records — horizontal.
Для shared images изменение flags0x20 перед draw является наблюдаемым эффектом.

## Диапазоны и границы доказанного переноса

Все исходные карты64×64, Cell Side480, Cell Height960. Центры клеток
лежат в240…30480 по X/Z. При стандартных параметрах N=6553600,
для depth>=0 factor находится в0…32768. Однако произвольные32-битные inputs
или отрицательная horizontal ветка могут переполнять low32 IMUL: замена всех
операций на64-битные без промежуточного wrap не является точным восстановлением.

Host probe корневого агента проверяет scalar projection **до сужения координат
вершин в raster code**, со сравнением C/Python на граничных и случайных inputs.
Это не проверка visibility, pixel rasterization, texture interpolation и
всех class branches. Статические functions вызывают virtual methods и работают
с указателями в ES/GS/FS; Ghidra C часто теряет эти сегменты.

Остаются явно открытыми: полный перенос neighbour logic class4/7; повторение
всех FCMap step faces/UV seams; clipping и16-битные сужения в rasterizer;
поведение пересекающихся прозрачных объектов с coarse occlusion; runtime
анимационные изменения image flags/crop; произвольные разрешения и viewport
scales; точное поведение исходных исключений при capacity/allocation failure.

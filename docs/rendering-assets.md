## Дисковый layout и runtime-поля

Изображение имеет 18-байтовый little-endian заголовок: width `u16 +0`,
height `u16 +2`, flags `u16 +4`, crop divisor/index `u16 +6/+8`,
pixel_bytes `u32 +10`, сериализованный far-pointer `+14`. Дальше идут
`width * height` однобайтных индексов, без сжатия и выравнивания строк.
Источник формата — [resources.md](resources.md), [animations.md](animations.md)
и чтение `src/image.c`/`src/animation.c`; это описание индексных пикселей,
а не заранее готового RGB/GBA framebuffer.

`10F8:02D9`/`1060:034D` назначают указатель заново как `image_base+18`,
а `+6/+8` устанавливают в `1/0`. Сериализованные указатели не являются
адресами хоста. Загрузчик анимаций принудительно задаёт каждому кадру
runtime flags=8; `stored_flags` нового C-декодера сохраняет поле файла.
Эти значения нужно различать.

Строковое хранение подтверждает подготовка обоих ASM-span:
адрес исходного текселя строится как `base + v_integer * width + u_integer`.
В обеих версиях горизонтальная подготовка `1010:0030…004C` умножает
`DS:[C1E6]` на `DS:[C14A]`, добавляет `DS:[C1E2]` и базу `DS:[C14C]`.
Эти четыре смещения приведены для RUS; в ENG они равны `C296`, `C1FA`,
`C292`, `C1FC` соответственно.
Вертикальная подготовка `1010:00E1…0105` получает соответствующие целые
части через арифметический сдвиг на 16. Следовательно, байт `(u,v)` имеет
смещение `v*width+u` в pixel payload. Это не column-major и не Morton-layout.

Все 77 отдельных изображений и 154 кадра каждой версии имеют **stored flags=0**.
Режим изображения определяется последующими runtime-записями: анимации
получают flags=8 (`1050:032D` / `1018:1273`), статические Sprite проходят
конфигуратор флагов. `Sprite=NAME flags` и flags определения игрового объекта
— разные поля LEVEL; смешивать их нельзя. Конфигуратор выполняет **OR**
(`10F8:05B7` / `1060:06C7`), а не замену. Общий кеш изображения допускает
накопление битов при нескольких обращениях к одному ресурсу.

## Обрезка и флаги

`10F8:0592` / `1060:06A2` меняют нулевой divisor на 1 и ограничивают index
сверху значением divisor через signed `JLE`; нижнего ограничения на index
в этой функции нет. Для положительных размеров и `0 <= index <= divisor`
смещение по X равно `trunc(width / divisor) * index`, по Y —
`trunc(height / divisor) * index`. Сначала выполняется деление, затем
умножение: `(width * index) / divisor` даёт другой результат при остатке.

`image_crop_transform` проверяет следующие пары **по порядку таблицы**.
При нескольких парах выполняется только первая с установленным битом.

| Биты flags | Операция в исходной сетке | Заполнение освободившейся области |
|---|---|---|
| `0x0040` / `0x0400` | Сдвиг вправо на X | Первый бит — нули; второй — хвост той же строки, циклически |
| `0x0080` / `0x0800` | Сдвиг влево на X | Нули / начало той же строки, циклически |
| `0x0100` / `0x1000` | Сдвиг вниз на Y строк | Нули / последние строки, циклически |
| `0x0200` / `0x2000` | Сдвиг вверх на Y строк | Нули / первые строки, циклически |

Если в паре установлены оба бита, побеждает циклическое заполнение.
RUS тесты пар: `10F8:05DB/05E2`, `06D3/06DA`, `07D1/07D8`, `087B/0882`;
ENG: `1060:06EB/06F2`, `07E3/07EA`, `08E1/08E8`, `098B/0992`.
Обычный путь без преобразований возвращает исходный far-pointer пикселей
(`10F8:09D2` / `1060:0AE2`). Остальные пути возвращают scratch:
Ghidra `1188:0300` / `10C8:0300`, данные NE-сегментов № 50 / № 26.
По инвентаризации их allocation=33 536, после `0x300` остаётся 32 768 байт.
Это не runtime-селектор, который можно подставить непосредственно в DPMI.

В реальных LEVEL найдены Sprite flags `0x0002`, `0x0008`, `0x0048`,
`0x0108`, `0x0018`, `0x0808`, `0x0408`, `0x2008`, `0x1008`, `0x0010`.
Максимальный Sprite с битами сдвига — 96×192=18 432 байта, меньше scratch.
Это проверка предоставленных данных, а не гарантия безопасности произвольного
изображения. Копирующие ветки работают с 16-битными SI/DI/CX и местами
читают младшее слово pixel_bytes; их нельзя автоматически объявлять
общим huge-copy для изображений больше 64 KiB.

После четырёх пар есть `0x4000`: периодическая маска плоского массива.
Условие с index=0 обходит запись локального слова delta, которое затем
читается (`10F8:0938…096B`, `1060:0A48…0A7B`). Это подтверждённый путь
чтения неинициализированного в пределах функции stack-slot. Точный результат
такого входа зависит от прежнего содержимого стека; безопасный эквивалент
не выбран. В исходных Sprite-директивах `0x4000` не найден. Сам режим
не следует переносить как проверенную регулярную маску с index=0.

Бит `0x0020` меняет направление обхода двух рёбер в rasterize H/V;
это видно по выбору ±1 (`1120:0CF9` / `1078:0CFF`,
`1120:1243` / `1078:1249`). Называть этот бит простым зеркалированием
пикселей без проверки UV/вершин преждевременно. Значения `0x0001`, `0x0002`,
`0x0004`, `0x0010` не получают полного назначения из рассмотренных span
и crop-путей; здесь их смысл остаётся **неустановленным**.

## Освещение и прозрачность

В обоих span последовательность чтений — **сначала индекс текстуры GS,
затем байт таблицы освещения FS, затем запись результата ES**. В обоих
образцах адреса внутри ASM-сегмента совпадают:
`1010:0090…009A` для горизонтального непрозрачного цикла,
`1010:0168…016E` для вертикального непрозрачного.

Важное отличие прозрачной вертикальной ветки: `1010:0197` читает исходный
тексель, `019A` заменяет его через FS, `019D` выполняет `TEST BL,BL`,
`019F` пропускает запись при нуле. Проверяется **результат освещения**,
а не исходный индекс. Формула ветки:

```text
texel = image_pixels[v * width + u]
mapped = light_row[texel]
if mapped != 0:
    destination = mapped
```

Непрозрачные циклы записывают и нулевой mapped-индекс. Горизонтальный ASM
не имеет отдельной прозрачной ветки; присвоение глобального флага перед
вызовом не превращает его автоматически в прозрачный renderer.
Вертикальная подготовка проверяет `DS:[C1F0] & 1` по `1010:015E`.
Растеризаторы задают этот бит из image flags bit `0x0008`
(`1120:0CC9/1213` и `1078:0CCF/1219`). RUS глобальный флаг лежит
в `DS:[C1F0]`, ENG — в `DS:[C2A0]`.

Выбор light-row `1088:0544` ограничивает unsigned индекс сверху числом 15
и берёт far-pointer из таблицы 16 указателей. `1088:0553…055F` использует
беззнаковый переход `JC`, поэтому отрицательное signed-значение, переданное
как word, здесь также попадает в верхнее ограничение. В ENG соответствующий
clamp находится по `1028:197D…1989`.
Загрузчики `1088:0498` / `1028:18C2` копируют 16 последовательных блоков
по 256 байт из ресурса в эти строки. Конструктор выделяет строкам DOS-память
и задаёт offset=0; span использует селектор строки FS и индекс 0…255,
без прибавления младшего слова far-pointer light-row.

Вызовы в горизонтальном и вертикальном растеризаторах получают индекс
из интерполированной глубины: целая часть Q16 через `SAR ...,16`, вычитание
near, отрицательная разность заменяется нулём, затем signed `IDIV 120`.
В обычном диапазоне без word-overflow это `row=min(15,max(depth-near,0)/120)`
с целочисленным делением. RUS деления: `1120:0F4B/1495`,
ENG `1078:0F51/149B`. Это координата глубины, прошедшая геометрический
pipeline; её не следует подменять евклидовым расстоянием до центра объекта.
При переполнении 16-битных промежуточных значений важны реальные x86-флаги;
математическая формула выше не определяет эти крайние случаи.

Во всех шести LIGHT-блоках row 0 — identity, и каждый ряд сохраняет `0→0`.
Но LIGHT1/2/3 в row 15 дополнительно переводят в ноль 39/26/36 ненулевых
индексов. Поэтому перенос проверки прозрачности перед light lookup меняет
семантику даже на реальных таблицах. Это статическое свойство данных и кода,
не измерение числа исчезающих пикселей в игровой сцене.

## Значимые ASM-эффекты

Текстура читается через GS, light-row через FS, framebuffer пишется через ES.
Декомпилированное C часто изображает эти операции как обычные обращения
через один указатель и потому недостаточно для проверки эквивалентности.
Таблица строк framebuffer содержит far-pointer на каждую строку.
Перенос 16-битного DI меняет ES на runtime selector-step из `DS:[C144]`;
это переход huge-pointer в оперативном буфере, не VESA bank-switch.

Горизонтальная ветка `1010:00BA…00C7` при переносе DI возвращается к чтению
следующего пикселя, **пропуская обновление U/V**, которое находится
по `00A2…00AA`. Это наблюдаемый эффект оригинального ASM; буквальное
переписывание в обычный цикл с обязательным шагом координат меняет его.
Пока поведение не требуется сохранять на GBA как отдельное исправление,
но его нельзя терять при заявлении точного восстановления DOS.

## Проверки и границы

Выполнено:

```powershell
C:/Source/wasdify/.venv/Scripts/python.exe scripts/probe_render_layout.py
```

Host-probe проверила C-декодером `dok-anim.exe` все 77 изображений и 154 кадра
каждого языка: всего 462 изображения, 3 289 364 байта пикселей. Метаданные
и FNV совпали с независимым Python-разбором; C-export всех кадров PGM
побайтно совпал с packed row-major payload. Максимум реальных размеров —
320×200, 64 000 байт. Проверены все 6 таблиц LIGHT по 4096 байт.

Девять синтетических случаев различают строки, сохраняемые flags/игнорируемый
far-pointer, flat-view больше 64 KiB, усечение и противоречивые размеры.
Поле width=`0xFFFF` с соответствующими 65535 байтами принимает C-декодер
как **unsigned 65535**; это не тест signed width=-1 в DOS renderer.
Не следует считать такой вход поддержанным оригинальным rendering-profile.
Отдельный пример LUT, меняющей `0→7` и `1→0`, доказывает различие прозрачности
до/после освещения. Синтетический пример проверяет формулу, а не исполняет
оригинальный ASM. Проверки полной геометрии, DOS renderer и FPS сюда не входят.
Сами DOS crop-ветки не исполнялись: таблица сдвигов выше восстановлена по
инструкциям обеих версий. Проба также проверяет наличие 12 нужных ролей
и 26 ключевых ASM-инструкций в каждом свежем Ghidra-экспорте, включая порядок
GS→FS→проверка нуля, OR флагов, runtime flags анимаций и unsigned clamp LIGHT.
Полные пиксели, преобразованные изображения и дампы остаются в ignored
`build/render-layout/`; в `analysis/` входят только хеши, счётчики и результаты.

Материалы WASDify `performance.md` и `render.md` использованы как указатели
на участки исходного кода. Их адреса NE-сегментов переводятся отдельно;
их профили изменённых EXE и FPS не считаются измерениями G04.

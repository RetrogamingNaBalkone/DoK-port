# Воспроизведение декомпиляции

Нужны Ghidra 12.1.2 и JDK 21.0.12.1+1 (именно эти версии использованы
в первом запуске), PowerShell и Python 3.11+ для независимой инвентаризации.
Скрипты используют Ghidra headless; открытый CodeBrowser и MCP не требуются.

## Запуск

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/decompile.ps1
# Или одна версия:
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/decompile.ps1 -Language en
# При другой установке:
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/decompile.ps1 `
  -GhidraHome C:/Tools/ghidra_12.1.2_PUBLIC -JavaHome C:/Tools/jdk-21
python scripts/inventory.py --wasdify C:/Source/wasdify
```

В текущей среде Python доступен через
`C:/Source/wasdify/.venv/Scripts/python.exe`; зависимости этой venv скрипту
`inventory.py` не нужны. Команда `python` в PATH ведёт к заглушке Microsoft Store.

EXE проверяются по SHA-256 до и после Ghidra. Импорт использует штатный
NE-loader и явно заданный `x86:LE:16:Protected Mode`. Первичный автоанализ
ограничен 600 секундами на файл; декомпиляция — 60 секундами на функцию.
Логи сохраняются и должны проверяться на тайм-ауты, ошибки и предупреждения.
Windows PowerShell 5.1 пишет перенаправленный `ghidra.log` в UTF-16 LE;
это нужно учитывать при чтении журнала из Python.

Программа импортируется в отдельный сохраняемый проект каждого языка.
Повторный запуск обрабатывает существующий проект и сохраняет смысловые метки.
Чтобы воспроизвести анализ с чистого импорта, предварительно **переместите**
свои старые каталоги `build/ghidra/<language>` и `decompiled/<language>`
в резервное место. Скрипт не удаляет проекты и не заменяет оригинальные EXE.
Экспорты предназначены для генерирования; ручные правки в них будут перезаписаны.

## Что делает экспорт

1. Выполняет автоанализ NE.
2. Ищет характерные прологи в исполняемых блоках. Новые функции создаются
   только вне уже существующих тел функций и без известного линейного
   перехода из предыдущей инструкции; в комментарии записывается
   эвристическое происхождение. Это не доказывает правильность каждой границы.
3. Применяет адресные метки из `analysis/seeds-*.tsv`, запускает анализ изменений.
4. Выгружает C-псевдокод всех определённых функций, отдельные файлы, индекс
   результатов, листинг инструкций и ссылки из них.
5. Сохраняет штатный C-экспорт Ghidra с определениями типов и глобальными
   символами в `with_types.c`. Его типы соответствуют модели Ghidra,
   а не ABI обычного компилятора Windows/Linux.
6. Считает покрытие по блокам и сохраняет диапазоны вне тел функций.

Пустой список ошибок декомпиляции не отменяет предупреждений в самом C-коде.
`unrecovered.tsv` содержит также таблицы, встроенные данные и заполнение;
его размер нельзя считать размером заведомо пропущенного машинного кода.
Внешние импортные заглушки могут вызывать WARN о EXTERNAL; это не тела библиотек.

`inventory.py` независимо читает заголовки, сегменты и релокации, проверяет
SHA-256 образцов и строит `analysis/inventory-*.json`, `coverage-*.json`,
`segment-matches.tsv`, `wasdify-sources.json`. В происхождении документов
сохраняются хэши файлов, а не обещание, что каждое утверждение уже перепроверено.

## Следующий этап восстановления

Сначала проверить оставшиеся области и тела методов по листингу, восстановить
calling conventions, far/huge pointers, таблицы виртуальных вызовов и формат RES.
Затем переносить по подсистемам в типизированный C/C++, сверяя поведение с
оригиналом в DOSBox. Проверки игрового поведения и сборка SDL2/GBA в рамках
первого статического экспорта ещё не выполнялись.

# N07P — профиль и оптимизация вывода текущего NDS-прототипа

Дополнительное поручение пользователя от 29 октября 2026 года после N11.
Не открывает N12 и не заменяет N23/N24 полной игры.

Статус: **готово (эмулятор)**. Зависимости: [N07](N07.md), [N11](N11.md).
Последующие P-этапы выполняются по [общему протоколу](../spec/performance-checkpoints.md).

## Цель и входы

Измерить текущий вывод на стартах LEVEL1–3, уменьшить затраты renderer,
сравнить до/после при одинаковых камерах и проверить изображение.
Прочитаны NDS-план, handoff, паспорта N07/N11; входы — принятые пакет N04,
`build/nds/n07/scene.dat`, manifest и trig, текущий backend N07 и двери N11.
GBA/SDL2 не затрагиваются; исходные EXE не анализируются и не изменяются.

## Метод

- Отдельные сборки в `build/nds/perf/`, прежние ROM и доказательства сохраняются.
- Одинаковый N07 ARM9-драйвер: 936 кадров, 19 камер/маршрутов, первые кадры,
  три старта, низкие потолки, тяжёлые сцены и повороты. Загрузка отделена.
- CPU ticks и интервалы VBlank из read-only ABI, контроль GPU/VRAM,
  независимые matrix/PosTest/coverage проверки существующего observer.
- Сверка пикселей до/после. Это эмуляторные показатели, не аппаратный FPS.
- Отдельно оценить ограничение вывода диагностического N11 loop.

## Критерии

- [x] Получены baseline и optimized профили на одинаковых 936 кадрах.
- [x] Затраты вывода уменьшились; 19 top PNG и геометрия 936 кадров идентичны, GPU ошибок нет.
- [x] FPS стартов, N11 и audit измерены отдельно; ограничения ниже.
- [x] Обновлены NDS-план и handoff; следующий игровой ID остаётся N12.

## Результат

Программная приёмка завершена. Полные доказательства:
`research/evidence/nds/perf/`; [компактный итог](../../../analysis/nds-render-performance.json).
Исходные N07/N11 ROM, manifests и отчёты не перезаписаны. Шесть изменённых
прежних renderer source/build files и дополнительные исправления среды привязаны
к точным архивным байтам в `host-check.json`. Остальные pin records проверены.
Baseline хранит исходные backend/scene hashes.

### Изменения

- `render_backend.c`: при ≤614 quads применяется доказанный worst-case bound
  10 вершин на quad. Матрицы/координаты/UV/material по-прежнему проверяются
  целиком до записи FIFO; для больших сцен действует прежний exact interior bound.
  Отдельная оценка диапазона матрицы сохраняет rejection переполнения clip coordinates.
- GPU state кэшируется внутри одного submit: polygon format задаётся один раз,
  texture/color — при изменении, identity modelview не загружается для каждой
  клетки, GL_QUADS begin/end объединены по клетке. Порядок полигонов не меняется.
- `scene.c`: точный ранний выход при нулевом пересечении frustum outcodes.
- `door_render.c`: клетки без TMap class4/7 не строятся повторно ради поиска
  дверей; проверка merges реконструирует только class7. Основание — единственные
  ветви DOK_GEOMETRY_DOOR в `render/geometry.c`; crop/mirror не изменены.
  Door pass теперь компилируется ARM, как scene/backend.
- N11 предъявляет кадр на каждом service sweep. C2 продолжает измерять фактический
  sweep, логика не переводится на фиксированные 60 Hz.
- Полное хеширование maps/flags/doors/event bank до/после каждого кадра выделено
  в `RENDER_AUDIT=1`: около 100 КиБ сканирования на кадр — тестовая нагрузка.
  Обычная сборка `RENDER_AUDIT=0` сохраняет motion/camera/revision guards;
  обе сборки проходят внешний snapshot/x86 verifier. Большой прирост N11
  нельзя целиком приписывать алгоритму renderer: он включает устранение audit overhead.

### Измерения

melonDS DS libretro core 1.4.0, DS mode, builtin BIOS, direct boot, JIT off,
software renderer, readonly FAT, host sync off. CPU timer 33513982 Hz,
VBlank 560190 ticks: 59,826098 Hz. Это эмуляторные интервалы, **не аппаратный FPS**.
Обычный N07 renderer и диагностический N11 измерены отдельно.

| Сцена N07, 32 кадра | FPS до → после | Prepare + submit + GE wait, мс до → после |
|---|---:|---:|
| Старт LEVEL1 | 59,83 → 59,83 | 15,290 → 12,550 |
| Старт LEVEL2 | 59,83 → 59,83 | 12,526 → 10,632 |
| Старт LEVEL3 | 59,83 → 59,83 | 10,652 → 8,983 |
| Тяжёлая LEVEL1 | 29,91 → 29,91 | 24,637 → 18,169 |
| Тяжёлая LEVEL2 | 29,91 → 29,91 | 24,490 → 18,323 |
| Тяжёлая LEVEL3 | 29,91 → 59,83 | 19,986 → 15,516 |

Стартовые CPU stages сократились на 15,1–17,9%, submit — на 36,0–38,3%.
Тяжёлые повороты LEVEL1/2/3: 30,29/40,56/37,59 → 44,87/44,32/59,83 FPS.
936 кадров/19 сценариев до и после, все ≤2 VBlank, без geometry/matrix overflow;
GPU hardware counts/poses/texture bytes совпали на всех 936 кадрах.
19 финальных top PNG побайтово совпали, включая flat coverage и moving endpoints.
Старты и промежуточная дверь просмотрены визуально.

N11, шесть state-driven fixtures, активные интервалы внутри одного case/stage
(загрузка, pause и переходы исключены):

- До: 18,75 FPS, интервалы 3–5 VBlank, минимум 14 новых кадров в окне 1 с.
- Обычная оптимизированная сборка: **58,23 FPS**, 2772 интервала по одному
  VBlank и 78 по два; p99=2, минимум **38** новых кадров/1 с, 1562 проверенных окна.
  По cases: 59,31/59,37/59,30/**46,93**/59,83/59,83 FPS. Порог 30 соблюдён
  в этом диагностическом маршруте; цель 60 при ≥99% в один VBlank **не достигнута**:
  фактически 97,26%. Предъявлен 2941 кадр, 1601 ARM9 shared check/0 failures.
- Audit: 19,94 FPS, полные guards прошли. Низкая частота audit не является
  штатным бюджетом, но публикуется как стоимость проверки.

Маршрут реагирует на состояния, поэтому число callbacks и точная timeline
до/после различаются; это оценка живого диагностического цикла, не парный
benchmark одинаковых callbacks. Каждый запуск независимо сверяется с исходными
x86 операциями. До/после start/closed pixels всех четырёх дверей совпали
(8 PNG для каждой из обычной и audit-сборок).

### Проверки и доказательства

Свежие host suites: interactions101, door-render1450, router50;
scene20762 checks. Полный phase-zero scan трёх уровней: 65192 poses,
4937991 checks — PASS. Actual ARM9 admission: 10 checks/0 failures,
614/615 quads, точный interior и worst-case clipped bounds, плохие UV,
вершины и signed32 overflow проверены отдельно.

Обычный N11 runtime/source verifier: 654 native operations, 15 queue deadlines,
990 hero/floor/motion callbacks, 7 conveyor callbacks, 8093696 exact MMap bytes,
1011712 counter bytes, 30 finish predicates, 4 sensor entries, 2893 C2 updates,
2941 camera renders и 27 resets — PASS. Audit отдельно: 227 native operations,
950 hero callbacks, 982 camera renders — PASS. FAT до/после не менялся.
Memory closure остался 3670016 B: static430080 + managed2293760 + SDK290816
+ reserve655360. RAM/CPU/result injection не использовалась.

`archive-manifest.json` закрепляет полные профили, snapshots и контрольные PNG.
Компактный итог содержит hashes обычной/audit ROM/ELF/map, host gates и архива.
Обычная ROM `build/nds/perf/n11-optimized/dok_nds_interactions.nds` — 229376 B,
SHA-256 `a355d7c1dabce6713c04f8c01cb41734271a5cb7db6e03546f93ea2a331364bf`.
Исходная N11 ROM остаётся по прежнему пути/хешу; не выдавать её за новую.

### Команды повторения

После замечания пользователя удалены пять старых `sys.path`-вставок из NDS
native-oracle scripts и жёсткий путь Python в `audit_evidence.py`. Новые проверки
раньше наследовали эти импорты — это была межпроектная зависимость инструментов,
а не игровых данных. Теперь общий Python3.14.6/Unicorn2.1.4 установлен в user site;
импорты и повторные renderer/N11/audit проверки выполняются без модулей из соседнего
проекта. `python-environment.json` фиксирует реальные пути и пустой список таких
модулей. Зависимость закреплена в `ports/nds/tools/requirements.txt`:

```powershell
py -3.14 -m pip install --user -r ports/nds/tools/requirements.txt
```

Исторические отчёты не редактируются ради замены фактически использованных команд.

Из корня, PowerShell, Python3.14.6, Zig0.13.0, BlocksDS1.24.0-1/GCC16.2.0,
20 закреплённых SDK packages, melonDS DS core1.4.0, Unicorn2.1.4:

```powershell
$ndsCore = 'C:/Users/dspev/AppData/Local/Programs/melonDS-DS/1.4.0/melondsds_libretro-win32-x86_64-Release/cores/melondsds_libretro.dll'
py -3.14 -B -X utf8 ports/nds/tools/benchmark_renderer.py --variant optimized --core $ndsCore
py -3.14 -B -X utf8 ports/nds/tools/check_renderer_admission.py --core $ndsCore
py -3.14 -B -X utf8 ports/nds/tools/check_render_performance.py --core $ndsCore
py -3.14 -B -X utf8 ports/nds/tools/check_render_performance.py --audit --core $ndsCore
py -3.14 -B -X utf8 ports/nds/tools/summarize_render_performance.py
```

Baseline был собран и измерен `benchmark_renderer.py --variant baseline --core
<DLL>` **до правок renderer**; повторить существующий baseline без пересборки —
та же команда с `--skip-build`. Не пересобирать baseline текущими оптимизированными
исходниками: для чистого восстановления использовать архивные backend/scene,
точные hashes закреплены в `baseline/build-manifest.json`.
При ручном переключении `RENDER_AUDIT` в одном output directory нужна Rebuild;
драйвер использует отдельные `n11-optimized/` и `n11-audit/`.

### Решение по архитектуре и следующий шаг

**Продолжать к N12 после отдельного поручения.** Геометрический renderer
жизнеспособен, но actor/animation/texture working set и совместный LIGHT/вода/
отражения ещё не проверены. N13P — совместное решение о бюджете этих подсистем;
локальные проблемы актёров исправляются внутри N12. Следующие крупные
оптимизации — после живого боя N17P и двух экранов N21P.
Полная игра, настоящий audio/map/UI budget и физическая DS/DS Lite остаются
последующими этапами; N23/N24 не выполнены. GBA/SDL2 не изменялись.
Следующий игровой ID — **N12**, автоматического продолжения нет. Первый шаг:
прочитать N12, сверить текущие N07P gate/manifests и принять модель объектов.

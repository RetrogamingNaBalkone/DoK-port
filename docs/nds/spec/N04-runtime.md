# N04: ограниченная runtime-читалка и проверка ARM9

29 октября 2026 года. Host-проверки и три сценария эмулятора пройдены.
Формат — [DOKNDS1](N04-assets.md), подготовка и независимая сверка данных —
[N04-converter](N04-converter.md), итоговая приёмка — [паспорт N04](../tasks/N04.md).
Бюджет памяти сохраняет решения [N03](N03-memory.md).

## Владение и чтение

[assets.h](../../../ports/nds/include/dok/assets.h) и
[assets.c](../../../ports/nds/core/assets.c) реализуют strict C11 без SDK,
stdio и динамических выделений. SHA-256 находится в отдельном переносимом
модуле. Поля диска читаются little-endian по байтам; C-структуры и исходные
DOS-указатели на дисковую память не накладываются.

Caller передаёт `dok_asset_reader`: context, read-only callback `read_at` и
известный размер файла. Один запрос не превышает 65536 байт. До чтения
проверяются offset и длина через вычитание, без переполняющего сложения.
Ошибка callback возвращает `IO_ERROR`; результат короче или длиннее запроса
даёт `SHORT_READ`. Читалка не превращает короткое чтение в успешное.

`dok_assets_open` потоково проверяет header и каталог: SHA, версию, порядок
ID, происхождение производных записей, поля представлений, диапазоны,
точные aliases и нулевое выравнивание. Каталог целиком не остаётся в RAM.
Сессия хранит reader и проверенные метаданные; lookup использует двоичный
поиск фиксированных записей. Открытие ещё не проверяет все payload.

Память сессии, context и пакет принадлежат caller и остаются живыми во время
использования. Сессия, конфигурация reader и bytes пакета неизменяемы;
внутренние курсор файла и счётчики чтений context могут обновляться callback.
`AssetCatalog.implementation` заимствует сессию; mutable cache state хранится
отдельно. Файл нельзя менять или
закрывать под работающей сессией; после изменения требуется новое открытие.
SHA проверяет целостность, а не авторство пакета. Привязка оригиналов к
известным SHA выполняется конвертером и независимым oracle.

При ошибке открытия выходная сессия сохраняется; workspace может измениться.
`dok_assets_load` читает payload в ещё не опубликованный candidate, проверяет
SHA, типовую схему и ссылки descriptor, затем выдаёт `dok_asset_view`.
Выходной descriptor при отказе сохраняется. Байты candidate **могут измениться
при отказе** и остаются недоступны потребителю. Candidate не должен пересекаться
с живой сессией или выходным объектом. `RAW_SOURCE` возвращает `VERIFY_ONLY`;
для него предусмотрена отдельная потоковая проверка хеша, без объявления
исходных bytes готовым runtime-объектом.

## Кэш и сроки жизни

Caller задаёт backing и размер каждого `dok_asset_cache_slot`; фиксированных
слотов по 128 КиБ и автоматического LRU нет. Замена требует отдельного
candidate. Старый backing, metadata и выходной lease сохраняются при отказе.
При успехе проверенные bytes копируются в backing, generation увеличивается
и публикуется один pinned lease. Пока есть pin, замена отвергается до чтения.
Счётчики generation и pins не заворачиваются при переполнении.

Lease имеет линейное владение: его нельзя копировать как ещё одного владельца.
`acquire` создаёт дополнительный pin, `release` снимает pin и очищает переданный
lease. Проверка generation отклоняет устаревшую ссылку после замены. Caller
сохраняет слот и backing до завершения всех потребителей. Дальнейшие policy
рабочего набора, GPU uploads и eviction принадлежат N07; N04 их не подменяет.

Кандидаты и все resident backing суммарно входят в 1 МиБ asset pool. API не
выделяет скрытый staging поверх этого потолка. Он проверяет размеры переданных
слота и candidate; общий учёт нескольких слотов остаётся обязанностью владельца.

## Платформенный probe и память

[file_reader.c](../../../ports/nds/platform/assets/file_reader.c) использует
только `fopen(...,"rb")`, `fseek`, `ftell` и `fread`; путь пакета в probe —
`fat:/dok/assets.ndp`. Локальный `dok-assets.ndspak` копируется под этим именем
8.3. Wire-формат имеет uint32 offsets, но этот stdio adapter ограничен
положительным 32-битным `long`: файл не больше `LONG_MAX`, то есть меньше
2 ГиБ. Текущий пакет размером 9230016 байт укладывается в этот предел.

Probe сначала ограничивает SDK heap областью ARM9 и исключает резерв
655360 байт. Затем выполняет отдельные стартовые выделения:

| Область | Выделено, байт | Использование в этом probe |
|---|---:|---|
| Asset pool | 1048576, плюс до 31 байта выравнивания | Два региона по 131072: candidate и backing |
| I/O | 131072 | Typed workspace 114688: ranges 81920 и scratch 32768 |
| Audio | 262144 | Одна проверяемая PCM-часть до 65536 байт |

Поле `asset_highwater=262144` описывает **фиксированное резервирование двух
регионов probe**. Это не измеритель allocator и не пик полной игры; оно
заполняется и в сценариях без пакета. Long PCM не собирается в один буфер.
В happy-сценарии конечный heap limit равен `0x022E0000`, static занимает
92692 байта, доступный хвост роста SDK heap — 1474560 байт. Эти числа относятся
к диагностическому ROM, а не к будущим миру и renderer.

## Что проверено

Host выполнил 4759 проверок: все 1466 записей реального пакета, 292 RAW,
все 16 представлений и обе локализации; SHA и типовые схемы, cache lifetime,
overflow, bounds, short read и сохранность результатов при отказах.
Дополнительные тесты изменяют отдельную host-копию пакета и пересчитывают SHA:
неверные ссылки анимаций, PCM offset, GPU padding, глубину LEVEL и четыре
некорректные UTF-8 последовательности всё равно отклоняет typed validation.
Linux x86_64-musl собран, но не исполнялся. Переносимые файлы и compile gates
скомпилированы для ARM9 в strict C11; только SDK-facing `main.c` — GNU C11.

Реальное исполнение ROM в эмуляторе прошло три сценария:

| Сценарий | Результат ARM9 |
|---|---|
| `happy` | status 1, mask `0x3fff`, types `0xffff`, negative `0xff`, errors 0 |
| `missing-media` | status 3, FAT недоступна, mask `0x2000`, errors 0 |
| `missing-package` | status 4, FAT доступна, `NOT_FOUND=11`, mask `0x2000`, errors 0 |

В `happy` загружены представители всех 16 типов **обоих языков**. Проверены
реальный GPU payload 131072 байта и все 474361 сэмпл длинной заставки в восьми
частях. Наблюдатель отдельно прочитал из RAM все 49152 байта итогового RU
STATIC_INDEX8 и побайтно сверил с пакетом. Для каждого сценария получены
30 согласованных завершённых наблюдений; программа продолжает исполняться.

Отказы missing/version/truncated/hash/schema проверяются отдельными tiny
пакетами с положительным `control.ndp`. Эти файлы — синтетические format
controls, не ресурсы оригинальной игры. Short read и I/O error внедряются
в callback самого probe; игровое состояние, RAM и результаты наблюдателем
не подменяются. Реальные данные отдельно связывает с исходными RES oracle.

Наблюдаемый [ABI](../../../ports/nds/platform/assets/assets_probe.h) —
`g_nds_assets_probe`, 144 байта, little-endian uint32, версия 1. Для чтения
нужны два одинаковых чётных sequence; перед публикацией выполняется cache
flush. В диагностике показаны текстовые TOP/BOTTOM экраны. N04 проверяет
чтение PCM, не воспроизведение звука; игрового renderer здесь нет.

## Повтор и доказательства

Из корня репозитория, общий CPython 3.14.6:

```powershell
C:/Source/wasdify/.venv/Scripts/python.exe -X utf8 ports/nds/tools/check_assets.py
C:/Source/wasdify/.venv/Scripts/python.exe -X utf8 ports/nds/tools/run_assets_emulator.py --core C:/Users/dspev/AppData/Local/Programs/melonDS-DS/1.4.0/melondsds_libretro-win32-x86_64-Release/cores/melondsds_libretro.dll
```

Первая команда повторяет converter/oracle, сравнивает две подготовки пакета,
выполняет host tests и чистую ARM9-сборку. Вторая запускает три отдельных
процесса эмулятора. Версии: Zig 0.13.0, BlocksDS 1.24.0-1, ARM GCC 16.2.0;
driver проверяет все 20 закреплённых SDK-пакетов. Эмулятор — **melonDS DS
libretro core 1.4.0**, отдельный core-проект. Применены DS mode, builtin
BIOS/firmware replacements, direct boot, software renderer, JIT и threaded
renderer выключены, сеть и folder sync выключены. FAT16 fixture — 32 МиБ;
SD включена только в сценариях с носителем, runtime-запись запрещена.
Core при direct boot добавляет ROM в FAT до исполнения ARM9; хеш образа
после загрузки не меняется во время run и unload.

Первичные отчёты: `research/evidence/nds/n04/host-check.json`,
`build/nds/n04/build-report.json`, `build/nds/n04/emulator/result.json` и
по одному `result.json`/PNG в подкаталогах трёх сценариев. Они фиксируют
точные команды, версии, SHA исходников, core, пакета, ROM и ELF. Сводку и
окончательные пути постоянного архива передаёт паспорт N04.

Физическая DS/DS Lite, flashcart/loader, FPS, задержки microSD, полный рабочий
набор игры и звуковой вывод этой проверкой не доказаны. Аппаратная приёмка
остаётся N24 по [validation-policy](validation-policy.md).

# C8: независимая оценка порядка DMA

29 октября 2026 года. Рассмотрено предложение исполнителя; это не подтверждение
готовой C8-сборки. Аудитор не менял продукт и не запускал эмулятор.

Предложение: после presentation wait сначала перенести готовую нижнюю карту,
затем выполнить GPU stream commit и HUD. Дополнительно при позднем входе
дать map DMA одну новую границу VBlank с отдельным учётом extra wait.

**Обычный путь условно одобрен по статике.** Нужно сохранить следующие условия.

## Банки и последовательность

Map bitmap расположен в C/SUB_BG. Stream remap сохраняет C/SUB_BG и переводит
A/B/D в LCD для texture transfers; palette transfer использует F. HUD расположен
в E/MAIN_BG. Map `dmaCopy` синхронен и заканчивается до следующего transfer.
Перестановка не создаёт пересекающегося адресного диапазона или одновременного
использования DMA по рассмотренному коду.

GPU uploader уже использует допустимые VCOUNT окна [192…262] и [0…47].
Его guard нельзя ослаблять. Это действующий контракт реализации и эмуляторных
проверок; объяснение «на этих строках всегда только небо» не доказано.
Физическая проверка texture fetch timing остаётся N24.

Для map сохраняется более строгий gate 192 ≤ start ≤ end ≤ 262 и длительность
меньше кадра. Передача 49 152 байт должна начинаться с достаточным запасом
blank. При позднем входе допускается одно дополнительное ожидание, затем
повторная проверка admission с отказом вместо бесконечного цикла.

Extra wait нужен в полной cadence и touch latency, в отдельном probe поле,
в общем wait и CPU exclusion. Timestamp совместного предъявления и VBlank
counter должны относиться к новой границе. Map CPU остаётся prepare+commit
без паузы между ними. Повтор верхнего изображения не является новым кадром.

## Существенный риск audit-пути

Перенос **всего** прежнего `nds_map_commit()` первым переносит также
N21P_AUDIT VRAM memcmp, который занимает около 15,45 мс. Если он выполняется
перед pending GPU texture upload, uploader пропускает почти целую развёртку.
Его start/end VCOUNT modulo 263 могут вновь попасть в допустимое окно,
хотя deadline именно этого swap уже потерян. Это блокирующая оговорка
к механическому переносу всей функции в audit-сборке.

Предпочтительные варианты для исполнителя:

- Normal map commit первым; audit сохраняет GPU stream первым, затем выполняет
  map admission/commit с честным extra wait. Порядок диагностики различается,
  source disclosure, bitmap и общий guard сохраняются.
- Либо отделить bounded map transfer от дорогой проверки и выполнить проверку
  после GPU upload, сохранив честные probe counters и snapshot publication.

Чтобы VCOUNT modulo не скрывал пропущенный upload deadline, дополнительно
проверять elapsed stream completion от принятой presentation boundary.
По существующему окну от line 192 до окончания line 47 следующего кадра —
119×2130 = 253 470 timer ticks, около 7,563 мс. Один start/end VCOUNT этого
не доказывает. У подтверждённого C7 примера суммарные map DMA и stream transfer
занимают примерно 5,254 мс; audit memcmp заведомо не помещается в это окно.

После реализации требуются замороженные SHA, полный actual map DMA gate,
старый GPU upload gate с проверкой epoch/elapsed, independent LCD/texture
проверки, overflow flags и полный RU/EN cadence. Результат лёгкой сцены
не заменяет тяжёлые cases 14/15/39 и cold transfers.

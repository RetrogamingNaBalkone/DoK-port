# NDS: статическая оценка переноса рендера на GPU

29 октября 2026 года. [Паспорт исследования](../tasks/N17P-GPU.md).

## Вывод

**Потенциал дополнительного ускорения есть, но основной перенос уже выполнен.**
Стены, плоскости, двери и billboard-объекты растеризуются аппаратным 3D-движком;
он выполняет проекцию вершин, clipping, текстурирование и depth test. Выбранный
N13P добавляет аппаратный black fog вместо дорогого точного LIGHT.
Переписывать этот renderer как новый «GPU renderer» не требуется.

Следующие обоснованные направления: сохранённые списки команд с DMA,
перенос сдвига воды из пиксельных копий в UV и аппаратный вывод оружия/HUD.
Для самого крупного остаточного этапа, подготовки геометрии, нужен также
кэш статических поверхностей на ARM9. DS не исполняет произвольный код
обхода карты, построения полигонов или оригинальную таблицу LIGHT на GPU.
Универсальных программируемых shader/compute stages в её 3D API нет.

Одни display lists не доказывают 60 FPS. Статическая оценка рекомендует
сохранить архитектуру N13P, сначала сократить повторную подготовку сцены,
затем проверить DMA и воду отдельными парными опытами в N17P.

## Образец, доказательства и границы

- Анализируется текущее рабочее дерево `ports/nds/`, включая существовавшие
  до исследования незакоммиченные изменения N14–N16. Проверенные байты
  C/SDK и входов закреплены SHA-256 в локальном отчёте.
- База производительности: принятые RU/EN отчёты N13P из
  [компактного результата](../../../analysis/nds-n13p-performance.json).
  Их SHA перепроверены; ниже выполнен только offline-пересчёт существующих
  историй. Новых замеров, ROM-сборок и запусков эмулятора нет.
- SDK: установленный BlocksDS 1.24.0-1; проверены `videoGL.h`, `background.h`
  и исходник SDK tutorial. Онлайн-первичные источники проверены отдельно:
  [display lists](https://blocksds.skylyrac.net/tutorial/intermediate/3d_graphics/#13-display-lists),
  [texture modes/matrix](https://blocksds.skylyrac.net/tutorial/intermediate/3d_graphics/#10-final-notes-about-textures),
  [libnds API](https://blocksds.skylyrac.net/libnds/videoGL_8h.html).
  В онлайн-tutorial встречается ошибочная строка о palette banks;
  VRAM layout здесь берётся из установленного SDK и принятого N07/N13P.
- Новый анализ исходных EXE не выполнялся. Сведения о воде взяты из уже
  проверенных N13 материалов. Адреса ниже — строки файлов NDS-порта,
  не файловые смещения EXE, не Ghidra-адреса и не DPMI-селекторы.
- N13P измеряет накопленные renderer fixtures, без совместного живого боя,
  звука и полной touch-карты. N15/N16 проверяют логику отдельно. Полный бюджет
  остаётся N17P/N21P, физическая DS/DS Lite — N24.

Воспроизведение без запуска игры:

```powershell
py -3.14 -B -X utf8 ports/nds/tools/audit_gpu_potential.py
```

Отчёт: `research/evidence/nds/gpu-static-20261029/report.json`.
Collector проверяет исходный fixture SHA и SHA обоих полных N13P отчётов,
разделяет штатные и synthetic cases по тому же правилу, что N13P, сохраняет
23 source/SDK pins и 6 input pins. Это статическое исследование с повторным
разбором старых измерений, не парный performance-тест новой реализации.

Средние рассчитаны по 1849 штатным presentations без 17 cold-loading кадров.
Источник полей — `platform/effects_probe/main.c:533–585`, правило отбора —
`tools/summarize_effects_performance.py:13–30` и `tools/render_metrics.py`.
Submit включает исполнение ARM9 и возможные stalls при записи в FIFO.
Короткий финальный fence не доказывает отсутствия GE stalls внутри submit
и ничего не измеряет о полном времени растеризации.

Худший RU кадр, case16/frame654: geometry 13,885 мс, sprites 1,042 мс,
effects 5,542 мс; prepare всего 20,471 мс, submit 6,535 мс,
upload 3,446 мс. Это nonloading кадр, CPU-read bytes = 0,
generated effect bytes = 49 152. Effects включает scheduling, обработку
вариантов и stream plan; все 5,542 мс нельзя приписывать одному memcpy.
Профиль других cases содержит и cold/synthetic пики: их нельзя смешивать
со штатными steady-state затратами.

При 59,826 Гц один VBlank даёт 16,715 мс, два — 33,430 мс.
В худшем RU кадре требуется убрать примерно 13,737 мс измеренных компонентов
для одного VBlank ещё до добавления боя/UI/audio. Даже условное обнуление
всех 6,535 мс submit оставит 23,917 мс. Это арифметическая граница,
не прогноз реального DMA-ускорения. Средняя сумма компонентов и FPS
не обратны друг другу из-за VBlank, фаз uploads и служебной публикации.

GPU storage в существующем полном наборе: максимум 287/2048 polygons (14,0%),
1154/6144 vertices (18,8%), textures 260 096/393 216 B (66,1%).
Это запас ёмкости, не гарантированный запас fill rate. После укрупнения
пакетов или добавления полигонов заново проверяются counts, sticky overflow,
line underflow и cadence. Нельзя оценивать GPU-загрузку как «14%» по числу граней.

### 1. Packed display lists и DMA

Backend сейчас уже использует quad strips и не повторяет одинаковые
texture/color bindings. Поэтому сравнивать нужно с этим вариантом.
`glCallList()` передаёт packed words через asynchronous DMA; display list
лежит в RAM и повторно передаётся, это не GPU-resident mesh или vertex buffer.

Разумный опыт: сохранить утверждённые вершины/UV/порядок в командах,
обновлять только камеры, двери, актёров и material bindings. Неподвижную
геометрию переупаковывать при изменении входов, а не на каждом кадре.
Простая упаковка всего динамического packet заново может только заменить
одну CPU-петлю другой; ускорение этой реализации пока гипотеза.

Требуются bounded command storage, flush CPU cache перед DMA, завершение
DMA до повторной записи/освобождения списка, согласование DMA channel
с texture uploads и сохранение порядка immediate/FIFO commands.
Нынешний контракт `render_scene.h` разрешает release после синхронного submit;
асинхронность нельзя добавить без нового срока жизни буфера.
Списки с TEXIMAGE_PARAM/PAL_FORMAT должны перепривязываться при eviction,
repacking и смене поколений VRAM. Сохранять физические адреса навсегда нельзя.

Admission, ошибки и публикация целого кадра сохраняются. В production fog
весь наблюдённый набор имеет максимум 291 quads: он уже проходит
`worst_case_fits <= 614` и обычно не выполняет подробный per-vertex CPU
clip-transform в backend. Перенос этого уже пропущенного этапа не даст
обещаемого выигрыша. Пер-вершинный `visible()` в scene builder остаётся.

### 2. Статическая геометрия и сокращение матриц

Основной кадр вновь вызывает `dok_geometry_build_cell()` для клеток gather AABB,
затем `visible()`, копирование, merge и подготовку локальных origins.
Для неизменившихся стен/полов/потолков можно кэшировать исходные поверхности
и компактные данные для visibility, оставляя динамические двери отдельно.
Это CPU-кэш и снижение объёма подготовки, которое затем помогает DMA-пути.

Нужны invalidation по world epoch, изменениям TMap/FCMap и соседних клеток,
bindings/размерам материалов; после pickup клетка тоже может измениться.
Порядок обхода, source_surface_id и исходные UV resets сохраняются.
Полный mesh всех клеток в RAM без расчёта размера не предлагается:
world slab N13P занят 379 576/393 216 B, reserve 655 360 B не расходуется.
Бюджет командных буферов/кэша также нельзя считать уже свободным.

GE умеет умножать матрицы, но текущий CameraPlan специально фиксирует
квантизованный базис и точно сдвигает его по integer lattice. Обычное
раздельное projection × modelview давало разницу в один clip LSB на стыках.
Выгода крупных chunks — меньше matrix loads; цена — изменение merging/culling,
диапазон v16, геометрический бюджет и повторная проверка near/стыков.
Сначала кэширование существующей схемы, затем отдельный эксперимент с chunks.

### 3. Вода: переносить sampling, сохраняя исходную фазу

В production fog ключ текстуры всё ещё содержит water phase/direction.
`dok_effects_pixels()` генерирует сдвинутые CPU pixels, effect cache хранит
варианты, streaming загружает новые payload. DMA копирования в VRAM уже есть
в `dok_nds_stream_commit()`: повторное предложение «включить DMA uploads»
не устраняет генерацию вариантов.

Сохранённые N13 native phase headers всех трёх уровней показывают 96×96.
POT storage — 128×128. Wrap на GPU повторит весь storage вместе с padding,
а source cyclic crop повторяет 96 texels. Масштабирование 96→128 изменит
исходные детали и sampling; это отдельная художественная адаптация.

Предпочтительный первый GPU-опыт для cyclic воды: подготовить offline две
копии исходных 96 texels вдоль оси движения. Видимая область 192×96 хранится
в 256×128 (для второй оси — 96×192 в 128×256). Целый сдвиг
`floor(size/divisor) * phase` нормализуется по 96 и прибавляется к UV 0…95.
Диапазон выборки остаётся внутри двух копий, hardware wrap не требуется.
Ни ресэмплинг исходных texels, ни фазовые pixels, ни дополнительные грани
для cyclic сдвига здесь не нужны. GPU выполняет sampling при прежней геометрии.
Обновляются несколько UV либо texture matrix; callback/phase остаются ARM9.

Цена такого extended texture — 32 КиБ вместо 16 КиБ на ресурс/ось, то есть
дополнительно 16 КиБ. При трёх независимых resident variants это ещё 48 КиБ;
запас 133 120 B при максимуме N13P допускает такой опыт арифметически,
но новый working set, contiguous allocation и будущие projectile frames
ещё требуется проверить. Разные ресурсы объединяются только по доказанному
совпадению. Logical source dimensions 96 должны остаться отдельными от
sampling extent 192 и POT storage: нынешние UV guards/backend metadata
не разрешат расширенные UV без явного изменения контракта.

Альтернатива без дополнительной texture memory: исходная texture остаётся
неизменной, поверхность делится на границе логического wrap, а UV второй
части возвращаются в 0…95. Для одной оси на прямоугольной поверхности
достаточно рассмотреть максимум две области, но после clipping/других
разбиений общий бюджет считается заново. Текстурная матрица сама проблему
периода 96 не решает. У extended texture нет нового геометрического шва,
что делает её более простым первым кандидатом при доступной VRAM.

Нециклический crop должен сохранять нулевое заполнение: clamp последнего texel
не эквивалентен. Для непрозрачного материала index0 может быть видимым цветом,
поэтому «просто не рисовать пустую область» также не эквивалентно.
Понадобятся правильные пустые участки/геометрия или сохранение CPU fallback.
Швы, nearest sampling, index0/depth, все направления и фазы проверяются
по имеющимся 150 synthetic crops на язык и 540 actual phase pairs,
а также новым парным GPU-растром: совпадения CPU pixels недостаточно.

Более простой альтернативный опыт — предгенерация bounded набора фаз при
загрузке с RAM-кэшем. Она сокращает CPU generation, но не переносит её
на GPU и не гарантирует сокращение VRAM uploads. Один 128×128 INDEX8 frame
занимает 16 КиБ, 18 фаз одного ресурса — 288 КиБ; размещать все фазы
в VRAM без рабочего набора нельзя. Делить/объединять разные directions
можно только по доказанному совпадению payload и фаз.

### 4. Оружие, HUD и карта

N15 `dok_weapon_overlay()` очищает 39 424 pixels сцены и обходит до стольких же
позиций, вычисляя source nearest coordinates `x*5/4`, `y*25/24`.
Это software API, проверенный отдельно; его стоимость не входит в N13P FPS.
При N19 перенос на affine 2D bitmap/OBJ или ортографический textured quad
уберёт full-screen CPU scaling. Кадры можно также готовить offline с точным
принятым sampling, затем аппаратно позиционировать.

Коэффициент 25/24 и целочисленная source позиция могут не совпасть побитово
с Q8 affine sampling DS: нужен контроль растра. На 3D-пути оружие рисуется
последним с отдельной ortho/depth/fog политикой; на 2D-пути нужны палитра,
transparent index и правильный приоритет BG/OBJ поверх 3D.
Main VRAM E = 64 КиБ уже отведена HUD/background: дополнительные BG/OBJ
нельзя обещать без раскладки банков. Нижняя карта должна использовать
отдельный 2D engine; раскрытие visited остаётся игровой логикой ARM9.

## Что не стоит переносить

AI, collision, события, выбор кадров и исходное scheduling остаются ARM9.
Draw-derived рассмотрение актёров уже отделено в N16 от cadence вывода;
GE visibility не должна включать/выключать simulation.
Sprite source bounds и near semantics также нельзя молча заменить GPU clip.

Hardware box/position tests полезны как точечные инструменты, но выдача
запроса и чтение результата сериализуют работу. Для сотен отдельных клеток
они могут быть дороже консервативного CPU coarse test. Box test не является
occlusion query; глубинное перекрытие им не определяется. Простое отключение
`visible()` увеличит набор полигонов и текстур; запас уже видимого набора
не доказывает вместимость всего gather AABB. Fully black fog также не делает
автоматически безопасным удаление полигонов, влияющих на depth/occlusion.

Ни vertex lights, ни fog не заменяют точный исходный LIGHT с произвольным
palette index remap и nonzero→0 holes. Принятое отличие уже описано N13P;
новая попытка точного восстановления не требуется этим запросом.

## Рекомендуемая проверяемая последовательность

1. В N17P связать живую сцену с production `EFFECT_GPU_FOG=1`, снять baseline
   со стадиями geometry/visibility/sprites/effects/admission/packing/FIFO wait.
   Сравнивать с ней каждый следующий вариант при одинаковом состоянии мира.
2. Проверить bounded кэш статических поверхностей и invalidation; сохранить
   текущую математику и порядок. Опубликовать RAM и выигрыши steady/turn/cold.
3. Проверить retained packed lists + DMA; считать упаковку/cache flush и stalls,
   не только длительность `glCallList()`. Сохранить admission и frame lifetime.
4. Отдельно проверить воду с extended texture + UV, затем при необходимости
   UV-разбиение или phase cache; выбрать вариант
   по изображениям, generation/upload bytes, худшему кадру и VRAM, а не среднему FPS.
5. В N19/N21P проверить аппаратный overlay и два 2D экрана совместно с боем/звуком.

Приёмка ускорения: одинаковые исходные состояния/callbacks и кадры ресурсов,
полный состав объектов/эффектов, изображения с проверенными допустимыми
отличиями, отсутствие overflow/underflow и соблюдение RAM/VRAM reserve.
Штатные маршруты отделяются от all-awake; цель 30 и цель 60 проверяются
по существующему VBlank-протоколу. Новые варианты здесь не реализованы;
их ускорение, 60 FPS и аппаратный запас остаются гипотезами.

# N06: новые DOS-эталоны с настоящей VGA-палитрой

Этот документ описывает отдельный стенд N06. Старые G00-кадры остаются
неизменными: их серые PNG нельзя считать цветными DOS-эталонами. Новый
коллектор — [capture_visual_dos.py](../../../ports/nds/tools/capture_visual_dos.py).
Он не импортирует реализацию GBA, не меняет код игры и не подставляет позу.

процесс, в отчёт не записывается.

## Штатный выбор мира

Каждая пара языка и номера уровня получает чистую копию и отдельный процесс.
Последовательность: титул → Enter → предыстория → Enter → меню; затем
`Down` ровно `level−1` раз → Enter → BINTROn → Enter → Enter → первый 3D-кадр
с ожидающей нажатия заставкой попытки.
Сохраняются титул, предыстория, меню до и после выбора, BINTRO и стабильный
первый 3D-кадр. Историческое имя файла `play-start` сохранено, но оно само
по себе не доказывает активный gameplay loop. Ввод идёт через API
`input/sequence`, make/break i8042, 100 ms PIC на
нажатие. Это проверяет путь оригинального ввода эмулируемой клавиатуры;
физическая клавиатура пользователя не проверяется.

Ожидаемые координаты из `analysis/originals/worlds-{ru,en}.json` используются
только для поиска и сверки героя. Это результат прежнего исследования
оригинальных LEVEL/ASM, а не импорт GBA-модуля. Координаты не записываются
в гостевую память. Проверка первого 3D-кадра требует единственного native-объекта
class 1 и совпадения естественной камеры с позой нужного мира:

| Образец | LEVEL1 x/y/z | LEVEL2 x/y/z | LEVEL3 x/y/z |
|---|---|---|---|
| PKR RU | 15120 / −300 / 22800 | 20880 / −300 / 3120 | 17520 / −300 / 28560 |
| PKE EN | 15120 / −300 / 23280 | 20880 / −300 / 3120 | 17520 / −300 / 28560 |

Heading каждого старта — 90°. Английский LEVEL1 не выдаётся за RU-мир NDS.
Для целевых кадров NDS используются три RU-старта; три EN-запуска служат
проверкой второго оригинала и локализованного оформления.

## Что именно захватывается

Индексный кадр — прямое чтение гостевой VGA RAM `0xA0000`, 64000 байт,
320×200. Палитра `.vga6` — 768 последовательных чтений порта `0x3C9`
после выбора read index 0 через `OUT 0x3C7`. Запись меняет только индекс
чтения DAC, не цветовые компоненты, код, данные мира или позу. Все компоненты
обязаны быть в диапазоне 0…63.

Независимо читается API `video/frame?format=raw&mode=raw`. В этом стенде он
выдаёт **BGRX32**, native width/height 320/200 и pitch 2560. Формат заголовка
подтверждён официальным `video.cpp`: LE u32 width, u32 height, i32 pitch,
u8 pixel format, u16 palette count; затем данные. Из каждой строки берутся
первые 320 BGRX-пикселей; padding не изображается. Производный `.api.rgb`
содержит RGB888, 192000 байт, и позволяет независимо повторить сверку цвета.
Для принятого кадра каждый его RGB-пиксель побайтно равен исходному VGA-индексу,
применённому к считанному DAC. Реальное расширение цвета данного эмулятора:
`rgb8=(vga6*255+31)//63`. Это не утверждение о физической передаточной
характеристике монитора и не правило преобразования RGB555 для NDS.

Для каждого имени кадра сохраняются:

- `.idx` — исходные 64000 индексов;
- `.vga6` и `.rgb8` — настоящий DAC и его проверенное расширение;
- `.api.rgb` — независимый цветной кадр API;
- `.png` — индексный PNG без коррекции аспекта, 320×200;
- `.data.bin` — 65536 байт native data segment для компактного воспроизведения
  camera-полей; адрес и SHA записаны в отчёте.

Герой ищется в 16 MiB гостевой памяти. Целый временный снимок не сохраняется:
выбранные поля, линейный адрес героя и два состояния находятся в `report.json`.
Камера читается по найденной базе C-runtime anchor, DS offsets RU `AA16…AA52`,
EN +`B0`; focal отдельно RU `0934`, EN `0A44`. Это линейная гостевая память
конкретного процесса, не NE/file offsets и не `selector*16`.

## Согласованность и границы доказательства

Отдельные API-запросы атомарны между шагами CPU. Глобальная пауза не
используется. Коллектор читает RAM A → RGB A → 768 DAC-компонентов → RGB B →
RAM B. Он принимает только bracket с одинаковыми двумя VGA-кадрами, двумя
RGB-кадрами, побайтным совпадением VGA+DAC с RGB и одинаковыми camera/hero
полями по краям. Продолжительность bracket и IRQ/scheduler до и после
сохраняются; часы могут идти. Это стабильный наблюдённый старт, а не обещание
захвата самого первого native presentation или одинакового tick во всех
процессах. Фаза воды/анимации/эффекта остаётся `unknown`, если специально
не установлена. Эти кадры не принимают будущую динамику N13/N22 за готовую.

Дополнительно первый 3D-кадр должен подтвердить измеренную камеру: D=200,
width/height argument=320/161, центр 159/79, clip 0/0/319/159,
viewport scale=8, focalQ12=4096. Различия между новыми изображениями и
историческими G00 не скрываются: новый процесс, настоящий клавиатурный путь,
другой стенд и время наблюдения могут менять HUD/динамическую фазу.

## Шестой Enter и чистая активная игра

Фаза первого 3D-кадра установлена отдельно по native data и ASM, а не по
слову `play-start`: счётчик RU DS:`1FAE` / EN DS:`205E` ещё равен 1,
scheduler_elapsed между чтениями не меняется, хотя IRQ идут. Оригинальная
заставка попытки не имеет таймера; она ждёт свежий ввод. Адреса ожидания и
инкремента описаны в [N06-ui.md](N06-ui.md). Поле жизней остаётся отдельным
`hero+0xD6`, значение 3; его нельзя путать с текущим номером попытки.

Для чистой сцены служит отдельный
[capture_clean_visual_dos.py](../../../ports/nds/tools/capture_clean_visual_dos.py).
Он использует замороженные транспортные функции первого коллектора,
запускает новую чистую копию, проходит то же меню и сохраняет настоящий
`attempt-popup` со счётчиком 1. Затем посылает **ещё один свежий Enter**,
дожидается счётчика 2 и сохраняет `play-clean`. Никакие pose, счётчики,
флаги паузы или guest-код не записываются.

Для активной игры нельзя требовать, чтобы за все 768 HTTP-чтений DAC
остановились анимации. Поэтому clean-проба сначала читает DAC, затем ищет
короткий bracket из двух одинаковых VGA RAM и двух одинаковых native RGB
кадров; после него вновь читает DAC. Палитры по краям длинного bracket должны
совпасть, весь VGA+DAC должен побайтно совпасть с независимым RGB, camera/hero
короткого bracket должны совпасть, а scheduler_elapsed за длинный bracket
обязан продвинуться. В `.data.bin` чистого кадра номер попытки уже равен 2.
Фаза конкретной анимации остаётся `unknown`; глобальная пауза не заявляется.

Фиксированные пути — `research/evidence/nds/n06/dos/<lang>/levelN-clean/`:
`attempt-popup.*`, `play-clean.*`, полный `report.json`, конфиг и журналы.
Повторные boot/story PNG не создаются; порядок штатного ввода записан
в отчёте. Пример одной команды, остальные пары задаются аналогично:

```powershell
C:/Source/wasdify/.venv/Scripts/python.exe -X utf8 ports/nds/tools/capture_clean_visual_dos.py ru 1 --output research/evidence/nds/n06/dos/ru/level1-clean --port 8147
C:/Source/wasdify/.venv/Scripts/python.exe -X utf8 ports/nds/tools/audit_visual_dos.py
```

Независимый аудитор не импортирует collector: он проверяет оригиналы,
копии, SHA текущих скриптов, все PNG CRC/индексы/палитры, полный RGB dump,
native data камеры и счётчиков, естественный переход 1→2 и продвижение
scheduler. `dos/manifest.json` получает PASS только после проверки обоих
наборов: шесть первых 3D-сессий и шесть clean PLAY-сессий.

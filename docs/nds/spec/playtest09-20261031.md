## Мерцание и удержание изображения

Причина playtest07 подтверждена кодом и наблюдениями предыдущего плейтеста:
при обновлениях текстур более 32 КиБ `stream_bulk_begin` выключал BG0 и 3D
rasterizer, пока preload и следующий swap не завершатся. Это предотвращало
исходную фатальную ошибку DMA, но давало чёрные вспышки при обычном движении.
Поднимать порог до 64 КиБ нельзя: отрицательный playtest06 уже нарушал окно
рендера. Проверки 192…213 и порог 32 КиБ сохранены.

Теперь на время такой операции выводится аппаратно сохранённый предыдущий
кадр MAIN с HUD. Видеопамять перераспределена:

| Банк | Назначение |
| --- | --- |
| A/B/D, 384 КиБ | Прежние текстуры 3D |
| E, 64 КиБ | Прежний MAIN BG/HUD |
| F | Прежняя палитра текстур |
| H, 32 КиБ + I, 16 КиБ | Все видимые 256×192 пикселя SUB BG8 |
| C, 128 КиБ | Аппаратный захват MAIN 256×192 RGB555 и временный framebuffer display |

H отображается с `0x06200000`, I с `0x06208000`. Нижние 64 невидимые строки
bitmap 256×256 не требуют backing: карта и frontend передают только 49 152
байта. SUB bitmap остаётся полным; его разрешение, индексы и палитра не урезаны.

`dok_nds_render_present` запускает capture MAIN в C. При большой замене
следующий VBlank завершает захват; capture отключается, MAIN выбирает MODE_FB2.
Текстуры загружаются при отключённом rasterizer. После submit и swap
восстанавливается сохранённый DISPCNT, затем захват для следующей операции.
Первичная загрузка уровня по-прежнему использует отдельный loading screen.

Это необходимо потому, что у DS нет полного framebuffer внутри 3D engine:
она повторно растеризует старую геометрию, используя 48-строчный кэш вывода. Просто оставить
BG0 включённым при отключении rasterizer недостаточно.
[GBATEK: Rendering Engine, Scanline Cache vs Framebuffer](https://mgba-emu.github.io/gbatek/#ds3dvideo),
а bank enums/DCAP/MODE_FB2 сверены с установленными первичными libnds headers
BlocksDS 1.24.0. Новая схема пока проверена в эмуляторе; физическая DS — N24.

Флаг LOADING для большой замены сохраняется: предыдущий FPS observer исключает
такие интервалы. Отсутствие чёрного кадра не является доказательством 60 FPS.
При загрузке новых текстур возможен повтор предыдущего изображения.

## HUD

Высота HUD осталась 38 пикселей, сцена — 154. Нижняя рамка (прежние строки
36 и 37) больше не рисуется. Верхняя рамка остаётся в строке 0; разделитель
перенесён из 19 в 20. Область сообщений выросла с 18 до 19 пикселей,
область чисел/значков — с 16 до 17: по одному освобождённому пикселю каждой.

Исходный FONT8 8×8 без масштабирования сохранён. Однострочное сообщение
начинается в y=7, двухстрочное — в y=3/11. Наличие второй строки определяется
тем же word-wrap, которым сообщение рисуется. Видимые цифры исходного FONT16
занимают строки 1…12 glyph: baseline y=23 помещает их в y=24…35, по центру
нижней области с округлением на полпикселя, согласованным со значками.
Пустые нижние строки FONT16 не записываются за границу HUD.

Оружие остаётся справа от патронов, ключи справа внизу; их отношение сторон
сохраняется. Банк UI не расширялся. Исходные RES не менялись.

Host oracle независимо читает исходные изображения/шрифты, проверяет все
546 сообщений, 1320 целевых растров, все signed16 числа и 132 669 защищённых
HUD-растров. INDEX8/RGB нижнего экрана и frontend проверены на трёх уровнях,
в обоих языках, включая паузу, drag/zoom и возврат карты.

## Проверка часов и анимаций

Глобальный разгон не обнаружен. `dok_world_clock` использует исходную шкалу
1193182/119 ≈10 026,74 тика/с; установленный systemCounter имеет BUS_CLOCK/64.
Живое наблюдение опубликованных часов на длинных отрезках даёт примерно
10 027…10 031 тика/с; небольшая разница связана с фазой публикации снимка.

`playtest_probe.py` читает реальные AI structs по DWARF точного ELF, кадры
sprite bindings и неизменённые signed интервалы из package animation metadata.
Для последовательных кадров ходьбы одной анимации проверяется, что разность
реальных `last_motion_ticks` не меньше интервала предыдущего кадра. Смена
состояния, пропущенные кадры, hurt/attack/death не выдаются за такую проверку.
В первичном прогоне трёх маршрутов было 6150 успешных проверок; ранних шагов нет.
Итоговые закреплённые результаты — в компактной сводке ниже.

Периоды ресурсов отличаются: у полёта мыши 500 тиков (около 49,87 мс/кадр),
у многих человеческих walking sequences — 2500 (около 249,33 мс/кадр).
Расчёт не зависит от FPS. Core AI, scheduler, clock и интервалы ресурсов
этим исправлением не изменены. Номинальный RES-период не доказывает совпадение
с фактическим темпом конкретного DOS PC: его dispatch зависит от кадрового цикла.
Пользовательское ощущение ускорения остаётся предметом визуального сравнения;
в чате запрошено, на каких врагах и в каком действии оно заметнее.

## Проверки и доказательства

Постоянные compiled inputs/ROM/ELF/map:
`research/evidence/nds/n23/candidates/playtest09-ru/`.
Итоговые runtime reports и snapshots наблюдателя:
`research/evidence/nds/n23/playtest09/`.
Компактная сводка — `analysis/nds-playtest09-20261031.json`.

Набор: LEVEL1 220 клеток, LEVEL2/3 по 100; живые joypad inputs, без инъекций
RAM/VRAM или скрытой перемотки. Для каждого удержания наблюдатель сравнивает
36 пикселей фактического LCD с чтением завершённого VRAM C capture (RGB555),
проверяет отсутствие полностью погашенной сцены. После освобождения capture
кадр может уже смениться на новую геометрию; это отдельно учитывается.

Live/LCD: все три уровня, RU/EN, 57 touch stages; также запуск без DLDI и
проверка packed frame/audio payload. Исходные EXE заново не анализировались;
никакие NE/Ghidra/DPMI адреса не переименовывались в ARM9 offsets.

закреплённый melonDS DS libretro 1.4.0. Runtime и host собираются с `-Werror`.

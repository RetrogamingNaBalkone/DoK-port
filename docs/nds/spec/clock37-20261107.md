# N23: обратный скачок системного счётчика в DraStic

7 ноября 2026 года. Работа в рамках N23; N24 не начата.

## Наблюдение и идентификация

Пользователь сообщил об остановке посреди перестрелки на LEVEL1 в DraStic.
Перед активной игрой уровень долго оставался запущенным без ввода. Отдельно
подтверждён холодный запуск ROM, без savestate/автопродолжения.

На фото читаются `playtest34-final-ru`, `main.c:1071`, `render_one`,
`simulation Status 3`, `Sim 1 rc3 evt1`, нулевые Game/AI/Combat/Effects,
GPU/audio fault. Последний принятый счётчик заканчивается на `FFFD`, новый —
на `0000` и меньше предыдущего. Длинные hex-строки на перспективном фото
не используются как машинно-точная выгрузка RAM. Нижний экран содержит
искажённый остаток карты; восемь событий по нему восстановить нельзя.

Поставка playtest34-final-ru известна по SHA-256
`c83b7f39be315a0e61e124195de43abe4b28e86232e138f522182120d0289a66`.
Это сопоставление видимой метки и source line; SHA ROM пользователя не считан.
Текущий локальный `dok.nds` перед работой был message36-ru, SHA
`1c340bf30161b3838150331e80dde1a24c0a9559a8bfd40b726e8d9586cf8416`.
Его независимые незакоммиченные изменения UI сохранены и вошли в новый кандидат.

`Sim 1` означает отказ `dok_events_dispatch`; `evt1` выставляется при ошибке
`read_ticks`. `dok_world_clock_read` возвращает INVALID_STATE, если платформа
вернула counter меньше `_last_counter`. Это проверенный непосредственный
механизм остановки. Утечка памяти, виновность стрельбы, порог общего времени
и точная причина неверного платформенного значения этим не доказаны.

## Машинная проверка и гипотеза

Исследован NDS ELF playtest34-final-ru (не DOS EXE): SHA-256
`341a588b966da27f3f23576352e4b2c1af9d6e7f63fc0e727b259bfa1cb42605`.
`systemCounterGetTicks` имеет ARM9 runtime/ELF VMA `0x01007838`, 96 байт,
SHA-256 `f6438b73b198b3d757d6c843ea8ed05b27e9fff4add775445d8fb9f97c5d9446`.
Это не файловое смещение, NE-сегмент или DPMI-селектор. Для извлечения
инструкций скрипт преобразует VMA через ELF section table.

SDK отключает IRQ CPU, читает программную старшую часть, TIMER2_DATA,
REG_IF, снова TIMER2_DATA, восстанавливает IRQ CPU. К старшей части
добавляется 65536, если IF_TIMER2 установлен либо второе чтение таймера меньше
первого. При обычной видимости регистров оба случая переполнения обработаны.

Unicorn исполняет эти реальные инструкции на пяти явных MMIO fixtures:
до переполнения, pending IRQ, переполнение между двумя чтениями, обслуженный
IRQ, предполагаемая задержка IF. Последний fixture задаёт оба чтения уже
нулевыми, но программный counter и IF ещё старыми. Тогда получается возврат
назад на 65533 ticks после предыдущего `...FFFD`: примерно 125,145 мс.
Fixtures используют условную старшую часть `0x27F20000`, не выдают её
за точную расшифровку фотографии.

Это проверка механизма при заданных регистрах, **не воспроизведение DraStic**.
Нет доказательства, что DraStic действительно публикует регистры именно так;
альтернативы включают преждевременную компенсацию IF в предыдущем чтении.
Младший TIMER2 переполняется каждые `65536*64/33513982` ≈125,15 мс,
а не впервые после нескольких минут. Долгий простой увеличивает число
возможностей редкой гонки; сам по себе не доказывает накопление ошибки.

## Поведение кандидата clock37

Только NDS platform clock adapter повторяет обратное чтение SDK до восьми
раз. Возвращается реальное повторное значение SDK: нет clamp к предыдущему
времени, сброса часов, синтетического прибавления периода или очистки fault.
Обычный путь выполняет прежнее единственное чтение. Если откат сохраняется,
последнее полученное значение доходит до прежнего INVALID_STATE/fatal guard.
Смена SDK, таймеров и исходной игровой арифметики не требуется.

`Retry` на crash screen — число дополнительных SDK-чтений за холодный запуск,
включая неудачные. Ненулевое число само по себе не означает успешное исправление.
Фатальная диагностика по-прежнему не перечитывает аппаратный таймер.

```powershell
py -3.14 -B -X utf8 ports/nds/tools/performance/check_sdk_counter_boundary.py build/nds/n23/playtest34-final-ru
py -3.14 -B -X utf8 ports/nds/tools/performance/check_platform_clock_retry.py
py -3.14 -B -X utf8 -c "import json,sys; from pathlib import Path; sys.path.insert(0,'ports/nds/tools/performance'); from build import build; build('fresh-label-ru',json.loads(Path('build/nds/n23/message36-ru/build-manifest.json').read_text())['feature_selection'])"
py -3.14 -B -X utf8 ports/nds/tools/check_playtest34_emulator.py build/nds/n23/clock37-ru
py -3.14 -B -X utf8 ports/nds/tools/performance/check_crash_diagnostic.py build/nds/n23/clock37-ru --fault clock
py -3.14 -B -X utf8 ports/nds/tools/performance/check_idle_simulation.py build/nds/n23/clock37-ru 84000
py -3.14 -B -X utf8 ports/nds/tools/package_rom.py --target build/nds/n23/clock37-ru
git diff --check
```

Сборка общим BlocksDS вне песочницы: MSYS2 внутри неё получает signal pipe error5.
Новый label immutable; `fresh-label-ru` при повторе заменить новым именем,
а последующие команды направить в него.

Host: 37 checks, включая краткий откат с восстановлением, непрерывность дробного
времени, счётчик старше 32 бит, паузу и устойчивый откат. Компилируются реальные
`platform/time/clock.c` и `core/time.c`; подменён только источник SDK.
При устойчивом откате выполнено ровно девять чтений, состояние world clock
и выходной аргумент не изменились, INVALID_STATE сохранён.
MelonDS UI/input/settings/FAT/cold restart и persistent-clock/events injection PASS;
новая строка Retry помещается на верхнем LCD (снимок просмотрен).
Память: static348900 B, startup520192 B, SDK200704 B; прежние лимиты сохранены.

ROM clock37-ru: 10179072 байта, SHA-256
`9167b17d84bb109cbdd3745b08d119f9d52d4e8574aa68b214f09b1866102bc4`.

564,39 секунды wall time (~2,5×). Это простой на стартовой позиции, без стрельбы.
Поставка `artifacts/nds/dok.nds` байтово совпадает с кандидатом; пакет и пять
встроенных payload проверены упаковщиком. Все635 pins кандидата совпали.
Итоги — `analysis/nds-clock37-20261107.json`, полные отчёты и два контрольных

Ограничения: причина на уровне регистров DraStic не доказана; bounded retry —
кандидат восстановления, не подтверждённое устранение пользовательского сбоя.
